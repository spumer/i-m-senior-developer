# Разбор красного прогона

Порядок проверен на реальном разборе: первый полный прогон planner был красным,
и каждая гипотеза проверялась отдельно, а не менялась вместе с критерием.

## Шаг 1. Открыть агрегат, а не догадываться

Свежий `aggregate-result.json` содержит по каждому повтору: оценку, признак
`passed`, объяснение каждого критерия, путь к трассе и стоимость. Начинать с него.

Полезные признаки в JSON:

- `partial` и `partialReason` — прогон неполный, выводы делать нельзя;
- `explanation` критерия — точная причина отказа;
- `skippedPaidGraders` — платный критерий не считался;
- `error` повтора — среда, а не обязательно дефект.

## Шаг 2. Отделить критерий от поведения

Отказ `tool_used: called 0x` означает одно из трёх:

1. инструмент недоступен кейсу;
2. имя инструмента в критерии не совпадает с фактическим;
3. модель действительно не вызвала инструмент.

Различать по началу трассы: там перечислены доступные инструменты, скиллы и
загруженные плагины. Если инструмент и скилл присутствуют, значит механизм
доставки работает и дефект в поведении.

## Шаг 3. Проверить модель

Модель — значимое условие. Наблюдение от 19.08.2026 на Claude Code `2.1.234`,
плагин planner: маршрутизация в продуктовую проработку не сработала ни в одном из
шести повторов на `sonnet`; на `opus` те же кейсы вызвали скилл. Это одно
наблюдение на одном наборе, а не общий закон о моделях.

Проверять дешёвым пилотом одного кейса:

```bash
claude plugin eval <plugin> --case <case> --runs 1 --ablation none \
  --no-scaffold --no-publish --model <model> --max-cost-usd 1 \
  --output-dir <fresh-dir>
```

Если пилот на другой модели проходит, закрепление модели в скрипте выбрано
неверно: закреплять ту, на которой плагин используется.

## Шаг 4. Не ослаблять критерий

Запрещённые способы «починить» прогон:

- понизить `--threshold`;
- уменьшить число повторов;
- убрать упавший критерий;
- ослабить регулярное выражение до совпадения с любым ответом;
- убрать операторское разрешение опасного инструмента, чтобы запрет стал
  автоматическим.

Каждый из них сохраняет зелёный цвет и уничтожает доказательную силу.

## Шаг 5. Отличить шум среды от дефекта

Признаки шума:

- `error: timed out after Ns` при работающем скилле;
- `grader threw: judge call failed` с сетевой ошибкой;
- разные результаты одного кейса между прогонами без изменений в плагине.

Действия: повторить прогон; при устойчивом таймауте поднять `timeout_seconds`
кейса, потому что работающий скилл занимает больше времени, чем прямой ответ.

Отдельный ожидаемый случай: сообщение `error: exit 1: (no stderr)` у успешного
повтора. Скилл дошёл до вопроса человеку, а в headless-режиме такой вопрос
недоступен. Договор повтора задают критерии и оценка, поэтому проверяющий скрипт
не должен механически отклонять повторы с непустым `error`.

## Шаг 6. Искать устойчивость в механизме

Если поведение наступает не всегда, переписывание `description` даёт неустойчивый
результат: один кейс поднимается, другой остаётся на одном успехе из трёх.

Устойчивое срабатывание требует структурного механизма. Образец —
`deterministic-routing.md`.

## Что записать после разбора

Отчёт по плагину должен содержать не только зелёный итог, но и историю:
какая гипотеза проверялась, чем опровергнута, что оказалось причиной. Это
предотвращает повторный разбор той же проблемы через полгода.
