# Отчёт по проверке плагина

## Зачем отдельный отчёт

Правила проверки и результат проверки живут в разном темпе. Правила меняются
редко и одинаковы для всех плагинов. Отчёт меняется после каждого прогона и
относится к конкретной версии конкретного плагина.

Смешение этих двух вещей в одном файле приводит к тому, что общие правила
устаревают вместе с числами, а числа теряются среди правил.

Разделение: общая часть — один набор страниц на репозиторий; отчёт — один файл на
плагин.

## Где хранить

Конвенция, применённая в этом репозитории: сайт документации собирается из
каталога `docs/`, внутри него `docs/testing/` для общих правил проверки.

Числа наблюдённого прогона в документацию не переносятся: перенесённые, они
устаревают молча — страница не знает, что прогон повторили. Числа остаются в
`aggregate-result.json` прогона, каталог результатов игнорируется git, а
найденное прогоном ограничение называется в документации словами.

Если у проекта нет сайта документации, отчёт кладут рядом с набором:
`<plugin>/evals/REPORT.md`. Важно не место, а отделение от общих правил.

## Обязательные поля

| Поле | Почему обязательно |
|---|---|
| дата прогона | результат привязан ко времени, поведение модели меняется |
| версия Claude Code | формат результата и поведение зависят от версии |
| версия плагина | отчёт относится к конкретному содержимому |
| модель и модель-судья | другая модель даёт другой результат |
| порог | без порога оценка нечитаема |
| стоимость и длительность | нужны для выбора предела стоимости |
| признак частичного прогона | частичный прогон не является проверкой |
| оценка и число успешных повторов по каждому кейсу | это и есть результат |
| причина каждого отказа | наблюдаемая, из агрегата, а не предположение |
| открытые вопросы | что осталось нерешённым и чьё решение требуется |

## Шаблон

```markdown
# Отчёт: <плагин>

Что проверяется: <одно предложение о предмете проверки>.

## Последний прогон

| Параметр | Значение |
|---|---|
| Дата | <дата> |
| Claude Code | `<версия>` |
| Версия плагина | `<версия>` |
| Модель | `<модель>`, судья `<модель>` |
| Порог | `<порог>` |
| Стоимость | `$<сумма>` |
| Длительность | <минуты> |
| `partial` | `<true|false>` |

Итог: <проходит | не проходит>.

| Кейс | Оценка | Успешных повторов |
|---|---|---|
| `<кейс>` | `<оценка>` | <N> из <M> |

## Что покрыто

- `<кейс>` — <что именно доказывает>.

## Известные ограничения

- <что проверка не подтверждает>.

## Как обновить этот отчёт

<команда прогона>
```

## Что писать в историю отказов

Если проверка была красной и стала зелёной, отчёт обязан сохранить путь: какая
гипотеза проверялась, чем опровергнута, что оказалось причиной. Иначе через
полгода тот же разбор придётся повторить с нуля.

Формулировать по наблюдению. «Скилл не вызывался ни в одном из шести повторов» —
наблюдение. «Модель плохо понимает описание» — догадка, в отчёт не идёт.

## Чего в отчёте быть не должно

- утверждения «проверка проходит» без зелёного полного прогона;
- пилотного запуска с одним повтором в роли успеха;
- чисел, взятых из прошлого прогона после изменения плагина;
- пересказа общих правил проверки — для них есть отдельные страницы.
