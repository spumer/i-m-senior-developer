# Проверяющий скрипт прогона

Прямой вызов `claude plugin eval` release-проверкой не считается. Слишком много
способов получить зелёный цвет без доказательства: забыть операторское разрешение
инструмента, принять частичный результат, прочитать старый каталог результатов.

Скрипт живёт рядом с набором: `<plugin>/evals/run.py`.

## Что скрипт обязан делать до расходов

1. Требовать точную версию Claude Code. Обновление CLI меняет формат результата и
   поведение модели — молчаливый переход недопустим.
2. Проверять, что гейт раннего доступа открыт: запуск в пустом временном каталоге
   должен дать сообщение об отсутствии кейсов, а не сообщение о раннем доступе.
3. Прогонять структурные проверки плагина.
4. Создавать новый, ещё не существующий каталог результатов. Чужой каталог
   принимать нельзя: старый успешный результат выдаст себя за новый.

## Что скрипт обязан зашить в команду

Флаги, которые нельзя оставлять на усмотрение вызывающего:

- отключённое сравнение с запуском без плагина, если оно бессмысленно для набора;
- фиксированное число повторов;
- операторское разрешение инструментов, нужных кейсам для доказательности;
- отключённый подготовительный скрипт;
- запрет публикации отчёта;
- строгий порог;
- закреплённые модель и судья;
- предел стоимости;
- свежий каталог результатов.

Пользовательские позиционные аргументы принимать не нужно: они превращают полный
прогон в выборочный.

## Что скрипт обязан проверить после прогона

Нулевой код выхода недостаточен. Обязательные проверки агрегата:

- версия схемы результата;
- `partial` равен `false`;
- присутствуют ровно ожидаемые кейсы, без пропусков и лишних;
- у каждого кейса ожидаемое число повторов в основной ветке;
- каждый повтор успешен и имеет полную оценку;
- ни один платный критерий не пропущен;
- рядом лежат свежие файлы результата и отчёта.

Любой ненулевой код CLI — отказ, включая код достигнутого предела стоимости и код
прерывания.

**Чего проверять не нужно.** Непустое поле `error` у повтора само по себе
отказом не является: маршрутизационный кейс закономерно доходит до вопроса
человеку, недоступного в headless-режиме. Договор повтора задают критерии и
оценка.

## Как проверить сам скрипт без расхода токенов

Скрипт — обычный код, поэтому он проверяется обычными тестами через подменный
CLI. Нужны две точки подмены: путь к исполняемому файлу CLI и корень каталога
результатов.

Подменный CLI записывает фактические аргументы в журнал и умеет отвечать на:
запрос версии, проверку гейта, структурную проверку и сам прогон — создавая
заготовку результата.

Обязательные сценарии тестов:

| Сценарий | Ожидание |
|---|---|
| полный успех | код `0`, точные аргументы, четыре структурные проверки, свежий каталог |
| несовпадение версии | отказ до проверки гейта |
| закрытый гейт | отказ до структурных проверок |
| коды прогона `1`, `2`, `130` | отказ |
| `partial: true` | отказ |
| пропущенный кейс | отказ |
| меньше повторов, чем нужно | отказ |
| пропущенный платный критерий | отказ |
| повреждённый или отсутствующий результат | отказ |
| отсутствующий файл отчёта | отказ |
| позиционный аргумент | отказ до обращения к CLI |

Успешный сценарий обязан проверять фактические аргументы, иначе тест не заметит
потерю операторского разрешения или включённую публикацию.

## Доказательство, что проверка работает

Зелёные тесты не доказывают ничего сами по себе. Проверка принимается после
наблюдённого падения: скопировать скрипт во временный каталог, удалить одну
защиту, запустить неизменённые тесты и увидеть падение именно нужного теста.
После прогона сверить отпечатки оригиналов.

Проверенный пример: удаление отказа по признаку частичного результата уронило
тест соответствующего случая при неизменных оригиналах.

## Предел стоимости

Предел выбирать по измеренной стоимости, а не наугад. Измерение от 19.08.2026,
Claude Code `2.1.234`, плагин planner: зелёный прогон трёх кейсов по три повтора
на `opus` с судьёй `haiku` стоил `$3.06` и занял 17 минут. Предел там выставлен
`$6` — вдвое выше измеренного: запас есть, а неограниченного расхода нет.
