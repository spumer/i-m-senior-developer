# Синтетические паттерны AI-текстов

> Каталог паттернов, которые AI-авторы систематически вносят в документы.
> Каждый паттерн — отдельная категория находок для Clarity Validator.
>
> **Отличие от `ai-prose-detector`:** тот ловит стилистические AI-паттерны
> в художественной прозе (дистанция, метафоры, физиология). Этот — ловит
> **смысловые** синтетические паттерны в технических документах:
> искажения мышления, leaked контексты, выдуманные процедуры.

## 1. Negation of Nothing (отрицание незаданного)

**FPF-основа:** A.1.1 BoundedContext — «Local rules leak globally»

**Что это:** отрицание правила или ограничения, которое в текущем контексте никто не устанавливал. Обычно — residual от прошлых версий: раньше обсуждалось введение ограничения, его отвергли, но отрицание осталось жить в тексте как артефакт.

**Детекция:**
- «Без X» / «Не X» / «Нет Y» — где X или Y в этом контексте никогда не упоминались
- «Не автоматическая процедура» — если автоматизация нигде не обсуждалась
- «Без триггеров по дням» — если никаких дневных триггеров не было
- «Не путать с Y» — если Y не определён в документе

**Тест:** подставь фразу в другой случайный документ. Если смысл не меняется — значит она **ни к чему не привязана** в текущем контексте. Это leaked invariant.

**Пример (был в разделе про релизы):**
```
❌ Назначение релиз-менеджера — решение команды, не автоматическая
   процедура. Без триггеров по дням.
```
Никаких «дневных триггеров» в разделе про назначение релиз-менеджера не обсуждалось. Это residual от удалённой дискуссии про SLA.

```
✅ Назначение релиз-менеджера — решение команды.
```

**Почему опасно:** читатель начинает искать «дневные триггеры», которых нет, — думает, что пропустил контекст, или ищет другой документ.

## 2. AI-метки провенанса

**FPF-основа:** A.7 Strict Distinction (смешение описания и метаданных)

**Что это:** вставки в текст, указывающие кто/когда/откуда взял утверждение. Полезно в changelog и внутренних артефактах. **Вредно** в публичной документации — читатель не должен видеть провенанс каждой фразы.

**Маркеры:**
- `(Owner, Q5)`, `(Alt-A, D2, подтверждено Decider Q1)`
- `(Team)`, `(Reviewer, TechLead)`, `(Team/CI)`
- `**Фрейм (Owner):** ...`, `**Обоснование (Q3):** ...`
- Ссылки на внутреннюю нумерацию: `см. DEC-001`, `по OQ-M1`

**Тест:** если метка нужна — провенанс уместен в Changelog и в commit message, не в теле публичного документа.

**Пример:**
```
❌ **Фрейм (Owner, Q5):** телеметрия по фичам — это вклад в observability.
❌ Роль кеша (Alt-A, D2, подтверждено Decider Q1):
```

```
✅ Телеметрия по фичам — это вклад в observability.
✅ Роль кеша:
```

## 3. Плейсхолдеры, не привязанные к флоу

**FPF-основа:** A.7 Strict Distinction (Description ≠ Work) + Evidence Graph

**Что это:** шаблонные формулировки с `[имя]`, `[дата]`, `[причина]` — которые предполагают, что автор сообщения знает конкретные значения. Часто — не знает, потому что флоу не предусматривает такой ввод.

**Детекция:** любые `[...]` в примерах формулировок. Проверь: где читатель возьмёт эти значения?

**Пример (был в contribution-гайде):**
```
❌ Шаблон: «Сомневаюсь по [причина], хочу согласовать с [имя],
   дедлайн [дата]»
```
Контрибьютор не знает конкретного имени — он пишет в issue и отмечает владельцев секции. Плейсхолдер `[имя]` привязан к флоу «я знаю кого пинговать», которого нет.

```
✅ Открой issue, опиши в чём сомневаешься, отметь maintainers
   затронутой секции.
```

**Вариант проверки:** спроси себя — «кто в реальном процессе заполнит этот плейсхолдер и откуда возьмёт значение?».

## 4. Выдуманный флоу

**FPF-основа:** A.7 Strict Distinction (MethodDescription vs Work) + A.10 Evidence Graph

**Что это:** AI описывает процесс, которого не существует, как будто он существует. Часто — подстановка типичного шаблона (бот назначает, лид эскалирует, система уведомляет) туда, где реальный процесс устроен иначе.

**Детекция:**
- «Бот назначит ревьюера» — а бот этого не делает
- «Система уведомляет X» — а системы такой нет
- «После этого Y автоматически делает Z» — а никто не делает
- «Лид секции созывает встречу» — а встречи не созываются формально
- Любая формулировка «кто-то там что-то делает» без верификации у владельца процесса

**Тест:** для каждого субъекта в процедуре спроси — «это реально происходит или я это выдумал по шаблону?».

**Пример (был в contribution-гайде):**
```
❌ Открой issue. Бот автоматически назначит ревьюера из core-команды,
   и вы вместе примете решение.
```
Реальность: бот ревьюеров не назначает, автор сам отмечает maintainers.

```
✅ Открой issue, опиши развилку. Отметь maintainers затронутой секции
   и примите решение в обсуждении.
```

**Правило:** если описываешь процесс, в котором участвует роль X — проверь через владельца процесса или существующие документы, что X делает именно это.

## 5. Имитация авторитета через цифры

**FPF-основа:** A.10 Evidence Graph — «claim without proof is opinion»

**Что это:** необоснованные конкретные цифры, создающие видимость измерения. AI часто вставляет «80%», «15-20 часов», «в 3 раза эффективнее» — цифра кажется конкретной, но никто её не измерял.

**Детекция:**
- Процент без источника: «снимает 80% нагрузки», «в 90% случаев работает»
- Диапазон часов без хронометража: «15-20 часов на цикл»
- Сравнения без замера: «в 3 раза быстрее», «вдвое меньше»
- Пороги без валидации: «расхождение <1% на 4 из 5 метрик»

**Тест:** задай вопрос «как это считалось?». Если ответа нет — цифра выдумана.

**Правило:**
- Если цифра нужна практику для планирования — заменить на список компонентов: «~30-60 мин на подготовку схемы, ~1.5 часа на прогон» (то, что реально измеримо)
- Если цифра критерий решения — явно пометить «ориентир, уточняется после первых прогонов»
- Если цифра — украшение без функции — удалить

**Пример:**
```
❌ Включи кеш — снимает 80% нагрузки
❌ Полный цикл миграции ≈15-20 часов за ~2 спринта
```

```
✅ Включи кеш — обычно заметно снижает нагрузку; замерь на своём профиле
✅ Прикинь по составу цикла: столько-то на схему, столько-то
   на прогон. Реальные трудозатраты зависят от объёма данных.
```

## 6. Неуместная иноязычная вставка

**FPF-основа:** F.0.1 Contextual Lexicon Principles

**Что это:** слово или оборот из **другого** языка там, где в языке документа есть точный аналог, и иноязычное слово не несёт нового смысла. Паттерн **языко-нейтрален**: он про вставку чужого языка в текст на любом языке (английское слово в русском, англицизм во французском, латинизм в английском и т.д.), а не только про «англицизмы в русском». Часто — прямой перенос из AI-training data или из внутренних обсуждений.

**Что НЕ паттерн (допускать):**
- **Устоявшиеся заимствования**, ставшие нормой языка документа. В русском это, например, «фидбек», «баг», «коммит», «дедлайн», «релиз» — их **не трогать**, замена на кальку-перевод звучит хуже оригинала.
- **Термины-жаргон**, ставшие рабочей нормой команды (round-robin, p95) — допустимы, при первом упоминании пояснить.
- Случаи, где аналог языка документа звучит искусственно — оставить иноязычное слово с пояснением. Русификация ради русификации тоже вредна.

**Что паттерн (флагать):**
- Маркетинговый шум без функции: seamless, cutting-edge, best-in-class.
- Калька-дублёр рядом с родным словом: `below-threshold` рядом с «ниже порога».
- Номинализация-перенос вместо живого оборота языка документа (см. `russian-style`, правило 1).

**Примеры спорных слов (требуют классификации):**

| Слово | Если устоялось → допустить | Если калька → заменить |
|-------|----------------------------|------------------------|
| retention | (нет, в общей речи) | удержание |
| drift | (нет) | отклонение, дрейф |
| quality score | (нет) | показатель качества |
| graceful degradation | да, термин (с пояснением) | мягкая деградация |
| cooldown | да, прижилось | пауза, перерыв |

### Протокол классификации (при сомнении — спросить Человека)

Граница «устоявшееся заимствование ↔ неуместная калька» подвижна и зависит от
аудитории. **Не решай в одиночку, когда не уверен.**

1. **Очевидно устоявшееся** (фидбек, баг, коммит) → допустить молча, не флагать.
2. **Очевидная калька-дублёр** без новой семантики → флагать с заменой.
3. **Спорное** (непонятно, прижилось ли слово для этой аудитории) → **не выносить вердикт сам**. Вынести Человеку: «слово X — считать устоявшимся заимствованием или заменить на Y?».
4. **После решения Человека — записать его в память** (персональный лексикон допустимых/недопустимых слов), чтобы в следующий раз не спрашивать повторно. Формат записи: слово → вердикт (допустить / заменить на Y) → для какой аудитории/языка.

При старте проверки сверяйся с уже накопленными в памяти решениями по лексикону —
повторно по тем же словам Человека не дёргать.

## 7. Design-time ↔ Run-time смешение

**FPF-основа:** A.7 Strict Distinction (MethodDescription vs Work) + FPF-Spec §467 «Conflation of Plan and Reality»

**Что это:** в одном абзаце смешиваются утверждения из design-time контекста (как мы решили, почему рассматривали альтернативы) и run-time контекста (как это работает в реальности, что делать читателю-практику).

**Маркеры:**
- «Альтернативы Alt-B и Alt-C рассмотрены и сняты Decider'ом» — в публичном документе
- «Это решение принято потому что...» — в инструкции для практика
- «Q3: заложить место под метрику качества» — в описании процесса
- Упоминания «проектных сессий», «ревью ролями», «решений владельца» — в run-time документе

**Тест:** спроси — «читателю публичного документа нужна эта информация для его работы?». Если нет — это design-time, выносим в changelog или внутренний артефакт.

**Пример:**
```
❌ Альтернативы Alt-B (синхронный кеш) и Alt-C (без кеша) рассмотрены
   и сняты Decider'ом: большие операционные издержки.
```

```
✅ (удалить из публичного текста, оставить в Changelog черновика)
```

## 8. Панибратский или AI-приподнятый тон

**FPF-основа:** BoundedContext (тон — часть контракта контекста)

**Что это:** AI сваливается либо в панибратство («все мы ребята занятые»), либо в приподнято-корпоративный стиль («в рамках осуществления деятельности», «с целью обеспечения»). Осознанный авторский живой тон — другое дело, его не трогать (см. `russian-style`, правило 4).

**Детекция:**
- Фамильярные обороты: «ребята», «все мы», «нам всем», «понимаю, бывает» — если это не авторский стиль
- Канцелярит: «в рамках», «с целью», «осуществлять», «подлежит», «имеет место быть»
- AI-вежливость: «важно отметить, что», «следует учитывать», «необходимо помнить»
- Эмоциональные интенсификаторы без функции: «действительно важно», «крайне критично», «абсолютно необходимо»

**Правило:** нейтральный прямой тон. Технический документ не должен звучать ни как отчёт в министерство, ни как синтетическое заигрывание от лица системы.

**Примеры:**
```
❌ В рамках осуществления роли ревьюер обязан обеспечить присутствие
❌ Важно отметить, что критически важно помнить о необходимости
```

```
✅ Ревьюер отвечает в разумный срок, учитывая загрузку
✅ (удалить преамбулу полностью, перейти к сути)
```

## 9. Self-justifying loop

**FPF-основа:** A.10 Evidence Graph failure mode #3

**Что это:** обоснование изменения через само изменение. Классика AI-псевдоаргументации.

**Детекция:**
- «Мы делаем X, потому что X работает»
- «Это правильное решение, потому что оно устраняет проблему»
- «Один человек апрувит, агрегирует и решает — и это не конфликт интересов, а наоборот, гарантия объективности»
- Любая формула вида «А → А» под видом причинно-следственной связи

**Пример:**
```
❌ Релиз-менеджер одновременно собирает, тестирует и катит релиз — это не
   концентрация ответственности, а наоборот, единая точка контроля.
```
Утверждение «не концентрация, а наоборот» ничем не подкреплено, кроме желания автора.

```
✅ Релиз-менеджер одновременно собирает, тестирует и катит релиз. Риск
   концентрации закрывается защитами §5.1 (чек-лист, второй апрув, аудит).
```

## 10. Ссылка на несуществующее

**FPF-основа:** A.10 Evidence Graph + A.7 (MethodDescription vs Work)

**Что это:** ссылка на файл, секцию, роль или артефакт, которых в реальности не существует. Обычно — AI предположил что они должны быть.

**Детекция:**
- Ссылки на файлы проекта — проверить через Glob
- Ссылки на якоря `#section-name` — проверить что якорь есть
- Упоминание ролей, процессов, инструментов — проверить что они существуют
- «См. Confluence» — проверить что страница существует

**Пример (был в черновике):**
```
❌ зафиксировано в аудите SETUP.md
```
Файла `SETUP.md` в проекте не существует. Был выдуман AI.

**Правило:** все ссылки из сгенерированного текста — верифицировать. Если ссылка — на внутренний файл проекта, использовать Glob/Read для подтверждения.

## 11. Скачки логики

**FPF-основа:** B.5 Canonical Reasoning Cycle

**Что это:** вывод без промежуточной посылки. Из A следует C, но B пропущено.

**Детекция:**
- Правило без установленной посылки: «Линтер красный — мерж блокируем» — почему линтер важнее тестов, когда это установлено?
- Вывод с «следовательно» там, где посылка не дана
- «Очевидно, что X» без объяснения откуда очевидно

**Правило:** каждое правило должно быть либо (а) обосновано в этом же документе раньше, либо (б) явно помечено как дизайн-решение.

## 12. Дублирование вывода в разных секциях

**FPF-основа:** A.11 Ontological Parsimony + A.1.1 BoundedContext

**Что это:** одно и то же решение/правило сформулировано разными словами в двух секциях одного документа. Проблема: когда одну формулировку обновят, вторая отстанет — рассогласование.

**Детекция:**
- Одна и та же тема в двух секциях
- Таблицы с пересекающимся содержанием
- «Что проверяет CI» + «Как принимать решение о мерже» содержат одни и те же выводы

**Правило:** каждое правило — **одно каноническое место**. Остальные секции — только ссылки.

**Пример:**
```
❌ Секция «Что проверяет CI»: «Решаем по линтеру»
   Секция «Правила мержа»: «Линтер красный, но на генерёжке → мержим»
```
Одно правило в двух местах разными словами.

```
✅ Секция «Что проверяет CI»: только Knowledge (что проверка демонстрирует)
   Секция «Правила мержа»: все решения — здесь, один раз
```
