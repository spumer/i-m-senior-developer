# Пять проверок Clarity Validator — подробное описание

## Проверка 1: Смешение слоёв внутри файла

**FPF-основа:** A.7 Strict Distinction + Intellect Stack

**Что ищем:**
- Утверждения разных когнитивных слоёв в одной секции / абзаце / ячейке таблицы
- Императив (Action) в описательной секции (Knowledge)
- Стратегическое решение (Strategy) в описании структуры (Structure)
- Скачок через слой: Knowledge → Strategy без Action

**Как проверять:**

1. Для каждой секции определить **заявленный слой** по заголовку:
   - «Что проверяем» / «Что показывает» → Knowledge
   - «Как проводить» / «Что делать» → Action
   - «Как принимать решение» / «Правило решения» → Strategy
   - «Из чего состоит» / «Формат» → Structure
   - «Кто отвечает» / «Процесс согласования» → Governance

2. Пройти по каждому утверждению в секции и определить **фактический слой** (тест подстановки из intellect-stack.md)

3. Если заявленный ≠ фактический → **находка**

**Формат находки:**

```
СЛОЙ-СМЕШЕНИЕ: [файл]:[секция]
  Заявленный слой: Knowledge
  Утверждение: «Решаем по ревью»
  Фактический слой: Strategy
  Рекомендация: перенести в секцию «Правило решения»
```

**Серьёзность:**
- Смешение в документе для конечного пользователя (внешний читатель) → **высокая**
- Смешение во внутреннем артефакте → **средняя**
- Смешение в черновике → **низкая** (отметить, не блокировать)

## Проверка 2: Консистентность между файлами

**FPF-основа:** A.1.1 BoundedContext (значение локально, перевод явный)

**Что ищем:**
- Одно правило / утверждение / критерий сформулировано по-разному в двух файлах
- Противоречия: файл A говорит X, файл B говорит не-X
- Дублирование: одна и та же информация в двух местах (risk of drift)
- Ссылка на правило, которое в целевом файле изменилось или удалено

**Как проверять:**

1. Составить список **ключевых утверждений** в проверяемом файле (правила, критерии, определения)
2. Для каждого — Grep по связанным файлам: не упоминается ли это же утверждение
3. Если упоминается — сравнить формулировки
4. Если расходятся → **находка**

**Типичные пары файлов для проверки:**
- CONTRIBUTING ↔ гайд по онбордингу (правила поведения, SLA ревью)
- README ↔ docs/ (описания возможностей, команды запуска)
- API-reference ↔ примеры использования (сигнатуры, имена полей)
- index.md ↔ все файлы (навигация, описания разделов)
- Гайд по релизам ↔ runbook (раздел про роли)

**Формат находки:**

```
РАССОГЛАСОВАНИЕ: [файл_A]:[секция] ↔ [файл_B]:[секция]
  Файл A: «Ответ ревьюера в день PR, максимум +1 рабочий день»
  Файл B: «Регламент ревью до двух рабочих дней»
  Тип: противоречие / дублирование / устаревшая ссылка
  Рекомендация: выбрать каноническую версию, второй дать ссылку
```

## Проверка 3: Логика аргументации

**FPF-основа:** A.10 Evidence Graph + B.5 Canonical Reasoning Cycle

**Что ищем:**

1. **Вывод без посылки.** Утверждение «X, потому что Y» — но Y нигде не установлено
2. **Скачок логики.** Из A следует C, но пропущен промежуточный B
3. **Self-justifying loop.** «Мы делаем X, потому что X работает» без внешнего evidence
4. **Circular reference.** Секция A ссылается на секцию B, секция B — обратно на A, ни одна не самодостаточна
5. **Assertion without evidence.** Утверждение подаётся как факт, но нет источника (данные, опыт, ссылка)
6. **Несоответствие между описанием и инструкцией.** Описание говорит одно, инструкция требует другое

**Как проверять:**

1. Для каждого **вывода/правила** в тексте задать: «Откуда это следует?»
2. Если ответ — другое место в этом же тексте → проверить что оно самодостаточно
3. Если ответ — «это очевидно» → пометить как допущение (может быть ок, но должно быть явным)
4. Если ответа нет → **находка**

**Формат находки:**

```
ЛОГИКА: [файл]:[секция]
  Утверждение: «Линтер красный — мерж блокируем, даже если тесты зелёные»
  Тип: вывод без явной посылки
  Отсутствует: почему линтер приоритетнее тестов (посылка не введена в этой секции)
  Рекомендация: добавить посылку или ссылку на секцию где она установлена
```

## Проверка 4: Терминология

**FPF-основа:** A.1.1 BoundedContext + F.0.1 Contextual Lexicon Principles

**Что ищем:**

1. **Одна вещь — разные имена.** «Блок» / «секция» / «модуль» для одного и того же. «Порог» / «лимит» / «уровень» / «критерий»
2. **Одно имя — разные вещи.** «Хост» значит и «сервер», и «функция-обёртка» в разных местах
3. **Неуместная иноязычная вставка при наличии аналога в языке документа.** Слово из другого языка соседствует с равнозначным словом языка документа — и не несёт нового смысла (например `below-threshold` рядом с «ниже порога»). НЕ относится к устоявшимся заимствованиям, которые стали нормой языка (в русском: «фидбек», «баг», «коммит», «дедлайн») — их трогать не надо. Подробно — паттерн 6 в `synthetic-patterns.md`.
4. **Терминологический дрифт.** В начале файла «мерж», в конце «слияние» — для одного и того же действия
5. **Расхождение с глоссарием проекта.** Если есть glossary.md — проверить соответствие

**Как проверять:**

1. Собрать все **ключевые термины** в файле
2. Для каждого — поиск синонимов и вариаций в этом же файле и связанных файлах
3. Если вариации найдены → проверить: это синонимы или разные понятия?
4. Если синонимы → **находка** (унифицировать)
5. Если разные понятия с одним именем → **находка** (развести)

**Формат находки:**

```
ТЕРМИНОЛОГИЯ: [файл]
  Термин A: «зовём» (строки 270, 275)
  Термин B: «пригласить» (строка 269)
  Тип: синонимы одного понятия
  Рекомендация: унифицировать на «пригласить» (как в форме ОС)
```

## Проверка 5: Синтетические паттерны AI-текста

**FPF-основа:** A.7 Strict Distinction + A.10 Evidence Graph + A.1.1 BoundedContext + F.0.1 Contextual Lexicon

**Что это:** каталог специфичных для AI-авторов смысловых искажений. Отличается от проверок 1-4 тем, что это готовый **набор распознаваемых паттернов** — не нужно выводить проблему логически, достаточно сравнить с шаблоном.

**12 паттернов** (подробно в `references/synthetic-patterns.md`):

| # | Паттерн | Маркер |
|---|---------|--------|
| 1 | Negation of nothing | «Без X», «не Y» где X/Y в контексте не обсуждались |
| 2 | AI-метки провенанса | `(Owner, Q5)`, `(Alt-A, D2)`, `**Фрейм:**`, `см. DEC-NNN` |
| 3 | Плейсхолдеры без флоу | `[имя]`, `[дата]`, `[причина]` без источника значения |
| 4 | Выдуманный флоу | «Бот назначает ревьюера», «система уведомляет» — не проверено |
| 5 | Имитация авторитета через цифры | «80% нагрузки», «15-20 часов», «в 3 раза быстрее» без источника |
| 6 | Неуместная иноязычная вставка | слово из другого языка там, где есть точный аналог языка документа, без пояснения |
| 7 | Design/Run-time смешение | «Alt-B рассмотрен и снят», «Q3: заложить» — в публичном тексте |
| 8 | Панибратский/канцелярит | «все мы ребята», «в рамках осуществления», «важно отметить» |
| 9 | Self-justifying loop | «X работает, потому что X» без внешнего evidence |
| 10 | Ссылка на несуществующее | Ссылки на файлы/разделы/роли, которых нет |
| 11 | Скачки логики | Вывод без промежуточной посылки |
| 12 | Дублирование вывода | Одно правило в двух секциях разными словами |

**Процедура проверки:**

1. Прочитать файл целиком с мыслью «что из этого мог вставить AI по инерции»
2. Для каждого подозрительного места — сопоставить с паттерном из таблицы выше
3. Применить **тест принадлежности**:
   - Паттерн 1: «если удалить эту фразу, читатель поймёт меньше?». Если нет → negation of nothing
   - Паттерн 2: «это полезно читателю или автору/ревьюверу?». Если второе → AI-метка
   - Паттерн 3: «где читатель возьмёт значение для этого плейсхолдера?». Если неизвестно → проблема
   - Паттерн 4: «этот субъект реально делает это действие?». Проверять через владельца процесса или существующие документы
   - Паттерн 5: «как эта цифра считалась?». Если неизвестно → имитация
   - Паттерн 7: «читателю публичного документа нужна эта информация для его работы?». Если нет → design-time
   - Паттерн 10: использовать Glob/Grep/Read для верификации ссылок
4. При подозрении — проверить ПОЛНЫЙ каталог реальных примеров в `references/examples.md`

**Формат находки:**

```
ТИП: СИНТЕТИЧЕСКИЙ ПАТТЕРН
Серьёзность: критическая | рекомендация (по таблице в synthetic-patterns.md)
Файл: [путь]:[строка]
Паттерн: #N — [название]
Утверждение: «цитата»
Диагноз: [почему это попадает под паттерн, со ссылкой на FPF-основу]
Рекомендация: [направление исправления, примеры в examples.md]
```

**Пример:**

```
ТИП: СИНТЕТИЧЕСКИЙ ПАТТЕРН
Серьёзность: критическая
Файл: docs/release-guide.md:110
Паттерн: #1 — Negation of nothing
Утверждение: «Назначение релиз-менеджера — решение команды, не
  автоматическая процедура. Без триггеров по дням.»
Диагноз: В разделе про назначение релиз-менеджера никаких «дневных
  триггеров» не обсуждалось. Leaked invariant из другого bounded context
  (было в §SLA ответа, удалено в прошлой версии, residual остался).
  FPF A.1.1: «Local rules leak globally».
Рекомендация: Удалить фразу «Без триггеров по дням». См. examples.md
  раздел «Сопровождение релизов».
```

**Серьёзность по таблице паттернов:**

| Уровень | Паттерны |
|---------|----------|
| Критическая (блокирует публикацию) | 1, 3, 4, 5, 7, 9, 10, 12 |
| Рекомендация (улучшение качества) | 2, 6, 8, 11 |
