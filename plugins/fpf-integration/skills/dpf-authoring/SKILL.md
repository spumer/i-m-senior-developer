# DPF-Authoring — авторинг сводов принципов (DPF) по FPF

Скилл самодостаточен: метод, шаблоны и конвейер лежат внутри (пути в этом файле — относительно каталога скилла). Для работы не нужен никакой конкретный проект и никакие конкретные пути машины — DPF пишутся в тот проект, который явно указан в `args.repoRoot`; каталог самого скилла передаётся конвейеру явным `args.skillDir`.

**Состав скилла:**

- `references/method.md` — **канон метода** (6 фаз, гейты, канонический скелет, паттерны, типовые ошибки). Прочитать перед любым режимом ниже.
- `assets/dpf-authoring.workflow.js` — конвейер `dpf-authoring-pipeline` (6 фаз, файловый handoff).
- `assets/template-dpf.md` — скелет нового DPF; `assets/template-source-pack.md` — образец provenance-реестра.
- `frameworks/DPF-ADVERSARIAL-REVIEW/`, `frameworks/DPF-KNOWLEDGE-CURATION/` — **встроенные пакеты ролей** конвейера (формат dpf-apply: `DPF.md` + `assets/apply-prompt.md`).

**Привязка к редакции:** FPF `ailev/FPF@f7c7e93f` (E.4.DPF spine, CC-DPF.1–9, E.4.DPF.DA) — см. `fpf_edition` во frontmatter `references/method.md`. Агенты фаз читают FPF по приоритету источника: **сначала FPF-справочник через MCP** (`fpf_reference`: `search_fpf` / `read_fpf_doc` / `query_fpf_spec`), если он подключён — точные ID и цитаты; **иначе локальная копия** `~/.claude/knowledge/fpf/FPF-Spec.md`. Метод запинен на редакцию выше — если MCP отдаёт другую (`get_fpf_index_status`), агент фазы обязан явно отметить расхождение в `references/`, а не работать молча по чужой редакции (edition-пин E.4.DPF.DA). **Нет ни MCP, ни локальной копии — фаза не авторит по памяти, а падает громко** (FAIL-FAST, A.10): нужен хотя бы один источник FPF. Свежесть локальной копии — зона скилла `fpf-integration`, не этого; переход на текущую редакцию спеки — отдельная задача.

## Роли фаз — встроенные пакеты компетенций

Конвейер НЕ зависит от ролей какого-либо проекта. Роли фаз — пакеты компетенций, **встроенные в скилл** (`frameworks/<ID>/`) в формате dpf-apply: `DPF.md` (паттерны, контрпримеры, типовые ошибки — рабочий справочник роли) + `assets/apply-prompt.md` (процедура: чек-листы, порядок проверок, критерии отказа). Агент фазы читает оба файла и исполняет процедуру буквально — это и есть роль, а не однострочная этикетка.

| Фазы | Пакет | Функция |
|------|-------|---------|
| Bridge, Critic | `frameworks/DPF-ADVERSARIAL-REVIEW` | диалектика тезис/анти-тезис, devil's advocate, оценка пакета по E.4.DPF.DA |
| Source-pack, Assemble | `frameworks/DPF-KNOWLEDGE-CURATION` | провенанс G.2, сборка носителя по канон-скелету, дисциплина формата |

Пакет не читается → фаза падает громко (fail-fast), а не работает «как получится». Пакеты также резолвятся скиллом `dpf-apply` (общий формат) — для использования этих ролей вне конвейера.

## Запуск конвейера

Обязательные внешние параметры — два: `repoRoot` (абсолютный путь ТЕКУЩЕГО проекта; каталоги DPF пишутся в `<repoRoot>/project/frameworks/`, переопределяется `frameworksDir`) и `skillDir` (абсолютный путь каталога этого скилла — тот же, что в `scriptPath`; из него конвейер читает метод, шаблоны и пакеты ролей). Тихих дефолтов нет — без любого из них конвейер падает сразу.

```
Workflow({
  scriptPath: '<каталог этого скилла>/assets/dpf-authoring.workflow.js',  // абс. путь каталога, из которого прочитан этот SKILL.md (при установке из плагина — plugins/fpf-integration/skills/dpf-authoring)
  args: {
    date: '<сегодня>',                 // в workflow-скриптах нет Date.now
    repoRoot: '<абс. путь текущего проекта>',   // ОБЯЗАТЕЛЕН
    skillDir: '<каталог этого скилла>',         // ОБЯЗАТЕЛЕН — тот же каталог, что в scriptPath
    competencies: [{ id: 'DPF-…', name: '…',
                     kind: 'Domain Principle Framework' | 'Local Practice Framework',
                     owner: '<роль/владелец>', status: 'active',
                     bounded_context: '1-2 фразы: что покрывает и чем НЕ является' }],
    frameworksDir: '<абс. путь>',      // опц.: куда писать вместо <repoRoot>/project/frameworks
    exemplar: '<абс. путь DPF.md>',    // опц.: лучший DPF целевого проекта как эталон формата
    only: ['DPF-…'], exclude: ['DPF-…'], // опц. фильтры переданного списка
  },
})
```

(В проекте, где есть ссылка в `.claude/workflows/`, работает и `Workflow({ name: 'dpf-authoring-pipeline', args: {...} })` — `skillDir` обязателен и там.)

Если в целевом проекте есть `project/domain.md` и `project/decisions/` — агенты используют их как локальный контекст; их отсутствие прогон не ломает, но обедняет инстанциации.

## Режимы работы

### A. Полный авторинг (новый DPF или доавторинг заготовки)

1. Собрать список компетенций (id, name, kind, owner, bounded_context — заполнить содержательно: питает фазу scope). Источник — карта компетенций целевого проекта или явное поручение человека.
2. **Подтвердить состав у человека ДО запуска** — прогон дорогой (~0.5M токенов на компетенцию); правило появилось после случая, когда запустили 5 вместо строго нужных 3.
3. Запустить конвейер (SoTA → Bridge → Source-pack → Assemble → Critic; все артефакты — только через файлы).
4. Сразу сверить первую строку лога `DPF-authoring: N компетенций` — N обязан совпасть с переданным списком.
5. После прогона: проверить диск (`ls` каталогов, не доверять отчётам агентов), вердикты критика (`gate_passed`, статус пакета), обновить карту компетенций целевого проекта, замечания критиков — в бэклог.

### B. Переоценка пакета без пересборки (E.4.DPF.DA)

Когда содержание не менялось, а планка изменилась (новая редакция FPF, плановая дата пересмотра): прогнать только фазу критика — роль из `DPF-ADVERSARIAL-REVIEW` (Opus) делает подпроход PFM1–PFM11 + таблицу координат D1–D11 + статус пакета + строку `> maturity-critic:` (метод §Фаза 6), пишет `references/package-adequacy-<дата>.md` в каталоге целевого DPF; историю прошлых ревью не трогает.

Финальный детерминированный шаг (после критик-фазы, до отчёта человеку): запустить `assets/maturity.py <каталог целевого DPF> [--json] [--write-profile]` — читает свежий `package-adequacy-<дата>.md` (D-таблицу + строку `maturity-critic`) и канон-скелет `DPF.md` (read-only), печатает уровень, компонентный чек-лист, список «доработать next» и предлагаемую правку карты (`maturity_level: <old?>→<new>`). `--write-profile` переписывает раздел `## Профиль зрелости` в том же package-adequacy (идемпотентно, историю прошлых dated-файлов не трогает). Скрипт сам в `competency-map.md` не пишет — правку карты по напечатанной строке применяет мейнтейнер.

### C. Ремонт по repair-спискам

После вердикта `repairBeforeDPFUse`: цепочка «ремонт (Sonnet, роль из `DPF-KNOWLEDGE-CURATION`) → повторная проверка (Opus, роль из `DPF-ADVERSARIAL-REVIEW`)», максимум 2 круга. Правила ремонта: процессные следы из `DPF.md` **переносить** в `references/quality-record-<дата>.md`, не удалять (no information loss); тела паттернов и source-pack не переписывать; статус «пригоден» дописывает только критик по факту.

### D. Точечная правка готового (conformant) DPF

Опечатка, ссылка, новый факт в одну строку — конвейер НЕ гонять (контрпример Паттерна 1 метода). Обычная Code-Change Discipline: точечная правка + при содержательном изменении отметка в `references/`.

## Инварианты (нарушение = повторение прожитых инцидентов)

- **Fail-fast вход:** `repoRoot`, `skillDir` и `competencies` — только явные; пусто → ошибка. Массового «прочитать всю карту» и тихих дефолтов записи нет намеренно (инцидент 2026-07-04: фолбэк прогнал 29 вместо 5).
- **Роли — только из пакетов:** фаза без доступного пакета компетенции не исполняется «на общих знаниях» — падает с эскалацией.
- **Research-first гейт:** `DPF.md` не пишется, пока нет `sota-research.md` + `theses-antitheses.md`.
- **Файловый handoff:** агенты фаз возвращают только короткий статус; контент — в файлах.
- **Модели по фазам:** Sonnet — ресёрч/сборка/провенанс; **Opus** — Bridge и Critic (диалектика/адверсарность). Модель задаётся явно, не наследуется от роли.
- **Честный статус пакета:** stub/stage-0 = seedOnly; «пригоден» (`admissibleForDeclaredDPFUse`, пол 4) — только вердиктом критика.

## Происхождение метода

Авторская комната (исследование, provenance, записи качества; для прогонов не нужна) — каталог `DPF-AUTHORING/` библиотеки сводов в репозитории `aifirst` владельца метода. Правки метода — в `references/method.md` скилла, затем зеркалятся в комнату.
