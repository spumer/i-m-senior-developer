# Тезисы-антитезисы — DPF-KNOWLEDGE-CURATION (Фаза 2)

> **Компетенция:** кураторская функция в авторинге сводов знаний (DPF/LPF) — провенанс источников
> (G.2), сборка пользовательского носителя по канон-скелету E.4.DPF, дисциплина формата (сжатие без
> потери смысла при переносах), зеркалирование канона, ведение карт компетенций. Owner — keeper.
> Critic (эта фаза) — guardian. **НЕ содержание паттернов** (это owner домена), **НЕ адверсарная
> критика** (это guardian на Фазе 6), **НЕ генерация ресёрча** — предмет здесь: дисциплина курирования
> самих сводов **как артефактов**.
>
> **Цель (E.4.DPF:3):** не синтез — **плюрализм**. Выявить конфликты и scope-зависимости между четырьмя
> традициями SoTA и ИИ-срезом. Никакого молчаливого слияния (no silent fusion): каждый тензион назван
> явно, с потерями при слиянии и типом связи (E.4.PFR).
>
> **Традиции (из `sota-research.md`):**
> T1 = Digital Curation / архивно-библиотечная наука (OAIS PDI/Provenance Information + DCC Curation
> Lifecycle) ·
> T2 = Structured / Topic-Based Technical Authoring (DITA topic, reuse-by-reference, Information
> Mapping/Chunking, минимализм) ·
> T3 = Editorial / Publishing Compression (copyediting «cut to fit» + формальный abstract ANSI/NISO
> Z39.14, «faithful compression») ·
> T4 = Governance разделяемых эталонных данных (MDM Golden Record + Taxonomy Governance/steward) ·
> AI = ИИ-срез (faithful prompt compression LLMLingua, hallucination benchmarks FaithBench, RAG
> attribution verification VeriCite/TREC, documentation drift docs-as-code).
>
> **Наш bounded context (не ограничивает SoTA, но фильтрует применимость):** keeper курирует библиотеку
> `project/frameworks/DPF-*` (33 компетенции) **вручную**, в **markdown**, БЕЗ формальных архивных
> систем/RDF/DITA-тулинга/MDM-платформы; один куратор + зеркалирование канона метода между
> `~/.claude/skills/dpf-authoring/` и комнатой `DPF-AUTHORING/`. Каждая традиция даёт **принцип**;
> **аппарат** (полная OAIS-механика, XML-DITA, MDM survivorship-движок) — избыточен и берётся только как

>
> **Важно (E.4.DPF:8, «Source summary as SoTA»):** несущие claim'ы этой компетенции — из смежных, но
> НЕ тождественных масштабов (архивы/датасеты, industrial prompt-компрессия, docs-as-code для кода).
> Перенос на «keeper курирует markdown-DPF вручную» — **hypothesis**, не проверенный факт (research-gap

### T1 × T2 — Digital Curation vs Structured Authoring

| Поле | Содержание |
|------|-----------|
| **Alignment** | Обе фиксируют, что связь между единицами должна быть **явной**: T1 — «links between outputs» (context-mapping, T1.5); T2 — conref/keyref (T2.2). Обе против незаметного расхождения копий |
| **Divergence** | T1 смотрит **назад по времени** (provenance — история происхождения и трансформаций, T1.1); T2 смотрит **вширь по носителям** (один topic → много изданий, T2.2). T1 про сохранность смысла ПОСЛЕ смены контекста; T2 про переиспользование В текущем контексте |

| Поле | Содержание |
|------|-----------|
| **Alignment** | Обе требуют, чтобы вторичный носитель **не терял** смыслонесущего содержания оригинала: T1 — provenance переживает миграцию формата; T3 — abstract = «accurate representation» (T3.3) |
| **Divergence** | T1 — **накопление** (история растёт, ничего не стирается, T1.1); T3 — **сокращение** (текст ужимается, T3.2). Прямое противонаправление: провенанс копит, компрессия режет |

| Поле | Содержание |
|------|-----------|
| **Alignment** | Обе вводят **постоянную роль-хранителя**: T1 — curation lifecycle с community watch/participation (full-lifecycle actions, T1.3); T4 — steward/governance team (T4.4). Обе: курирование не разовое |
| **Divergence** | T1 — про **один объект во времени** (его provenance и трансформации); T4 — про **согласованность многих потребителей** (SSoT как организационный исход, T4.2). T1 внутриобъектная история, T4 межпотребительская согласованность |

| **Scope строки** | T1 доминирует внутри одного DPF-каталога; T4 доминирует на уровне библиотеки (competency-map, зеркала канона) |

### T2 × T3 — Structured Authoring vs Editorial Compression

| Поле | Содержание |
|------|-----------|
| **Alignment** | Обе — про **экономию внимания читателя**: T2 chunking (блок под объём памяти, T2.4) + минимализм (не выдавать лишнего, T2.5); T3 «omit needless words» (T3.1). Прямая параллель PFM2 (паттерны — главный язык, тяжёлые карты вторичны) |
| **Divergence** | T2 режет по **структуре** (типизированные единицы, границы topic); T3 режет по **тексту** (замена слабых конструкций, объём). T2 — архитектура носителя, T3 — плотность формулировки |

### T2 × T4 — Structured Authoring vs Reference-Data Governance

| Поле | Содержание |
|------|-----------|
| **Alignment** | Обе против **молчаливого расхождения копий**: T2 reuse-by-reference (правка одного topic долетает всюду, T2.2); T4 golden record из примирения источников (T4.1). Оба — «одно определение, много потребителей» |
| **Divergence** | T2 — механизм (**ссылка вместо копии**); T4 — процесс (**survivorship-правила + steward**, T4.3). T2 технический single-sourcing, T4 организационное согласование |
| **Losses при слиянии** | «Есть reuse-by-reference → governance не нужен» теряет: ссылочный механизм (T2) не решает, ЧЬЯ версия каноническая при конфликте (это T4 survivorship); наш случай — канон в двух местах (скилл+комната) БЕЗ ссылочного механизма, только ручной синк, значит нужен явный steward (T4), а не только дисциплина автора. | **Scope строки** | T2 применим где перенос технически ссылочный (внутри markdown); T4 применим где источников несколько и нужна политика (канон↔зеркало) |
| **Тип связи** | **scope-dependent**: reuse-by-reference (T2) работает при наличии ссылочного механизма; без него governance (T4) обязателен |

### Тезис T-01 — «Провенанс накапливается, не переписывается: adopted/rejected с причинами и retired-премиссы не стираются задним числом»

**Scope валидности (A.2.6 USM):**
- Тип носителя: реестр провенанса (`source-pack.md`, `quality-record-*.md`) — артефакт, переживающий смену контекста/ремонт
- Масштаб команды: любой
- Автоматизация: любая (принцип не зависит от инструмента)
- Не применим: пользовательский носитель (DPF.md/llms.txt), где действует ОБРАТНЫЙ режим — сжатие (T-05); не применим к verbatim-логу, который и так append-only

**Антитезисы (NQD ≥3):**
1. **Накопление без ротации раздувает реестр** — при 33 DPF × многих ремонтах source-pack становится нечитаемым; нужна не потеря истории, а вынос устаревшего в отдельный слой (quality-record), не стирание. Evidence: T1.3 (occasional actions: dispose/reappraise — управляемое, не произвольное), ME-1.
2. **Не вся история равноценна** — retired-премисса (R1) полезна как «мы это отвергли и почему»; но телеметрия каждого прогона в реестре провенанса — шум (это T4 governance-запись, не provenance-объекта). Граница: копим РЕШЕНИЯ об источниках, не операционный лог. Evidence: T1.1 vs T1.4, PFM7.
3. **Провенанс постфактум дешевле кажется, но дороже выходит** — соблазн «допишу историю потом» ломает T1.4 (метаданные в момент создания, не позже); наш аналог — research-first гейт (пиши source-pack в момент решения). Antithesis тут не «не копить», а «копить СВОЕВРЕМЕННО, иначе реконструкция дороже». Evidence: T1.4 (hypothesis-статус переноса помечен).

**Тип связи:** composition с T-08 (провенанс — вход для steward-governance); conflict-по-направлению с T-05 (накопление vs сжатие, разрешается scope-разметкой артефакта).

### Тезис T-02 — «Курирование — жизненный цикл с типами действий (постоянные / последовательные / эпизодические), а не разовое создание носителя»

**Scope валидности:**
- Тип носителя: библиотека DPF-каталогов + карты компетенций (`competency-map.md`)
- Масштаб команды: где носитель живёт дольше одного прогона (все наши DPF имеют review_due)
- Автоматизация: любая
- Не применим: одноразовая заметка без review_due; не применим как оправдание бесконечного «дозревания» без гейта

**Антитезисы (NQD ≥3):**
1. **Полная OAIS-механика избыточна** — 3 типа информационных пакетов + 6 функциональных сущностей (T1.2) не переносятся на ручной markdown-каталог; берём принцип «жизненный цикл ≠ разовость», не аппарат. Evidence: T1.2/T1.3, bounded-region ClaimSheet T1.
2. **Lifecycle без триггеров = ритуал** — «review_due раз в 3 мес» без механической проверки = decision debt (аналог DPF-ADR-DRR: правило без проверки — мнение). Антитезис: типы действий полезны только если привязаны к триггерам (изменение FPF-Spec, 3+ DPF с отклонением), а не к календарю. Evidence: T1.3 (occasional actions условны), метод §8 refresh-триггеры.
3. **Для solo-куратора «community watch/participation» вырождено** — full-lifecycle actions T1.3 предполагают сообщество; у одного keeper это самонаблюдение (риск «согласия с собой», ошибка №7 метода). Evidence: T1.3, bias-note sota-research AI.4.

**Тип связи:** composition с T-08 (lifecycle-действия исполняет steward); scope-dependent (набор действий зависит от масштаба библиотеки).

### Тезис T-03 — «Носитель собирается из типизированных самодостаточных единиц; паттерны — главный язык (PFM2), chunking под объём внимания (PFM1)»

**Scope валидности:**
- Тип носителя: пользовательский DPF.md по канон-скелету E.4.DPF
- Масштаб команды: любой
- Автоматизация: любая
- Не применим: реестр провенанса (там порядок = хронология источников, не topic-модульность); не применим к verbatim-цитате как evidence

**Антитезисы (NQD ≥3):**
1. **XML-DITA-тулинг избыточен** — conref/keyref/специализация (T2.2/T2.3) требуют инфраструктуры, которой нет; берём принцип reuse-by-reference и chunking, не формат. Наш reuse — markdown-ссылка + ручной синк. Evidence: T2.2/T2.3, bounded-region ClaimSheet T2.
2. **Chunking-размер субъективен** — «под объём внимания читателя» (T2.4) не даёт числа; для ИИ-читателя и человека объём разный. Антитезис: границу секции задаёт ЕДИНОЕ намерение единицы (T2.1), не длина. Evidence: T2.1/T2.4.
3. **«Паттерны первым» конфликтует с провенанс-первичностью на входе** — PFM1 (паттерны-как-главный-язык) — про пользовательский носитель; на этапе research порядок обратный (источники→claim→bridge→паттерн). Front по declared dominance: для DPF.md доминирует PFM2, для research-артефактов — хронология источников. Evidence: T2.5 (параллель PFM2, помечена hypothesis), скелет метода §5.

**Тип связи:** composition с T-05 (модульность + плотность формулировки); specialization от общего T2 к нашему markdown-случаю.

### Тезис T-04 — «Reuse-by-reference, а не копипаст: одно определение подключается ссылкой; копия расходится молча»

**Scope валидности:**
- Тип носителя: переносимые единицы между носителями (канон метода skill↔room; определение термина glossary↔DPF)
- Масштаб команды: любой, где есть ≥2 носителя с общим содержанием
- Автоматизация: критично — при ссылочном механизме держится сам; при ручном синке требует steward (T-08)
- Не применим: единичный носитель без копий; не применим к намеренно расходящимся редакциям (edition fork)

**Антитезисы (NQD ≥3):**
1. **Канон метода НЕ кодогенерируем** — docs-as-code решает drift генерацией из одной спеки (T2.2/AI.6 S28 park); наш канон (skill↔room) — прозаический markdown, ссылочный reuse технически недоступен, остаётся ручной синк. Антитезис: reuse-by-reference — идеал, у нас реализуется как явный steward-процесс, не механизм. Evidence: AI.6, S28 (park, «наш случай не кодогенерируем»).
2. **Дублирование иногда осознанно** — self-contained abstract (T3.4) требует, чтобы носитель был понятен БЕЗ оригинала, т.е. некоторое повторение контекста в носителе легитимно (не всякая копия = дефект). Граница: копия БЕЗ явной связи и синка = дефект; намеренный self-contained дубль с пометкой = ок. Evidence: T3.4, T2.2 (конфликт reuse vs self-containment).
3. **Ссылка тоже дрейфует** — reuse-by-reference защищает от расхождения ТЕКСТА, но ссылка может указывать на устаревшую редакцию (edition drift); нужна ещё edition-дисциплина (E.4.PFR), не только ссылка. Evidence: T2.2, E.4.PFR:3 «evolution».

**Тип связи:** scope-dependent (механизм reuse доступен → держится сам; недоступен → governance T-08 обязателен); conflict-частичный с T3.4 (reuse vs self-containment).

### Тезис T-05 — «Сжатие при переносе — faithful: точность (accuracy) обязательна, не косметика; no information loss смыслонесущего»

**Scope валидности:**
- Тип носителя: перенос из длинного/первичного в короткий/вторичный (research→theses→DPF.md; DPF.md→llms.txt)
- Масштаб команды: любой
- Автоматизация: критично — ИИ-компрессор рискует инверсией смысла (AI×T3); человек-редактор знает несущее заранее
- Не применим: реестр провенанса (накопление, T-01); verbatim-лог; там, где сокращение не требуется

**Антитезисы (NQD ≥3):**
1. **«Omit needless words» — стилистика, не измеримый критерий** — T3.1 (fact/opinion) даёт направление, но граница «нужное/лишнее» субъективна; формальный критерий даёт только ANSI Z39.14 (T3.3: назначение/метод/результат/вывод присутствуют). Антитезис: faithful ≠ «покороче на глаз», а «проверяемо сохранены несущие элементы». Evidence: T3.1 vs T3.3.
2. **Faithfulness — ОТДЕЛЬНАЯ цель, не побочный эффект компактности** — LLMLingua-1 (perplexity-pruning) потребовал -2 (faithfulness-обучение) именно потому, что «сжато и правдоподобно» ≠ «сжато и верно» (AI.2, ME-5, R1 retired). Антитезис усиливает тезис: без явной faithfulness-цели сжатие теряет смысл. Evidence: AI.1/AI.2, ME-5.
3. **ИИ-самопроверка сжатия ненадёжна** — FaithBench: SOTA-детекторы ~50% на сложных случаях (AI.4); значит faithful-сжатие ИИ-агентом требует ВНЕШНЕГО критерия (guardian-критик Фазы 6, отдельный от автора). Антитезис: «faithful» нельзя делегировать тому же агенту, что сжимал. Evidence: AI.4.

**Тип связи:** conflict-по-направлению с T-01 (сжатие vs накопление, scope-разметка артефакта); composition с T-03 (плотность × модульность); specialization AI-случая (T-09).

### Тезис T-06 — «Пользовательский носитель самодостаточен: structure-account (CC-DPF.8) понятен сам по себе, без обращения к процессным артефактам»

**Scope валидности:**
- Тип носителя: DPF.md — пользовательский носитель
- Масштаб команды: любой
- Автоматизация: любая
- Не применим: research/quality-record (там процессное состояние ЖИВЁТ, PFM7); не применим к разделу, который по замыслу — указатель к деталям («как именно» → возврат к источникам)

**Антитезисы (NQD ≥3):**
1. **Self-contained только для «что», не для «как»** — formal abstract самодостаточен для «что сделано/найдено», но «как именно» требует перехода к тексту (T3.4). Антитезис: носитель не обязан вмещать ВСЁ; граница — понятность НАЗНАЧЕНИЯ и границ без оригинала, детали — по возврату. Evidence: T3.4, скелет §0 (structure-account: куда возврат за деталями).
2. **Полная самодостаточность конфликтует с parsimony** — вместить весь контекст в носитель = раздуть его (нарушить T3/PFM2); FPF читается живьём, не выжимками (метод: не храним выжимки FPF). Антитезис: самодостаточность = понятность интерфейса носителя, не инкапсуляция всех источников. Evidence: A.11, метод Carrier note.
3. **Процессное состояние всё же иногда нужно в носителе** — одна финальная conformance-строка со статусом пакета допустима в DPF.md (PFM7 исключение). Граница тонкая: durable-attestation — да, run-attribution/critic-verdict — нет. Evidence: PFM7, метод §5 (одна conformance-строка).

**Тип связи:** composition с T-05 (самодостаточность требует faithful-сжатия); conflict-частичный с A.11 (самодостаточность vs компактность).

### Тезис T-07 — «Канон = организационный ИСХОД (SSoT): истинность от того, что все потребители реально им пользуются, а не от того, что файл назван „канон“»

**Scope валидности:**
- Тип носителя: канон метода + библиотека DPF (потребители — роли проекта, скилл, воркфлоу)
- Масштаб команды: где ≥2 независимых потребителя одного канона
- Автоматизация: любая
- Не применим: единичный файл с одним читателем-автором (T4 «избыточно для единичного файла»)

**Антитезисы (NQD ≥3):**
1. **SSoT-переопределение — vendor-фрейминг** — T4.2 (fact/hypothesis) логически устойчив, но это MDM-маркетинг; для нашего масштаба «все потребители» = роли + 2 канала доступа, малое число. Антитезис: принцип верен, но не требует MDM-платформы; проверяется вручную (кто на что ссылается). Evidence: T4.1/T4.2 (trust-cue helped).
2. **Два места канона (skill↔room) структурно нарушают SSoT** — «слишком много мест, похожих на источник истины» (AI.6); даже при дисциплине зеркала расходятся без автодетекта. Антитезис: назвать ОДНО место каноном (skill — «архитектура метода»), room — зеркало; не два равноправных. Evidence: AI.6, метод (правки только в файле метода, зеркалятся в комнату).
3. **Golden record из примирения НЕСКОЛЬКИХ источников (T4.1) неприменим к канону-с-одним-автором** — у нас нет N систем-источников для примирения; канон авторский. Антитезис: T4.1 (примирение) — про данные из многих систем; наш случай — T4.2 (согласованность потребления), не T4.1. Разделить два смысла «single source». Evidence: T4.1 vs T4.2 (A.7 distinction).

**Тип связи:** composition с T-08 (SSoT поддерживается steward-ролью); scope-dependent (применим при ≥2 потребителях).

### Тезис T-08 — «Курирование требует постоянной роли-хранителя (steward/keeper), а не разового автора; без owner словарь/канон дрейфует несмотря на исходное качество»

**Scope валидности:**
- Тип носителя: библиотека DPF + glossary + канон
- Масштаб команды: любой, где носитель живёт дольше одного акта создания
- Автоматизация: любая
- Не применим: разовый артефакт без review_due; не применим как оправдание bus-factor=1 без делегирования

**Антитезисы (NQD ≥3):**
1. **Steward для solo-проекта = один keeper = bus-factor 1** — taxonomy governance (T4.4) предполагает team charter (scope+роли); у нас роль есть, команды нет. Антитезис: постоянство роли важнее численности, НО при одном кураторе нужна страховка (канон самодостаточен, чтобы пережить смену куратора). Evidence: T4.4, T3.4 (self-contained как bus-factor-страховка).
2. **Owner-роль ≠ автоматическая согласованность** — steward существует, но governance без editorial guidelines (T4.4) = субъективные правки; нужны явные правила (канон-скелет, гейты), не только назначенный человек. Антитезис: роль + правила, не роль вместо правил. Evidence: T4.4, метод (CC-DPF.1–9 как guidelines).
3. **Разделение owner компетенции vs owner формата** — keeper курирует ФОРМАТ/провенанс (эта компетенция), но НЕ содержание паттернов (owner домена). Смешение = keeper начинает решать за owner домена (выход за scope). Антитезис: steward-роль ограничена артефактной дисциплиной, не доменным содержанием. Evidence: scope.md non-use boundary, A.7.

**Тип связи:** composition с T-01/T-02/T-07 (steward исполняет провенанс, lifecycle, SSoT); governing-pattern (T-08 управляет применением остальных).

### Тезис T-09 (ИИ-специфично) — «Для ИИ-агента курирование текста — измеримый риск, не редакторское удобство: сжатие/атрибуция ненадёжно самопроверяемы, нужен внешний критерий»

**Scope валидности:**
- Тип носителя: любой, где перенос/сжатие/атрибуцию выполняет ИИ-агент (все наши фазы под мультиагентным прогоном)
- Масштаб команды: критично при мультиагентности (owner ≠ guardian ≠ keeper, DEC-003)
- Автоматизация: специфичен именно для ИИ-исполнения
- Не применим: чисто человеческий перенос под ревью человека; не применим как отказ от ИИ вообще (Lemonade: ИИ ускоряет, риск митигируется разделением ролей)

**Антитезисы (NQD ≥3):**
1. **Перенос из смежных масштабов — hypothesis, не факт для нашего случая** — AI.1–AI.6 из prompt-инженерии / industrial RAG / docs-as-code; изолированного исследования эффекта гейта на markdown-курирование малой командой НЕТ (research-gap). Антитезис: риск реален по аналогии, но не измерен для нас; не повышать до fact (A.10). Evidence: sota-research Research-gap.
2. **Внешний критерий = ещё один ИИ-агент, тоже ненадёжный** — guardian-критик тоже ИИ; FaithBench: LLM-судьи ~50% на сложном (AI.4). Антитезис: разделение ролей снижает self-consensus, но не даёт гарантии; нужен human-anchor на пороговых случаях (Founder-приёмка). Evidence: AI.4, DEC-006 (правило двух людей).
3. **Attribution verification (VeriCite/TREC) — про RAG-цитаты, не про markdown source-pack** — AI.5 операционализирует провенанс для генеративного ответа; наш source-pack пишется человеко-агентом с URL+датой. Антитезис: принцип «ссылка ≠ верная атрибуция» переносится, но механизм verification — из другого масштаба; у нас verification = ручная сверка Grep по FPF-Spec (Carrier note). Evidence: AI.5, метод Carrier note.

**Тип связи:** specialization (ИИ-случай T-05/T-01); governing-pattern для ошибок ОШ-10..12; conflict с «AI-consensus = evidence».

## Раздел 3 — Контрпримеры (A.11 Sharp Boundary)

> Ситуации, внешне похожие на кейс применения тезиса/паттерна, где применять вывод **НЕЛЬЗЯ**. Это НЕ
> анти-паттерны исполнения (те — Раздел 4), а **граница scope** (A.11:2 Sharp boundary — one-sentence
> inclusion/exclusion test). Отдельно от анти-паттернов метода.

---

### КП-01 — «Выглядит как нужна полная OAIS-механика, но у нас один markdown-каталог вручную»

**Похоже:** курируем сохраняемые артефакты, значит нужны Submission/Archival/Dissemination пакеты + 6 функциональных сущностей (T1.2).
**Нельзя применять аппарат OAIS 1:1:** полная механика — для институциональных архивов, переживающих смену организации; у нас ручной markdown, маленькая команда. Берём ПРИНЦИП (provenance накапливается, курирование = lifecycle), не аппарат.
**Правильно:** source-pack + quality-record как лёгкий provenance-слой; никаких формальных информационных пакетов/RDF.
**Evidence:** T1.2 bounded-region, ClaimSheet T1 validity-region.

---

### КП-02 — «Выглядит как reuse-by-reference применим к канону, но канон прозаический и не кодогенерируем»

**Похоже:** канон в двух местах (skill↔room) — применим single-sourcing DITA (T2.2), правим один, долетает всюду.
**Нельзя применять ссылочный reuse к прозаическому канону:** conref/keyref работают в XML-DITA или при кодогенерации из спеки (docs-as-code, S28 park); наш канон — markdown-проза, ссылочная подстановка технически недоступна. Остаётся ручной синк под steward (T-08).
**Правильно:** назвать ОДНО место каноном, второе — зеркалом; синхронизировать явным процессом, не полагаться на несуществующий механизм reuse.
**Evidence:** T2.2, S28 (park), AI.6.

---

### КП-03 — «Выглядит как сжали и звучит связно, значит сохранили смысл»

**Похоже:** ИИ-агент ужал research→DPF.md, текст гладкий и по-FPF-шному.
**Нельзя приравнивать fluency к faithfulness:** perplexity-based/наивное сжатие выбрасывает статистически «скучные», но смыслонесущие токены — отрицание, «bounded», «hypothesis не fact» (ME-5, AI.1); гладкость ≠ верность. Самопроверка ИИ ~50% на сложном (AI.4).
**Правильно:** faithful — отдельная проверяемая цель (сохранены ли несущие элементы, границы scope, статусы claim); внешний критик Фазы 6, не тот же агент.
**Evidence:** ME-5, AI.1/AI.2/AI.4, R1 retired.

---

### КП-04 — «Выглядит как файл называется „канон“, значит это SSoT»

**Похоже:** есть `method.md` с пометкой «канон метода» — источник истины найден.
**Нельзя выводить SSoT из имени файла:** SSoT — организационный исход (все потребители реально им пользуются, T4.2), не свойство файла. Если роли/скилл/воркфлоу опираются на параллельные копии — канона-как-SSoT нет, несмотря на заголовок.
**Правильно:** проверить, кто на что реально ссылается (потребление), назвать ОДНО место каноном, остальные — зеркалами с явным синком.
**Evidence:** T4.2, AI.6, T-07.

---

### КП-05 — «Выглядит как секции CC-DPF.1–9 присутствуют, значит носитель готов»

**Похоже:** DPF.md прошёл по канон-скелету, все заголовки на месте.
**Нельзя приравнивать присутствие структуры к faithful наполнению:** скелет с заголовками и очень короткими паттерн-секциями = seedOnly, читатель не может применить паттерн без реконструкции (skeleton carrier, E.4.DPF:8). Наличие структуры ≠ несущее содержание.
**Правильно:** оценивать пакет по E.4.DPF.DA поверх чек-листа секций (это Фаза 6, guardian); куратор готовит носитель к этой оценке, не подменяет её присутствием секций.
**Evidence:** E.4.DPF:8 «Skeleton carrier as DPF», метод типовая ошибка №3.

---

### КП-06 — «Выглядит как taxonomy governance = формальный team charter, но у нас один keeper»

**Похоже:** нужна governance-команда со scope+ролями (T4.4) для 33 DPF.
**Нельзя требовать team charter там, где команда = один куратор:** steward-РОЛЬ обязательна (без owner словарь дрейфует), но численность команды — переменная масштаба; team charter для одного человека вырождается в самонаблюдение (риск «согласия с собой», ошибка №7).
**Правильно:** удержать постоянство роли + явные правила (канон-скелет, гейты) + страховку самодостаточным каноном (bus-factor); не имитировать корпоративный charter.
**Evidence:** T4.4, T-08 антитезис 1, метод ошибка №7.

---

### КП-07 (ИИ-специфично) — «Выглядит как ссылка/цитата присутствует, значит атрибуция верна»

**Похоже:** claim в source-pack несёт URL — провенанс есть.
**Нельзя выводить верность атрибуции из наличия ссылки:** синтаксическая ссылка ≠ verified attribution; ссылка может указывать не на тот источник или на несуществующий (галлюцинация ref). VeriCite/TREC вводят attribution verification как ОТДЕЛЬНЫЙ шаг именно потому, что ссылки систематически ненадёжны даже когда присутствуют (AI.5).
**Правильно:** verification = ручная сверка (Grep по FPF-Spec для FPF-разделов; открытие URL для web); claim без ПРОВЕРЕННОГО источника = мнение (A.10).
**Evidence:** AI.5, метод Carrier note, A.10.

## Gate Check

| Критерий гейта | Статус |
|----------------|--------|
| Каждый тезис (T-01…T-09) со scope валидности (A.2.6 USM) | PASS — тип носителя × масштаб команды × автоматизация + «не применим» |
| ≥3 антитезиса на тезис (B.5.2.1 NQD, front по declared dominance) | PASS — по 3 на каждый, с evidence-якорем в sota-research |
| Тип связи по E.4.PFR:4 на каждый тезис | PASS — composition / conflict / scope-dependent / specialization / governing-pattern |
| BridgeMatrix: alignment/divergence + явные Losses + scope строк, no silent fusion | PASS — 6 попарных T1–T4 + 3 ИИ-строки; свёрнутые пары помечены явно (A.11) |
| Контрпримеры (A.11 Sharp Boundary), отдельно от анти-паттернов | PASS — КП-01…КП-07 (1 ИИ), «похоже/нельзя/правильно» |
| Каталог типовых ошибок (E.4.DPF:8), вкл. ИИ-специфичные | PASS — ОШ-01…ОШ-12 (3 ИИ: ОШ-10/11/12) |
| Конфликты не слиты молча | PASS — T1×T3 (копить vs резать) и AI×T3 (fluency vs faithful) названы conflict, разрешены scope-разметкой, не слиты |
| Claim'ы не повышены до fact сверх статуса ClaimSheet (A.10) | PASS — перенос из смежных масштабов помечен hypothesis (T-09 антитезис 1, research-gap унаследован) |

**Ключевые devil's-advocate находки Фазы 2:**
1. **Центральный конфликт T1×T3 (накопление vs сжатие)** — provenance копит, компрессия режет; разрешается НЕ слиянием, а scope-разметкой артефакта (source-pack копит; DPF.md/llms сжимаются). Смешение = либо раздутый носитель, либо потерянная история.
2. **AI×T3 = самый острый ИИ-риск** — faithfulness есть ОТДЕЛЬНАЯ явно оптимизируемая цель (индустрия сама признала: LLMLingua-1→-2), а не побочный эффект компактности; ИИ-самопроверка ~50% ⇒ обязателен внешний критик, отдельный от автора сжатия (guardian Фазы 6, DEC-003).
3. **Два места канона (skill↔room) структурно нарушают SSoT** — «слишком много мест, похожих на источник истины» (docs-as-code drift); дисциплина не заменяет автодетект. Наименьшая митигация: назвать ОДНО каноном, второе — зеркалом, синк под steward.
4. **A.7-различие внутри T4** — «single source» имеет два смысла: T4.1 (golden record из примирения многих систем — НЕприменим к авторскому канону) vs T4.2 (согласованность потребления — применим). Не смешивать.
5. **Research-gap не заполнен домысливанием (A.10)** — эффект гейта (research-first, PFM7) на точность малой markdown-команды не измерен; AI.1–AI.6 из смежных масштабов = hypothesis, унаследована как общее ограничение, не переоткрыта.
6. **Границы scope для solo-масштаба** — полная OAIS-механика (КП-01), team charter (КП-06), ссылочный reuse для прозы (КП-02) — все избыточны/недоступны; берётся принцип, не аппарат.

**Открытое для Фаз 3–5 (source-pack решение / DPF.md):**
- Выбрать ОДНО каноническое место метода и оформить зеркало явно (T-07, ОШ-08) → возможно DEC/DRR.
- Механизм детекта дрейфа skill↔room (checksum/manual-review-cadence) — не решён здесь (research-gap AI.6).
- Разметка «какой артефакт копит, какой сжимается» (T1×T3) — закрепить в паттерне DPF.md.
