# Жизненный цикл свода (DPF/LPF) — практические шаги

Задача-ориентированный маршрут: **создать DPF, дополнить DPF, создать LPF, обновить LPF** — и как во всё это встроен журнал применений (worked-evidence). Это указатель поверх канона, а не его пересказ: шаги ссылаются на первоисточники, детали там.

**Первоисточники (читать по ссылке, не дублировать сюда):**
- Метод и 6 фаз, канон-скелет, паттерны — `references/method.md` (§4 — фазы, §5 — скелет).
- Режимы работы (A/B/C/D) и запуск конвейера — `SKILL.md`.
- Применение свода и журнал worked-evidence — `../dpf-apply/SKILL.md`.
- Допуск в банк (verify + критик) — `plugins/fpf-competency-bank/CONTRIBUTING.md`.

---

## 0. Что такое DPF, LPF и worked-evidence (кратко)

- **Свод** — пакет знаний по FPF: каталог `<ID>/` с `DPF.md` (паттерны, контрпримеры, типовые ошибки) + `references/` (провенанс, ресёрч, оценки).
- **DPF vs LPF — один метод, разный `kind`.** `kind` решают **два** критерия, совпасть должны оба:
  1. **SoTA-опора** — свод стоит на ≥3 независимых традициях (не на одном фреймворке и не на личном опыте);
  2. **Объявленный контекст** — `declaredDomainOrLocalContext` + `intendedReaderOrOperator` явно названы.

  Контекст доменный (применим за пределами одного проекта) + SoTA есть → **Domain Principle Framework (DPF)**. Контекст локален к конкретному пайплайну/проекту → **Local Practice Framework (LPF)**, даже при сильной SoTA.
- **Исполнимость** — у свода есть `assets/apply-prompt.md` (+ `finding-schema.json`): тогда его можно не только читать (ground), но и прогонять агентом с типизированным выходом (apply). LPF обычно исполнимы, DPF — часто нет (knowledge).
- **worked-evidence** (`references/worked-evidence.md`) — журнал применений свода: одна строка на каждое реальное применение. Питает приёмочные случаи (координата D8) и рождает кандидатов в правку. Это петля обратной связи между применением и авторингом.

## 1. Создать DPF

Полный авторинг — режим **A** (`SKILL.md` §A), 6-фазный конвейер (`method.md` §4). Кратко:

1. **Определить состав** — id, `name`, `kind: Domain Principle Framework`, `owner`, `bounded_context` (что покрывает и чем НЕ является). Заполнить содержательно — это питает фазу scope.
2. **Подтвердить состав у человека ДО запуска** — прогон дорогой (~0.5M токенов на компетенцию). Инвариант fail-fast входа: без явного списка конвейер не стартует.
3. **Запустить конвейер** `dpf-authoring-pipeline` (`SKILL.md` «Запуск конвейера»): обязательны `repoRoot` (куда пишем) и `skillDir`. Фазы: Scope → SoTA-harvest → Bridge → Source-pack → Assemble → Critic.
   - **Research-first гейт:** `DPF.md` (фаза сборки) не пишется, пока нет `sota-research.md` + `theses-antitheses.md`. Голых частностей без общего принципа быть не должно.
4. **Проверить результат:** `ls` каталогов (не доверять отчётам агентов); вердикт критика (`gate_passed`, статус пакета). Статус `admissibleForDeclaredDPFUse` — только по критику, пол оценки = 4.
5. **Обновить карту компетенций** целевого проекта (строка свода); замечания критика — в бэклог.

Результат: каталог `<ID>/` с `DPF.md` + `references/` (sota-research, theses-antitheses, source-pack, critic-review, package-adequacy). Пока статус не `admissible` — это `seedOnly`, опираться на свод нельзя.

## 2. Дополнить / обновить DPF

Выбор режима зависит от того, **что** меняется. Не всякая правка — прогон конвейера.

| Что произошло | Режим | Действие |
|---|---|---|
| Опечатка, ссылка, один новый факт в строку | **D** — точечная правка | Обычная дисциплина правок; при содержательном изменении — отметка в `references/`. Конвейер НЕ гонять. |
| Планка изменилась (новая редакция FPF / подошёл `review_due`), содержание — нет | **B** — переоценка | Прогнать только фазу критика → свежий `package-adequacy-<дата>.md` (D1–D11 + статус + строка `maturity-critic`), затем `maturity.py` для профиля зрелости. |
| Критик дал `repairBeforeDPFUse` (список repair-шагов) | **C** — ремонт | Цепочка «ремонт → повторная проверка», максимум 2 круга. Процессные следы выносить в `quality-record-<дата>.md`, не удалять. |
| Нужен новый паттерн / традиция / приёмочный случай | **A** — доавторинг | Догнать нужные фазы конвейера (новый ресёрч → bridge → сборка → критик). |

**Откуда берётся сигнал на обновление:**
- **worked-evidence** — строки с исходом «показал границу» и «кандидат в правку свода» прямо называют, что дополнить (см. §5).
- **refresh-триггеры** (`method.md` §8): изменение FPF-Spec; 3+ свода с одинаковым отклонением (→ править шаблон/скилл, а не каждый свод); обратная связь ролей; наступивший `review_due`.

Правило по колонке доработок: в оценке пакета фиксируется **только то, что влияет на уровень**; косметику делать сразу, отложенное — оформлять обоснованным `no-proposal (проверено: …)` (иначе `maturity.py` засчитает как понижение — гейт floor-fragile).

## 3. Создать LPF (на основе worked-evidence домена)

**Честно про петлю:** автоматического «worked-evidence → LPF» нет. worked-evidence — это **доказательная база**, что локальная практика реально существует и работает; сам LPF авторится тем же 6-фазным методом (режим **A**, `kind: Local Practice Framework`). worked-evidence питает не генерацию, а содержание — приёмочные случаи (§10) и каталог локальных провалов.

Как это выглядит по шагам:

1. **Есть доменный DPF, его применяют** в конкретном пайплайне/проекте (dpf-apply, режим apply/ground). Каждое применение пишет строку в `worked-evidence.md` домена. Накапливается локальная практика: какие паттерны реально срабатывают на этом входе, какие границы вскрылись, какие провалы повторяются.
2. **Локальная практика стабилизировалась** — видно повторяемую процедуру одной стадии (например, ревью диффа на стадии «Упрощение»). Это сигнал: пора вынести её в отдельный LPF, а не держать в голове.
3. **Авторить LPF методом** (режим A, конвейер), с локальными отличиями:
   - `kind: Local Practice Framework`; `declaredDomainOrLocalContext` + `intendedReaderOrOperator` — на конкретный пайплайн/роль, не на домен;
   - **LPF специализирует гейты доменного DPF в процедуру, не переопределяет его принципы** (дублировать текст домена = провал компетенции, A.11 non-redundancy). Домен резолвится по id через dpf-apply, не копируется;
   - **зависимость** от домена — типизированной записью E.4.PFR (`targetRef@edition`, `relationFunction: dependency`), однонаправленно: потребитель → свод, свод о потребителях не знает;
   - **исполнимость** — если стадия прогоняется агентом: добавить `assets/apply-prompt.md` (процедура) + `finding-schema.json` (контракт выхода);
   - **приёмочные случаи (§10)** — брать из worked-evidence домена: реальные диффы/коммиты, где практика сработала и где показала границу.
4. **Критик** (фаза 6) выносит статус. `admissible` — только по существу: локальная завершённость + синхронность исполнимых носителей (широта ≥3 традиций у LPF по замыслу не требуется).

Пример в банке: `LPF-SIMPLIFICATION-REVIEW` специализирует `DPF-COUPLING-GENERALIZATION` в процедуру одной стадии конвейера esb-tools, исполнимый, зависит от домена.

## 4. Обновить LPF

Режимы — те же A/B/C/D, что для DPF (§2). Плюс **одна дисциплина, критичная именно для исполнимых сводов:**

**Синхронность исполнимых носителей (executable-sync).** Если меняется содержание LPF (`DPF.md`), обязаны измениться и `assets/apply-prompt.md` / `finding-schema.json` — иначе агент в режиме apply работает по устаревшей процедуре, а свод уже другой. Это реальный класс дефекта: в журнале `LPF-SIMPLIFICATION-REVIEW` критик круга 1 поймал ровно это — «свод обновлён, apply-prompt/schema — нет» (`repairBeforeDPFUse`, рецидив был бы неизбежен в apply-режиме). Поэтому:

- любое содержательное изменение LPF → пройти режим **B** (переоценка критиком) на свежем `package-adequacy`: адверсарная фаза 6 ловит рассинхрон свода с носителями;
- `maturity.py` отражает это компонентом `executable-sync` (для LPF): рассинхрон капит уровень ниже L3.

В остальном: точечная правка → **D**; наступил `review_due` / новая редакция FPF → **B**; критик дал repair → **C**; новый приёмочный случай из worked-evidence → **A** (доавторинг §10).

## 5. Петля worked-evidence (связующая ткань)

```
        авторинг (метод, 6 фаз)                применение (dpf-apply)
   ┌──────────────────────────────┐      ┌──────────────────────────────┐
   │  создать / дополнить свод     │─────▶│  ground | apply | direct     │
   │  (режимы A / B / C / D)       │      │  на реальном входе задачи    │
   └──────────────────────────────┘      └──────────────┬───────────────┘
              ▲                                          │ одна строка на применение
              │ кандидат в правку / показал границу      ▼
              │                          references/worked-evidence.md
              │                          (питает D8 + refresh-триггеры)
              └──────────────────────────────────────────┘
```

- **Кто пишет строку журнала:** тот, кто применил свод — сразу после реального применения (не после `--list` и не после отказа гейта свежести). Формат строки — единый (`../dpf-apply/SKILL.md` «Журнал применений»): дата · якорь (MR/коммит/файл/сессия) · ground|apply|direct · Паттерн N · что произошло · исход (подтверждает / опровергает / показал границу / TBD).
- **Исход `TBD`** — норма в момент применения; его закрывает шаг worked-evidence ритуала end-session (`/fpf-integration:end-session-setup`).
- **Как журнал возвращается в авторинг:** строки «показал границу» и явные «кандидат в правку свода» — это вход для §2/§4. При переоценке (режим B) сверяются с журналом; новый устойчивый приёмочный случай → доавторинг §10 (режим A).

## 6. Гейт допуска в банк

Свод входит в `fpf-competency-bank` только пройдя оба слоя (`CONTRIBUTING.md`):
- **механика** — `resolve.py --verify <id> --scope bank`: структура, обязательные поля frontmatter, `kind` из enum, свежесть, положительная финальная conformance-строка `E.4.DPF.DA: admissibleForDeclaredDPFUse` в `DPF.md`;
- **содержание** — критик `DPF-ADVERSARIAL-REVIEW`: согласованность `kind`, ≥3 традиции (для DPF), не `seedOnly` с формально верной структурой.

`seedOnly` и `repairBeforeDPFUse` в банк не входят. После входа — карта банка получает строку свода (`competency-map.md`), в т.ч. `maturity_level` по профилю зрелости.
