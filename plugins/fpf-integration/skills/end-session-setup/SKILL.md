# end-session-setup — установка ритуала end-session с шагом worked-evidence

Подтверждение сводов практикой теряется между сессиями: роли применяют паттерны
DPF/LPF, но никто не привязывает «что произошло» к конкретному паттерну — и при
плановом пересмотре свода подтверждений нет. Этот скилл ставит в проект явный
ритуал: команду `/end-session` (или шаг в существующей) с шагом worked-evidence,
который закрывает сессию записями в журналы сводов.

Скилл СТАВИТ ритуал, не исполняет его. На «заверши сессию» / `/end-session`
не активируется — это команды целевых проектов.

## Алгоритм

1. **Корень** — текущий каталог сессии.
2. **Каталог сводов**, по порядку: `project/frameworks/`, `.claude/frameworks/`;
   не нашлись — поищи `*/frameworks/*/DPF.md` (глубина до 3; кириллические пути —
   обычные пути). Сводов нет вообще → предупреди и спроси: ставить «на вырост»
   или отказаться. Молча не ставить. При «на вырост» путь журнала — по типу
   проекта (шаг 3).
3. **Тип проекта:** есть `project/` с признаками процесса (ledger, sessions) —
   «core team»; иначе — код-репозиторий.
4. **Состояние и режим:**
   - `.claude/commands/end-session.md` есть И в нём есть шаг worked-evidence
     (маркер — упоминание журнала `worked-evidence.md` внутри шага/подшага, а не
     случайная ссылка в тексте) → **уже установлен**: сообщи, где стоит шаг, и
     остановись. Ничего не менять.
   - Файл есть, упоминания нет → **merge** (см. «Merge-дисциплина»).
   - Файла нет, core team → **install-full**: поставь
     `assets/end-session-full.md` как `.claude/commands/end-session.md`.
   - Файла нет, код-репозиторий → **install-light**: поставь
     `assets/end-session-light.md` как `.claude/commands/end-session.md` ПЛЮС
     добавь секцию из `assets/rules-section-worked-evidence.md` в
     `rules/frameworks.md` (если он есть) или в CLAUDE.md проекта.
5. **План изменений — до записи, всегда.** Покажи: режим, целевые файлы, полный
   текст вставки/новых файлов (для merge — в виде диффа). Пользователь отклонил →
   не записывай ничего, ни одного файла.
6. **Применение и отчёт одним экраном:** режим, изменённые файлы, путь журнала.

Во всех шаблонах местозаполнитель `<каталог-сводов>` замени фактическим путём,
найденным на шаге 2.

## Merge-дисциплина

Инвариант: **чужой текст — дословно**. После записи сверь diff: изменения
затрагивают только вставленный блок (и, в простом протоколе, номера последующих
шагов). Любое другое отличие — откати и покажи diff с отказом.

Текст вставки — из `assets/step-worked-evidence.md`, способ вставки — по
протоколу хозяина (подробные прецеденты — `references/precedents.md`):

- **Перекрёстные ссылки на номера шагов** (в протоколе есть «см. шаг 5» и т.п.) —
  буквенный подшаг к соседнему шагу («Шаг 5c»), ВСЕГДА, независимо от прочих
  признаков: перенумерация сломала бы ссылки. Этот признак — старший.
- **Богатый протокол** (много шагов) без ссылок на номера — тоже буквенный подшаг,
  ничего не перенумеровывай.
- **Простой линейный протокол** без ссылок на номера — полноценный шаг с
  перенумерацией последующих; перенумерация — единственное допустимое касание
  чужого текста.
- **Многоуровневый протокол** (Полный/Стандартный/Минимальный) — шаг только в
  уровни, где уже есть расширенные шаги; в «минимальный» не лезь. Внутри уровня —
  по правилам выше (есть ссылки на номера → подшаг).

Признаки пересекаются (протокол бывает и многоуровневым, и со ссылками на номера) —
при конфликте выбирай НЕразрушающую вставку (подшаг), а не перенумерацию.

**Форма вставки следует хозяину.** Шаблон `step-worked-evidence.md` написан под
протоколы с заголовками (`## Шаг 5`). Если хозяин — плоский нумерованный список,
оформи вставку как элемент того же списка или как жирную строку-подшаг, а не как
markdown-заголовок; смысловые пункты канона (сверка TBD, ретроспектива, формат
строки) сохрани. Вводную заметку-блокквот шаблонов (`> Шаблон для…`) при установке
СНИМИ — она адресована установщику, не попадает в рабочий протокол.

Точка вставки: после шага подведения итогов/опыта, до завершающих шагов
(git-гигиена, закрытие). Нет такого шага — перед последним.

Язык вставки следует языку протокола хозяина: шаблон задаёт смысл и структуру;
если протокол не на русском — переведи вставку, сохранив структуру и инварианты.

## Инварианты шага worked-evidence

Канонический текст шага — `assets/step-worked-evidence.md`; install-шаблоны
включают тот же текст. Не пересказывай канон из головы — бери файл. Ключевые
инварианты (зашиты в канон, не ослабляй при адаптации):

- формат строки журнала един для всех писателей (его же пишет dpf-apply
  авто-записями) — не переформулировать;
- журнал — `<каталог-сводов>/<ID>/references/worked-evidence.md`; в `DPF.md` не
  писать (носитель свода без процессного состояния);
- ретроспектива сессии обязательна и работает без dpf-apply: прямые
  применения сводов фиксируются с меткой `direct`;
- висящие `TBD`-исходы поднимаются списком и закрываются или явно откладываются
  с причиной — молча не пропускаются;
- дедупликация по якорю и пакету: исход проставляется в существующую авто-запись,
  дубль не создаётся;
- «никакие своды не применялись» — валидный ответ; все своды подряд не
  прочёсываются;
- опровержения ценнее подтверждений: опровергающая запись рождает кандидата на
  правку свода (бэклог проекта или задача).

## Отчёт

Одним экраном: режим (merge / install-full / install-light / уже установлен),
изменённые файлы, путь журнала. Больше ничего.
