# dpf-apply

Резолвер и исполнитель пакетов компетенций (Domain/Local Practice Frameworks, FPF E.4.DPF). Находит пакет по id на диске (project → user → plugin), проверяет свежесть (E.4.DPF.DA), запускает нужный режим использования — ground (знание) или apply (процедура с типизированным выходом).

Это дом сценариев входа в использование (CC-E11-3): отдельный first-entry индекс не ведётся, потому что он бы дублировал три сценария ниже. Каждый сценарий — PUR-форма (E.11.PUR, `PatternUseRecommendation@Context`): концерн → кандидатные применения → рекомендованное применение → ожидаемый первый результат.

## Сценарий 1 — сессия: эфемерный PUR

**Концерн:** прямо сейчас, в разговоре, нужно применить конкретный свод к конкретному вопросу или диффу — без намерения закреплять эту привязку в проекте.

**Кандидатные применения:** прочитать `DPF.md` вручную; вызвать `/fpf-integration:dpf-apply` со скиллом; проигнорировать и решить на глаз.

**Рекомендованное применение:** вызвать скилл с id и входом задачи.

```
/fpf-integration:dpf-apply DPF-COUPLING-GENERALIZATION
  вход: два модуля с дублирующимся парсингом refer — обобщать или нет?

/fpf-integration:dpf-apply LPF-SIMPLIFICATION-REVIEW
  вход: дифф стадии «Упрощение», кандидаты дублирования #1, #2

/fpf-integration:dpf-apply --list
```

**Ожидаемый первый результат:** для ground-пакета — содержимое `DPF.md` прочитано в контекст, паттерны применены к вопросу текстом в этом же ответе. Для apply-пакета — агент вернул находки строго по `finding-schema.json`, число вердиктов равно числу поданных кандидатов. Привязка живёт только в истории этой сессии — не записывается никуда на диск.

## Сценарий 2 — проект: PUR-записи + карта компетенций

**Концерн:** привязка нужна постоянно, для всех участников проекта и агентов, работающих в нём — не пересобирать вход каждый раз заново.

**Кандидатные применения:** держать привязку в голове/переписке (теряется между сессиями); вписать текст свода прямо в промпт роли (запрещено — carrier ≠ edition, см. SKILL.md «Дисциплина»); оформить как PUR-запись в `.claude/rules/frameworks.md` + запись в карте компетенций `.claude/frameworks/competency-map.md`.

**Рекомендованное применение:** PUR-запись в `.claude/rules/frameworks.md`:

```markdown
## PUR: генерализация дублирующегося кода

- **Концерн:** дифф вводит второй похожий блок логики рядом с существующим.
- **Кандидатные применения:** оставить дублирование; точечно поправить оба места;
  обобщить в общий модуль.
- **Рекомендованное применение:** прогнать `DPF-COUPLING-GENERALIZATION` через
  `dpf-apply` (ground) на этапе architect-решения, до имплементации.
- **Ожидаемый первый результат:** решение «обобщать / не обобщать» с явной
  ссылкой на паттерн П1–П6, зафиксированное в PR-описании.
```

и relation-record во frontmatter потребителя (роль/скилл/агент, использующий этот свод), по форме E.4.PFR:

```yaml
competencies:
  - sourceRef: "role:architect"
    targetRef: "DPF-COUPLING-GENERALIZATION@2026-07-13"
    relationFunction: "governs"
    governedUse: "решение об обобщении дублирующегося кода в существующем диффе"
    directGoverningPatternRef: "DPF-COUPLING-GENERALIZATION#П1-П6"
    dependencyOrEditionEffect: "новая редакция пакета требует ревалидации PUR-записи выше"
```

Карта `.claude/frameworks/competency-map.md` — плоский список id → путь → kind → назначение, для быстрого `--list`-сверки глазами (query cues), не дублирует PUR-сценарии.

**Ожидаемый первый результат:** новый участник/агент проекта находит нужный свод без вопроса «а что тут вообще есть» — через `--list` или через `competency-map.md`, затем читает PUR-запись и понимает, когда её применять, без повторного объяснения человеком.

## Сценарий 3 — плагин: access carrier (`skill-pack`)

**Концерн:** несколько проектов должны переиспользовать один и тот же набор сводов, не копируя файлы `DPF.md` в каждый репозиторий по отдельности.

**Кандидатные применения:** скопировать `DPF.md` в каждый проект (расходится при пересмотре — источник истины теряется); держать своды только локально по проектам (дублирование авторинга); упаковать в плагин, везущий `frameworks/` + свою карту компетенций как единственный источник истины.

**Рекомендованное применение:** плагин = `packageKind: skill-pack` — везёт каталог `frameworks/<ID>/DPF.md` внутри себя и свою `competency-map.md`. Путь до плагина дописывается строкой в `~/.claude/frameworks.paths` потребляющего окружения:

```
# ~/.claude/frameworks.paths
/Users/x/.claude/plugins/acme-frameworks/frameworks
```

Каждый агент/команда-потребитель плагина несёт свою relation-record с явным edition-пином (та же форма E.4.PFR, что в сценарии 2) и свою PUR-запись — плагин их не диктует и не хранит централизованно (зависимость однонаправленная, E.5.3: потребитель → свод, не наоборот). Резолюция — `plugin:<ID>`, если нужно явно обойти project/user-переопределения:

```bash
python3 <каталог этого скилла>/scripts/resolve.py plugin:DPF-COUPLING-GENERALIZATION
```

Копирование текста свода в промпт запрещено и здесь — доступ только через резолв пути + чтение по требованию, так же как в сценариях 1–2.

**Ожидаемый первый результат:** второй проект получает тот же пакет без copy-paste `DPF.md`, обновление пакета в плагине автоматически видно всем потребителям при следующем резолве (с учётом edition-пина каждого потребителя — расхождение ловит гейт свежести SKILL.md).
