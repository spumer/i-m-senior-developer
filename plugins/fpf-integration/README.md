# fpf-integration — экосистема First Principles Framework

Помогает работать по сводам компетенций — писаным принципам, по которым команда
принимает решения: находит нужный свод, применяет к задаче и собирает новый по
методу. Этот файл отвечает на устройство плагина в репозитории и держит общий словарь терминов экосистемы. Договор — что даёт
каждый скилл, шесть фаз метода, где ищутся своды, границы — на странице
[`docs/plugins/fpf-integration.md`](../../docs/plugins/fpf-integration.md).

## Словарь

Термины ниже употребляются во всех скиллах плагина. Главное различение —
**свод** это носитель на диске, **компетенция** это то, что после него умеют;
одна компетенция на один свод, id у них общий.

| Термин | Что значит |
|---|---|
| **свод** (он же пакет, пакет компетенций) | каталог `<ID>/` на диске: `DPF.md` + `references/` + опционально `assets/`. Единица, которую резолвят, применяют и переоценивают |
| **компетенция** | что агент умеет после того, как свод прочитан или прогнан. Каталог может лежать на диске, а компетенции ещё не давать — если свод не дошёл до допуска |
| **DPF** — Domain Principle Framework | свод принципов домена: применим за пределами одного проекта, за ним стоит внешняя практика (SoTA). Пример: `DPF-COUPLING-GENERALIZATION` |
| **LPF** — Local Practice Framework | свод локальной практики: привязан к конкретному пайплайну или проекту. Специализирует доменный свод в процедуру, а не переписывает его принципы |
| **FPF** — First Principles Framework | внешний свод-первоисточник, по которому авторятся DPF и LPF (`ailev/FPF`). Не путать с ними: FPF — метод, DPF/LPF — то, что по нему собрано |
| **исполнимый свод** | рядом с `DPF.md` лежит `assets/apply-prompt.md` — свод можно не только читать, но и прогонять агентом с типизированным выходом |
| **ground** | применение-как-знание: `DPF.md` читается в контекст задачи, работает сам вызывающий |
| **apply** | применение-как-процедура: спаунится агент по `apply-prompt.md`, а его выход обязан лечь в `finding-schema.json`, если схема у свода есть. Соответствие схеме и полноту вердиктов сверяет сам `dpf-apply` по своему протоколу |
| **журнал применений** (worked-evidence) | `references/worked-evidence.md` свода: по строке на каждое реальное применение. Из него видны границы свода и кандидаты в правку |
| **резолюция** | поиск свода по id на трёх уровнях: проект → пользователь → плагин, первый найденный побеждает |
| **затенение** (`[shadowed]`) | id нашёлся на нескольких уровнях; верхний перекрыл нижние — обновления перекрытой копии не действуют |
| **протухание** (`[stale]`) | статус свода не `active`, либо `review_due` истёк, отсутствует или не разбирается как дата. Резолвер отдаёт код `2` и причину; отказать и эскалировать владельцу (поле `owner`) велят правила скилла и агента |
| **допуск** (`admissibleForDeclaredDPFUse`) | порог пригодности свода под объявленное применение. Машинно это последняя строка `> conformance:` с маркером `E.4.DPF.DA:` в `DPF.md`, её читает `resolve.py --verify`; дописывает её по правилу метода фаза критики |
| **зрелость L0–L4** | спектр качества над допуском, считается другим скриптом и по другим файлам — см. страницу договора, раздел «Стоимость и зрелость» |
| **авторинг** | сборка или доработка свода по методу `dpf-authoring`. Все шесть фаз гоняет только режим A; B — одна фаза критика, C — ремонт с повторной проверкой, D — точечная правка без конвейера |

## Migration notes — если раньше пользовались этими скиллами

Раньше `fpf-integration` жил внутри плагина `functional-clarity`, а
`dpf-authoring` и `framework-apply` — личными скиллами в `~/.claude/skills/`.
При переходе на плагин:

1. **Удалите личные копии.** Если в `~/.claude/skills/` остались каталоги
   `dpf-authoring` или `framework-apply`, в сессии живут две копии одного скилла:
   личная под голым именем и плагинная под именем с префиксом плагина. Копии
   расходятся при первой же правке, и по какой из них прошла работа, по итогу не
   видно. Сам плагин ничего не удаляет — шаг ручной:
   `rm -rf ~/.claude/skills/dpf-authoring ~/.claude/skills/framework-apply`.
2. **Проверьте старые абсолютные пути в проектах.** Ссылки вида
   `~/.claude/skills/dpf-authoring/…` в правилах и сводах проектов больше не
   работают. Известные точки: `rules/frameworks.md` проекта esb-tools, DPF-своды
   проектов со ссылками на скилл, ссылки в `.claude/workflows/`. Эти проекты
   правятся отдельно — плагин их не трогает.

   Отдельно проверьте `~/.claude/frameworks.paths`: строка, ведущая в удалённый
   каталог, ошибки не даёт — `resolve.py --list` печатает «пакетов не найдено ни
   на одном уровне» с кодом `0`, а хук `SessionStart` при пустом наборе молчит.
   Перепишите её на каталог `frameworks/` того плагина или проекта, откуда своды
   берутся теперь.
3. **Слэш-команды сменили имена.** `/dpf-authoring` →
   `/fpf-integration:dpf-authoring`, `/dpf-apply` →
   `/fpf-integration:dpf-apply`, `/fpf-integration` →
   `/fpf-integration:fpf-integration`. Редиректов нет.
4. **Редакция FPF у dpf-authoring не менялась.** Пин `ailev/FPF@f7c7e93f`
   переехал как есть — он стоит во frontmatter `references/method.md`, в тексте
   `SKILL.md` и в константе конвейера. Обновление редакции — отдельная задача, не
   связанная с переездом.

   Метод авторинга и навигационный индекс скилла `fpf-integration` запинены на
   разные снимки спеки (`f7c7e93f` и `44dd88188a07`) — это разные носители.
   Сверка пина с MCP-справочником остаётся ручной: `get_fpf_index_status` отдаёт
   `sourceHash` и `builtAt`, ревизию upstream — нет.
