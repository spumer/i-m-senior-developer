# fpf-integration — экосистема First Principles Framework

Вся FPF-экосистема одним плагином: интеграция FPF в multi-agent проекты, авторинг
сводов принципов и резолвер-исполнитель пакетов компетенций.

## Словарь

Термины ниже употребляются во всех скиллах плагина. Главное различение —
**свод** это носитель на диске, **компетенция** это то, что после него умеют;
одна компетенция на один свод, id у них общий.

| Термин | Что значит |
|---|---|
| **свод** (он же пакет, пакет компетенций) | каталог `<ID>/` на диске: `DPF.md` + `references/` + опционально `assets/`. Единица, которую резолвят, применяют и переоценивают |
| **компетенция** | что агент умеет после того, как свод прочитан или прогнан. Каталог может лежать на диске, а компетенции ещё не давать — если свод не дошёл до допуска |
| **DPF** — Domain Principle Framework | свод принципов домена: применим за пределами одного проекта, за ним стоит внешняя практика (SoTA). Пример: `DPF-COUPLING-GENERALIZATION` |
| **LPF** — Local Practice Framework | свод локальной практики: привязан к конкретному пайплайну или проекту. Специализирует доменный свод в процедуру, а не переписывает его принципы |
| **FPF** — First Principles Framework | внешний свод-первоисточник, по которому авторятся DPF и LPF (`ailev/FPF`). Не путать с ними: FPF — метод, DPF/LPF — то, что по нему собрано |
| **исполнимый свод** | рядом с `DPF.md` лежит `assets/apply-prompt.md` — свод можно не только читать, но и прогонять агентом с типизированным выходом |
| **ground** | применение-как-знание: `DPF.md` читается в контекст задачи, работает сам вызывающий |
| **apply** | применение-как-процедура: спаунится агент по `apply-prompt.md`, а его выход обязан лечь в `finding-schema.json`, если схема у свода есть |
| **журнал применений** (worked-evidence) | `references/worked-evidence.md` свода: по строке на каждое реальное применение. Из него видны границы свода и кандидаты в правку |
| **резолюция** | поиск свода по id на трёх уровнях: проект → пользователь → плагин, первый найденный побеждает |
| **затенение** (`[shadowed]`) | id нашёлся на нескольких уровнях; верхний перекрыл нижние — обновления перекрытой копии не действуют |
| **протухание** (`[stale]`) | статус свода не `active` либо истёк `review_due`. Работа по протухшему своду запрещена, решение — за владельцем (поле `owner`) |
| **допуск** (`admissibleForDeclaredDPFUse`) | порог пригодности свода под объявленное применение. Ставит только вердикт критика, шестая фаза авторинга |
| **зрелость L0–L4** | спектр качества НАД допуском, не сам допуск — см. «Чего ожидать» |
| **авторинг** | сборка или доработка свода 6-фазным конвейером скилла `dpf-authoring` (режимы A/B/C/D) |

## Что получаете при установке

- **Skill `fpf-integration`** — внедрение First Principles Framework (FPF) в
  multi-agent проекты: evidence-аудит решений, decay-механизм (DRR), проверка
  альтернатив (NQD), аксиомы A.7/A.10/A.11/A.1.1, навигация по спеке через
  готовые карты и grep-паттерны. Загружается на "integrate FPF", "FPF audit",
  "review decisions with FPF", "evidence graph review". Источник FPF:
  `https://github.com/ailev/FPF`.
- **Skill `dpf-authoring`** — авторинг сводов принципов (DPF/LPF): 6-фазный
  конвейер с файловым handoff, встроенные пакеты ролей (adversarial review,
  knowledge curation), канон метода и шаблоны внутри. Загружается на «создай
  DPF», «авторинг DPF», «переоцени пакет».
- **Skill `dpf-apply`** — резолвер и исполнитель пакетов компетенций:
  находит пакет по уровням project → user → plugin, проверяет свежесть, читает
  свод в контекст (ground) или спаунит агента по apply-промпту (apply).
  Загружается на «примени компетенцию», id вида `DPF-*` / `LPF-*`.
- **Агент `dpf-gate`** — гейт-диспетчер: проверяет допуск к своду (найден ли,
  не протух ли), называет режим работы и возвращает план, не выполняя работу
  сам. Инструментов записи у него нет — править свод он не может физически.
  Зовите явно, когда речь о применении, создании или обновлении свода.

## Что где живёт

Свод (пакет DPF/LPF) ищется на трёх уровнях, первый найденный побеждает:
проект (`.claude/frameworks/<ID>/`) → пользователь (`~/.claude/frameworks/<ID>/`)
→ плагин (пути из `~/.claude/frameworks.paths`). Как это работает точнее —
`skills/dpf-apply/SKILL.md`, раздел «Резолюция».

Пакет — это каталог `<ID>/`, в нём:

- `DPF.md` — сам свод (паттерны, контрпримеры, типовые ошибки);
- `references/` — ресёрч, провенанс, оценки, журнал применений;
- `assets/` — исполнимая процедура (промпт + схема выхода) — только если
  свод исполнимый.

За канон-скелетом `DPF.md` — `skills/dpf-authoring/references/method.md`;
за маршрутом «что делать под конкретную задачу» —
`skills/dpf-authoring/references/lifecycle.md`. Это первоисточники, здесь
они не пересказываются.

## Жизненный цикл

Свод живёт по кругу: создать → применять на задачах → каждое применение
пишет строку в журнал → журнал показывает границы и кандидатов в правку →
дополнить или переоценить свод → снова применять. Диаграмма петли и разбор
каждого шага — `skills/dpf-authoring/references/lifecycle.md`, §5 «Петля
worked-evidence».

## Что под какую задачу

Агент `dpf-gate` проверяет допуск к своду (найден ли, не протух ли) и
называет режим работы, не выполняя её сам — для большинства строк ниже это
первая точка входа.

| Хочу | Куда идти | Что получу |
|---|---|---|
| Применить свод к задаче | `dpf-gate` → скилл `dpf-apply` | план (допуск, режим ground/apply) → чтение свода в контекст или прогон агента по `apply-prompt.md`, строка в журнале применений |
| Создать новый DPF/LPF | `dpf-gate` → скилл `dpf-authoring`, режим A | план с составом на подтверждение → каталог свода (`DPF.md` + `references/`) |
| Дополнить или обновить существующий свод | `dpf-gate` → скилл `dpf-authoring`, режим B/C/D | план с названным режимом (таблица — `skills/dpf-authoring/references/lifecycle.md`, §2) → точечная правка, переоценка критиком или ремонт |
| Понять, что со сводом сейчас | `dpf-gate` | дословный вывод `skills/dpf-authoring/assets/maturity.py` (уровень L0–L4, чек-лист компонентов, что доработать) |
| Посмотреть, какие своды вообще есть | `skills/dpf-apply/scripts/resolve.py --list` | слитая карта id по всем уровням, отметки затенения (`[shadowed]`) и протухания (`[stale]`) |

## Чего ожидать

- **Стоимость.** Полный авторинг (режим A) стоит порядка 0.5M токенов на
  одну компетенцию и требует подтверждённого человеком списка компетенций
  до запуска — `skills/dpf-authoring/SKILL.md`, режим A, шаг 2.
- **Статусы свода.** `admissibleForDeclaredDPFUse` — пригоден, этот статус
  ставит только вердикт критика; `seedOnly`/стаб — заготовка, нужен
  доавторинг; `repairBeforeDPFUse` — нужен ремонт (режим C); наступивший
  `review_due` или смена редакции FPF — нужна переоценка (режим B).
  Подробнее — `skills/dpf-authoring/SKILL.md`, «Инварианты», и
  `skills/dpf-authoring/references/lifecycle.md`, §2.
- **Уровни зрелости L0–L4** (`seed → admissible → grounded → exercised →
  exemplar`) — это спектр качества НАД порогом допуска, не сам допуск:
  свод может быть пригоден (`admissible`) и при этом стоять невысоко на
  этой шкале. Считает и печатает `skills/dpf-authoring/assets/maturity.py`.

## Migration notes — если раньше пользовались этими скиллами

Раньше `fpf-integration` жил внутри плагина `functional-clarity`, а
`dpf-authoring` и `framework-apply` — личными скиллами в `~/.claude/skills/`.
При переходе на плагин:

1. **Удалите личные копии.** Если в `~/.claude/skills/` остались каталоги
   `dpf-authoring` или `framework-apply` — личный уровень затеняет плагинный:
   обновления плагина не будут действовать, а вы не заметите. Сам плагин ничего
   не удаляет — шаг ручной:
   `rm -rf ~/.claude/skills/dpf-authoring ~/.claude/skills/framework-apply`.
2. **Проверьте старые абсолютные пути в проектах.** Ссылки вида
   `~/.claude/skills/dpf-authoring/…` в правилах и сводах проектов больше не
   работают. Известные точки: `rules/frameworks.md` проекта esb-tools, DPF-своды
   проектов со ссылками на скилл, ссылки в `.claude/workflows/`. Эти проекты
   правятся отдельно — плагин их не трогает.
3. **Слэш-команды сменили имена.** `/dpf-authoring` →
   `/fpf-integration:dpf-authoring`, `/dpf-apply` →
   `/fpf-integration:dpf-apply`, `/fpf-integration` →
   `/fpf-integration:fpf-integration`. Редиректов нет.
4. **Редакция FPF у dpf-authoring не менялась.** Пин `ailev/FPF@f7c7e93f`
   переехал как есть; обновление редакции — отдельная задача, не связанная с
   переездом.

## Совместимость

Плагин `functional-clarity` (принципы кода, style guide, Code-Change Discipline)
теперь не содержит FPF-скиллов и развивается независимо. Ставьте оба, если нужны
и принципы кода, и FPF-экосистема.
