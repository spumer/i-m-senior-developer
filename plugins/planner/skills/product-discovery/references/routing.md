# Routing — диагностика способностей и выбор поставщика

Справочник отвечает на три вопроса: какие способности нужны виду документа, кто из доступных компонентов их закрывает и что делать, когда никто не закрывает. Продуктовую работу он не выполняет и её качество не оценивает.

## Четыре слоя различения

Не путай эти слои — ошибка между ними даёт ложное покрытие:

| Слой | Что это | Пример |
|---|---|---|
| Пакет | Установленный набор компонентов | плагин Core Team |
| Доступный компонент | Файл, который виден в окружении и поверхностен | проектный агент `product` |
| Заявленная способность | Что компонент обещает в описании | «продуктовая проработка» в description |
| Фактический результат запуска | Что компонент вернул в этом запуске | черновик с обязательными полями или отказ |

Установленный пакет без доступной роли поставщиком не считается. Заявленная способность без подтверждённого договора не даёт покрытия `full`. Фактический результат проверяется по договору ответа (раздел ниже) уже после выбора.

## Таблица способностей по видам документов

Базовый набор способностей:

| Способность | Что закрывает | Нужна для |
|---|---|---|
| `problem_outcome_framing` | формулировка проблемы и наблюдаемого результата | `idea`, `epic`, `feature` |
| `product_synthesis` | синтез черновика документа из собранных утверждений | `idea`, `epic`, `roadmap` |
| `decision_dialogue` | значимые решения с человеком | `idea`, `epic`, `roadmap`, `feature` |

Базовый набор — источник обязательности для помощника `product_state.py`, а `§9` — источник кандидатов. Если в `§9` нет строки базовой способности для нужного вида, способность считается непокрытой, даже если компонент существует, и `route` возвращает код `3`. Строка дополнительной способности проекта тоже делает её обязательной для перечисленных в ней видов.

## Формат раздела §9

Раздел `§9` файла `planner-context.md` — машинный договор, который разбирает помощник. Заголовок раздела начинается с `## §9`. Заголовок таблицы дословно:

```markdown
## §9 Способности и поставщики

| Способность | Нужна для | Поставщик | Источник | Доступность | Покрытие | Основание | Ограничения | Приоритет |
|---|---|---|---|---|---|---|---|---|
| product_synthesis | idea, epic, roadmap | product | project | available | full | .claude/agents/product.md | — | project |
```

Закрытые значения, дословно:

```text
Доступность: available | stale | error | not-surfaced
Покрытие:    full | partial | unknown | none
Приоритет:   configured | project | plugin | builtin
```

Правила заполнения:

- «Нужна для» — список видов через запятую: `idea`, `epic`, `roadmap`, `feature`;
- «Основание» содержит конкретный путь или запись обнаружения, которая объясняет покрытие;
- «Ограничения» — краткая пометка; прочерк означает «не задано»;
- покрытие `full` допускается только когда описание компонента подтверждает договор способности.

## Правило основания

Совпадение имени не является основанием. Компонент, названный «product», но с другим договором, получает покрытие `unknown`, а не `full`.

Основание содержательно, когда после удаления HTML-комментариев, символов `—` и пробелов остаётся текст. Прочерк, одна метка или их сочетание не дают покрытия: помощник возвращает для такой строки `coverage: unknown`, не меняя `planner-context.md`. Он не проверяет, существует ли указанный путь и можно ли его прочитать.

## Разбор матрицы

Точный вызов:

```text
python3 "${CLAUDE_PLUGIN_ROOT}/skills/product-discovery/assets/product_state.py" \
  parse-capabilities <planner-context.md>
```

Возвращает массив строк матрицы. У каждой строки есть `line` — её номер в Markdown-файле. Код `3` с номером строки — неизвестное значение закрытого поля или нарушенный формат таблицы: это остановка, матрицу надо исправить в `planner-context.md`, а не обходить.

## Порядок выбора

Точный вызов:

```text
python3 "${CLAUDE_PLUGIN_ROOT}/skills/product-discovery/assets/product_state.py" \
  route <planner-context.md> --for <kind> [--pin <provider>]
```

`--pin` главнее общего ранжирования: закреплённый поставщик выбирается на каждую способность, где заявлен, без сравнения с другими.

Без `--pin` кандидаты внутри каждой способности ранжируются так:

1. все кандидаты с покрытием `full` в порядке `configured` → `project` → `plugin` → `builtin`;
2. затем все кандидаты с покрытием `partial` в том же порядке.

Поэтому проектный `partial` не опережает плагиновый `full`. Выбирается ровно один поставщик на каждую требуемую способность. Несколько способностей могут закрыть разные поставщики — это составной набор, он допустим.

## Правила остановки

Код `3` у `route` — остановка только для матрицы, которая прочиталась. Если сам раздел §9 отсутствует или не разбирается (сообщение помощника в stderr называет секцию §9 или формат таблицы), это не продуктовая остановка: выполни повторное сканирование по `plugins/planner/skills/planner/references/bootstrap.md`, затем повтори `route`.

Для прочитавшейся матрицы код `3` — остановка, подмены закреплённого поставщика нет:

- закреплённый поставщик отсутствует в строках требуемой способности;
- закреплённый поставщик есть, но недоступен;
- закреплённый поставщик доступен, но его покрытие не `full` и не `partial`;
- без закрепления: обязательная способность не покрыта ни одним доступным кандидатом с покрытием `full` или `partial`.

Без закрепления помощник оставляет stdout пустым. В stderr он называет непокрытую способность и каждую относящуюся к ней строку как номер строки, поставщика и причину отклонения. Закреплённый поставщик возвращает своё сообщение об отсутствии, недоступности или недостаточном покрытии.

Покрытие `unknown` и `none` не считаются достаточными. Доступность `stale`, `error`, `not-surfaced` исключает поставщика из выбора. Устаревший компонент помечается в матрице, а не молча удаляется.

## След выбора

`route` выводит одну строку JSON с ключами:

- `for` — вид документа;
- `context_scanned_at` — самая поздняя дата `YYYY-MM-DD` из HTML-меток в ячейках «Основание» по всей матрице либо `null`, если меток с датой нет;
- `required` — требуемые способности;
- `candidates` — все строки матрицы, относящиеся к виду: `line`, `capability`, `provider`, `availability`, `coverage`, `priority`, `evidence`, `selected`, `rejected`;
- `fallback_used` — `true`, когда хотя бы одна способность закрыта поставщиком с приоритетом `builtin`;
- `limitations` — ограничения выбранных поставщиков из матрицы;
- `writer` — всегда `planner`. Иное значение — нарушение договора.

Причины отклонения в `rejected`: `not-pinned-provider`, `availability-<значение>`, `no-substantive-evidence`, `coverage-<значение>`, `higher-priority-<coverage>-provider`, `higher-coverage-provider`, `earlier-equivalent-provider`.

След не сохраняется отдельным файлом. Процедура выводит его в итог запуска: выбранные и отклонённые строки остаются видимыми.

## Договор поставщика

Вход поставщику:

- вид документа;
- текущая формулировка задачи;
- уже собранные утверждения с их типом (наблюдение, внешний источник, допущение, POV-гипотеза, неизвестное);
- список требуемых способностей;
- явный запрет записи файлов.

Выход — нормализованный черновик с полями:

```text
problem
outcome
actors
scope_in
scope_out
assumptions[]
unknowns[]
candidate_slices[]        # для epic и roadmap
recommended_outcome       # для idea
limitations[]
```

Обязательны `problem`, `outcome` и `limitations`.

### Машинная проверка состава и уборка черновика

После успешного выбора процедура резервирует путь:

```text
python3 "${CLAUDE_PLUGIN_ROOT}/skills/product-discovery/assets/product_state.py" \
  reserve-response-draft
```

В ответе будет единственный путь `DraftLease.path` с именем `<tempdir>/provider-response.json`. Он лежит в уникальном системном временном каталоге вне репозитория. Поставщик файл не пишет: только процедура записывает по этому точному пути объект JSON с полями ответа.

Состав ответа проверяет помощник, а не глаз. Сразу после записи вызови:

```text
python3 "${CLAUDE_PLUGIN_ROOT}/skills/product-discovery/assets/product_state.py" \
  check-response <DraftLease.path> --for <kind> --consume
```

Код `0` — состав принят; JSON содержит перечень полей, список `limitations` и `draft_removed: true`. Помощник удалил черновик и его каталог, а процедура продолжает с принятым в памяти содержимым. Код `3` — ответ отклонён: помощник называет полный путь и причину; до возврата он пытается удалить черновик и каталог. Ошибка уборки добавляется к сообщению, а не скрывается. Код `64` — неверный вызов.

Если поставщик не вернул ответ или запись не создала файл, отмени аренду:

```text
python3 "${CLAUDE_PLUGIN_ROOT}/skills/product-discovery/assets/product_state.py" \
  release-response-draft <DraftLease.path>
```

При отсутствии файла это штатный исход: JSON содержит `draft_existed: false` и `removed: false`. К сборке тела не переходи.

Помощник проверяет только состав: присутствие и непустоту `problem`, `outcome`, `limitations`, принадлежность полей виду, тип каждого поля. Поле не своего вида — отклонение, а не тихое отбрасывание: `recommended_outcome` относится только к замыслу, `candidate_slices` — к общей гипотезе и порядку фич.

### Что остаётся суждением

Машинно не проверяются и потому остаются на скилле:

- сообщение поставщика о записи файла;
- заявления, запрещённые разделом ниже.

Оба случая — отклонение по тем же правилам, что и неполный состав.

При отклонении ответ не используется как целое: для недостающей части применяется ограниченный режим (встроенный поставщик с явной пометкой), пригодная часть внешнего ответа не подмешивается к отклонённой без пометки об источнике.

Встроенный поставщик работает в ограниченном режиме, и это видно: его ограничения перечисляются в ответе и попадают в итог запуска. При доступном полном внешнем поставщике встроенный не выбирается.

## Запреты заявлений

Ни внешний, ни встроенный поставщик не вправе заявлять по результату работы модели:

- исследование пользователей;
- отзыв реального человека;
- независимую многоролевую проверку;
- подтверждение гипотезы.

Такое заявление в ответе равносильно нарушению договора. Отсутствие сведений — не отрицательный результат; ограниченная опора остаётся видимой в `limitations`.
