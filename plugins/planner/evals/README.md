# Кейсы проверок planner

Набор для `claude plugin eval`. Здесь только состав набора и его границы.
Формат кейсов, типы критериев и порядок прогона описаны в общей документации
(`docs/testing/`).

## Состояние набора

Числа последнего прогона живут в его `aggregate-result.json` под `results/`, и
Git этот каталог не отслеживает. Здесь они не дублируются: файл описывает состав
набора, а не результат.

Гейт раннего доступа и его включение — в `docs/testing/early-access.md`.

## Запуск

Полный релизный прогон из корня репозитория:

```bash
python3 plugins/planner/evals/run.py
```

Скрипт до расходов проверяет версию Claude Code, доступность `plugin eval` и
структуру planner через `plugin validate --strict`. Затем он запускает ровно
три повтора каждого кейса на модели `opus` с лимитом `$6`, оставляет отчёт
локальным и отклоняет частичный результат, пропущенный кейс, неполные повторы и
пропуск платного критерия. Результаты лежат в новом каталоге
`plugins/planner/evals/results/run-<id>/`.

Модель закреплена по наблюдению: на `sonnet` маршрутизация в проработку не
срабатывала ни разу за шесть повторов.

`baseline-provider-limits` получает `Write` на двух уровнях: кейс запрашивает
инструмент, а скрипт разрешает его операторским `--allow-tools Write`. Без
второго разрешения проверка «не пишет файлы» запрещала бы невозможное.

Прямой вызов CLI нужен только для отладки отдельного кейса и не считается
релизной проверкой:

```bash
claude plugin eval plugins/planner \
  --case idea-routing \
  --ablation none \
  --runs 1 \
  --no-scaffold \
  --no-publish
```

`--ablation none` выбран сознательно: базовое сравнение «без плагина» для
продуктовых кейсов не имеет смысла — без плагина нет ни скилла проработки, ни
встроенного поставщика, и разность очков будет мерить наличие плагина, а не
качество его поведения.

## Что покрыто

| Кейс | Что проверяет |
|---|---|
| `idea-routing` | сырой замысел попадает в проработку, а не сразу в требования фичи |
| `multi-step-input` | вход из нескольких самостоятельных исходов не сворачивается в одну фичу |
| `baseline-provider-limits` | встроенный поставщик называет ограничения, не заявляет исследование и не пишет файлы, хотя запись ему разрешена кейсом |

В `baseline-provider-limits` инструмент `Write` намеренно разрешён. Без этого
проверка «файлов не пишет» запрещала бы то, что и так невозможно, и ничего бы
не доказывала.

## Что здесь проверять не нужно

Помощник `product_state.py` и выбор поставщика — детерминированный код. Они
покрыты обычными тестами рядом с исходником
(`skills/product-discovery/assets/test_product_state.py`). Eval проверил бы их
слабее и дороже.

Не добавляйте кейс, который ищет слова в ответе там, где обычный тест может
вызвать функцию и сверить результат.

## Чего этот набор не проверяет

Четыре продуктовые команды обязаны спрашивать человека через
`AskUserQuestion`, а формат кейса не умеет подставлять ответы. Поэтому
одношаговыми кейсами нельзя покрыть:

- живой интерактивный выбор человека;
- сократический диалог как последовательность реальных вопросов и ответов;
- поведение после человеческого решения;
- проверку готовности документа, которая наступает в конце диалога.

Причина глубже отсутствия ответов, и она наблюдаема: в песочнице прогона
`AskUserQuestion` модели не выдаётся вовсе. Список инструментов в
`out/trace.jsonl` (запуск с `--keep-temp`) его не содержит, хотя кейс называет
его в `allowed_tools` — поле состав инструментов песочницы не задаёт. Поэтому
критерий на число вызовов этого инструмента не наблюдает поведение: требование
«вызван хотя бы раз» не выполнимо никогда, а требование «не вызван ни разу»
выполняется само собой. Два таких кейса из набора сняты; вернуть их можно
только вместе со средой, которая этот инструмент выдаёт.

Кейсы выше проверяют первый шаг и договор поставщика — то, что наблюдаемо без
диалога.

## Как добавить кейс с диалогом

Такие кейсы работают только воспроизведением записанного диалога:

1. провести настоящий диалог до нужного хода;
2. сохранить транскрипт JSONL в каталоге кейса;
3. указать его в `context.history_file` внутри `case.yaml`;
4. следующий ход человека передать в `execution.prompt`;
5. оценивать поведение именно на этом ходу.

Транскрипт должен быть записью состоявшегося прогона. Написанный от руки
диалог — это не свидетельство: кейс начнёт проверять придуманное поведение
вместо настоящего.

Такие кейсы запускаются только с `--ablation none`: базовый прогон без плагина
не должен проходить записанный диалог, как будто контекст плагина был.

## Оставшиеся непроверенными защиты

Из десяти контрпримеров договора машинно проверяемые закрыты тестами
помощника. Автоматической проверки не имеют защиты, живущие только в тексте
справочников:

- отсутствие подтверждений не превращается в отказ от идеи;
- гипотеза точки зрения не называется отзывом реального человека;
- элемент не попадает в ближайший горизонт без готовой фичи;
- гипотеза без границ и объёма усилий не проходит проверку готовности.

Первые две частично закрывает `baseline-provider-limits`. Две последние
наступают в конце диалога и требуют записанного транскрипта.
