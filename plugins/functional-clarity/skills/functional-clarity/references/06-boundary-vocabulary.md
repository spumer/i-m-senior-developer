# Словарь границы — язык объявления принадлежит контексту-владельцу

Контекст — зона владения знанием: слой внутри приложения, модуль в
монолите, сервис, система соседней команды. Между любыми двумя контекстами
действует одно правило, и масштаб границы его не меняет:

**Всё, что контекст объявляет на своей границе, он называет своим языком —
своими фактами и потребностями.** Действия, механизмы и доменные термины
тех, кто по ту сторону границы, в объявление не попадают.

У любой границы два уровня. Структурный — кто от кого зависит, нет ли
циклов, где объявлен контракт — проверяется инструментами. Словарный —
чьими словами названо объявленное — не проверяется ничем, кроме этого
правила.

## Три канала утечки

Знание пересекает границу не только импортом:

1. **Имя** — идентификатор, имя события, имя поля схемы.
2. **Тип и сигнатура** — параметры и их типы несут настройки чужого
   механизма.
3. **Текст** — докстринг, комментарий, описание контракта, документация.

Утечка любым каналом — один и тот же дефект: знание, которое по дизайну не
должно было попасть в контекст, уже там.

## Тест подстановки — критерий на любом уровне

Мысленно замени контрагента по ту сторону границы: другую реализацию, иной
канал доставки, второго потребителя рядом с первым, другую команду. Имя,
сигнатура и текст объявления остались точными? Если хоть что-то пришлось бы
править — объявление несёт чужой словарь. Это дефект границы с
воспроизводимым критерием, не стилистика.

## Кто переводит словари

Перевод между словарём владельца и словарём потребителя — обязанность
зависимой стороны, на её территории: адаптер, подписчик, антикоррупционный
слой. Владелец не именует свои объявления «удобно для потребителя» — именно
так словарь потребителя и протекает. У себя потребитель волен называть вещи
как угодно.

## Одно правило на всех уровнях

- **Слой** (чистая архитектура): порт, объявленный во внутреннем слое,
  говорит языком домена — без `queue=`, `retry=` и прочих ручек адаптера.
- **Модуль** (граница в монолите): канонический случай — инверсия
  зависимости; подробный разбор ниже.
- **Сервис**: событие называет факт производителя (`order.created`), а не
  ожидаемую реакцию потребителя (`trigger_welcome_email`); в полях
  контракта нет настроек чужого механизма.
- **Система, команда**: опубликованная схема или колонка не называется по
  применению у потребителя (`for_crm_export` в схеме владельца данных —
  утечка: смени потребителя, и имя лжёт).

Опаснее всего инверсия зависимости: B зависит от A, контракт объявлен в A и
реализуется в B. Именно тогда ничто структурное не мешает словарю B протечь
в имена A — импортов нет, тайпчекер доволен, тесты зелёные. Дефект невидим
в момент появления и бьёт при эволюции: замена контрагента превращает имя в
ложь; переименование механизма в B требует правок в A, хотя зависимость
разворачивали ровно затем, чтобы этого не было; читатель A вынужден знать
домен B, чтобы понять собственный код A.

## Канонический разбор — граница модулей

Четыре класса утечки, разобранные на самой частой границе — межмодульной,
при инверсии зависимости. Те же классы воспроизводятся на границе слоёв,
сервисов и систем.

### 1. Имя порта или метода — действие/механизм подписчика — ❌

    ❌ class InvoiceEmailQueuePort(Protocol):
           async def enqueue_email(self, invoice_id: UUID) -> None: ...
       # «email» — действие подписчика, «queue» — его механизм

    ✅ class InvoiceObserverPort(Protocol):
           async def invoice_created(self, invoice_id: UUID) -> None: ...
       # собственный факт владельца

Владелец сообщает своё событие; что с ним делать — знание подписчика.

### 2. Сигнатура — настройки чужого механизма — ❌

    ❌ async def invoice_created(
           self, invoice_id: UUID, queue: str = "notifications", retry: int = 3
       ) -> None: ...

    ✅ async def invoice_created(self, invoice_id: UUID) -> None: ...

`queue` и `retry` — параметры механизма реализации; вызывающий код принимает
решения за подписчика, знание протекло уже не именем, а типом. Абстрактный
контракт передаёт только факты владельца: идентификаторы и, при
необходимости, транзакционный контекст.

### 3. Имя события — ожидаемая реакция вместо собственного факта — ❌

    ❌ emit("trigger_welcome_email", user_id=user.id)   # чужое действие
    ✅ emit("user_registered", user_id=user.id)         # собственный факт

Со вторым потребителем (например, начислением бонусов) имя-реакция лжёт:
бонусный модуль оказывается подписан на «trigger_welcome_email».

### 4. Текстовая утечка — докстринг/комментарий про внутренности подписчика — ❌

    ❌ """Ставит задачу рассылки в очередь notifications
       (см. notifications/jobs.py::send_invoice_email)."""

    ✅ """Уведомляет наблюдателя о факте создания счёта в рамках открытой
       транзакции; реализация подключается через DI."""

Импортов нет, линтер молчит — а читатель отправлен изучать чужой контекст, и
текст устареет при первом же рефакторинге подписчика.

## Границы применения — что не считать утечкой

- **Внутренние имена контекста.** Правило действует для элементов,
  объявленных на границе. Внутри своего контекста код свободно говорит о
  собственных механизмах и очередях.
- **Слой предъявления.** Подписи кнопок, тексты для оператора, продуктовые
  формулировки на витринах — не доменный код границы; их словарь диктует
  продукт.
- **Совпадение словарей.** Если термин — собственный факт владельца, его
  совпадение с языком потребителя утечкой не является. Решает тест
  подстановки, а не поиск «подозрительных слов».

## Тяжесть находки (severity) на ревью

- **major** — объявления, связывающие эволюцию контекстов: публичные порты,
  события, сигнатуры, контракты, схемы.
- **minor** — чисто текстовые утечки (докстринги, комментарии, описания).

## Как это обеспечивается (два слоя)

1. **Этот референс** — единственный нормативный источник: правило владения,
   каналы утечки, тест подстановки, правило перевода, классы утечек,
   границы применения. Врезки в `00-principles.md` (Принцип 7) и в скиллах
   `sdlc` и стековых архитекторов — напоминания со ссылкой сюда; правило
   меняется только здесь.
2. **Дизайн-тайм и ревью.** Архитектор фиксирует владельца словаря в
   таблице контрактов (колонка «Vocabulary») и прогоняет тест подстановки
   по каждой строке с инверсией зависимости. Ревьюер ловит просочившееся
   категорией «vocabulary leak across a context boundary» — она явно
   выведена из-под принципа «нейминг — не предмет ревью», потому что у
   находки есть воспроизводимый критерий.
