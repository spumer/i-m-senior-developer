# apply-prompt: исполнение стадии «Упрощение» (LPF-SIMPLIFICATION-REVIEW)

> Промпт роли-исполнителя одной стадии конвейера 4.0. Самодостаточен для агента: не пересказывает
> тела паттернов П1–П6 базового свода или П1–П6 этой LPF — они читаются по месту резолва (шаг 0).
> Здесь — только процедура, порядок и формат выхода.

## Шаг 0 — обязательный первый шаг: прочитать оба свода по резолву id

Применение всегда парное: пакет × объявленное использование (declaredUse = стадия «Упрощение»
конвейера 4.0; nonUseBoundary = код-ревью на корректность, следующая стадия; intendedReaderOrOperator =
reviewer стадии / оркестратор; reopenCondition = см. §11 `DPF.md` refresh triggers). Не открывай
файлы по относительному пути — резолвь по id в порядке:

1. проект — `<repo>/.claude/frameworks/<id>/DPF.md`
2. пользователь — `~/.claude/frameworks/<id>/DPF.md`
3. плагины — путь из конфига плагина

Прочитать целиком:

- `DPF-COUPLING-GENERALIZATION` (id) — опорный доменный свод, критерий обобщения П1–П6, каталог
  ошибок №1–12. Edition-пин для этого прогона — см. §9 `DPF.md` этой LPF (Relations): дата/статус
  `admissibleForDeclaredDPFUse`, 2026-07-13.
- `LPF-SIMPLIFICATION-REVIEW` (id, эта практика) — П1–П6 процедуры ревью-стадии, §4 `DPF.md`.

Пакеты **не копируются** в этот промпт (carrier ≠ framework edition) — только читаются по месту
резолва при каждом запуске стадии.

## Шаг 1 — вход: диапазон диффа

Вход — диапазон диффа одной фазы конвейера (`git diff <base>...<head>` или диапазон коммитов),
полученный оркестратором ДО вызова этой стадии. Reviewer работает с точным списком изменённых
файлов и хунков этого диапазона — не с рабочим деревом целиком.

## Шаг 2 — процедура

### 2.1 Скан кандидатов — два класса

**Класс А — повтор.** Просмотреть дифф на текстовый/структурный повтор с существующим кодом
репозитория (внутри диффа и вне его). Каждый найденный повтор — `Candidate`, не `Finding`
(П5 этой LPF) до прохождения гейтов ниже.

**Класс Б — новое публичное имя (П6 этой LPF).** Инвентаризовать в диффе новые имена БЕЗ
ведущего подчёркивания (функции, методы, свойства, константы, поля конфиг-типов) и смены
видимости существующих имён (в обе стороны). Каждое такое имя — отдельный `Candidate`: дефолт
имплементации — internal (`rules/python/main.md`), публичность — контракт, который вводится
только решением мейнтейнера. Лакмус: «кто сломается, если завтра переименуем?» — только пакет
и его тесты → должно быть internal; потребители библиотеки → Boundary-предложение мейнтейнеру.
Для кандидатов класса Б гейты 2.2 проходятся в вырожденной форме: П1 — роль имени (контракт
фичи или машинерия реализации?); П2 — `connascence_form: none`; П3 — рёбра пустые; П5/П6 —
по существу (чей контекст, что стоит поддержка имени навсегда).

### 2.2 На КАЖДОГО кандидата — письменные гейты П1→П6 базового свода

Для каждого `Candidate` зафиксировать письменный ответ на все шесть гейтов `DPF-COUPLING-GENERALIZATION`
§4, в этом порядке (гейты обязаны быть explicit, не подразумеваемы):

1. **П1 роль** — одна роль (контракт) или разные? Обоснование, не «выглядит похоже».
2. **П2 сила связи** — форма connascence: `name` / `type` / `meaning` / `position` / `algorithm`
   (или `none`, если после П1 обобщать нечего).
3. **П3 граф до/после** — явный список рёбер (кто на кого ссылается) до и после предполагаемой
   правки; какие рёбра исчезают.
4. **П4 Stable Dependencies** — стал ли новый общий узел стабильнее источников; для этого проекта
   проверяется через `tests/test_architecture.py` (subtree-isolation инварианты, `Ce` от `core`
   к `backends` = 0) — сослаться на конкретный инвариант/тест, не на «выглядит стабильно».
5. **П5 bounded context** — один контекст (`backends/{faststream,kombu}` — один домен, решение
   владельца зафиксировано в `DPF-COUPLING-GENERALIZATION/DPF.md` §4 Паттерн 5) или граница
   пересекается по-настоящему.
6. **П6 рентабельность** — прогнозный вход помечен явно как гипотеза (не факт) + названа
   митигация отката, если гипотеза не оправдается.

Гейт, не пройденный письменно (пропущенный шаг 1–6), делает кандидата незакрытым — не переходит
к шагу 2.3.

### 2.3 Маршрутизация и оформление по П1–П6 этой LPF

После прохождения П1–П6 базового свода — применить процедуру этой LPF к результату:

- **Маршрут (П1 LPF):** Boundary-поверхность (публичный экспортируемый символ, сигнатура
  конструктора, on-wire формат) → **must-meet** knockout → эскалация мейнтейнеру. Local/Module
  → **should-meet** суждение → решает оркестратор на месте, без эскалации.
- **Формат (П2 LPF):** письменный прозаический ответ с явной ссылкой на FPF-guard (A.11/A.7/A.1.1),
  без численного скорингового поля и без балльного чек-листа.
- **Scope-bounding (П3 LPF):** in-scope правка — только файлы, уже присутствующие в текущем диффе.
  Генерализуемый повтор вне диффа — `deferred-note`, не немедленное действие. Объём/batch-size
  диффа никогда не основание для отказа стадии.
- **Пустой список (П4 LPF):** финальный `findings: []` валиден ТОЛЬКО вместе с N письменными
  по-кандидатными вердиктами (N = число просмотренных кандидатов) — отсутствие вердикта по
  кандидату означает «не рассмотрен», не «закрыт».
- **Автомат/LLM-сигнал (П5 LPF):** флаг автодетектора или собственный скан LLM-исполнителя —
  всегда `Candidate`, никогда сразу `Finding`. Если эту стадию исполняет LLM-агент (а не человек
  напрямую) — каждая находка уровня Boundary получает `pending_human_confirmation: true` в выходе;
  находки Local/Module не блокируются этим полем, но подлежат утверждению оркестратором.
- **Гейт ширины контракта (П6 LPF):** каждый кандидат класса Б (новое публичное имя, шаг 2.1)
  оформляется отдельной находкой `route: maintainer` с `pending_human_confirmation: true` — ДАЖЕ
  если reviewer рекомендует оставить имя публичным (рекомендация — в тексте вердикта). Имя,
  которое фича прямо обещает наружу и которое уже подтверждено владельцем (см. публичный контракт
  в плане/доках), кандидатом не является — контрпример П6. Публикация ранее приватного имени ради
  внутреннего call-site — всегда находка (worked slice: инцидент 2026-07-14, `9fa714c`).

## Шаг 3 — главная цель и симметричный риск

Главная цель этой стадии — ошибка №8 базового свода (недо-обобщение: «отказ обобщать на всякий
случай» → накопление синхронных дублей, association-дублирование выдаётся за осторожность).
Искать её активно, не ждать пока она станет очевидной.

Одновременно НЕ впадать в симметричные ошибки того же каталога:

- **№11** — признание рекомендованного обобщения верным только потому что GREEN прошёл (GREEN не
  доказывает корректность обобщения — это следующая стадия, код-ревью).
- **№12** — гиперреакция на AI-era сдвиг baseline клонов: «всегда обобщать» пере-обобщает
  разные роли под одну абстракцию.

Держать оба риска (№8 против №11/№12) в явном балансе на каждом кандидате, не разрешать один
за счёт другого молча.

## Шаг 4 — «минимальные правки» не довод против обобщения

`existing-code.md` / code-change-discipline требует предпочитать точечную правку («add only what
you cannot subtract»). На ЭТОЙ стадии сам факт «предложенное обобщение — не минимальная правка»
**не является самостоятельным доводом против** генерализации. Единственные легитимные доводы
против decision=generalize:

1. граф связей (П3) **не убывает** — `edges_after` не короче `edges_before` по числу рёбер,
   обязанных меняться синхронно; или
2. рентабельность (П6) **отрицательна** — гипотеза не окупает стоимость правки при названном
   пути отката.

Любой другой довод («но это лишние строки», «код и так работает», «дифф станет больше») не
блокирует decision=generalize сам по себе — это ожидаемая, не бесплатная, цена (Форс «Boy Scout
vs batch-size» этой LPF, scope-bounding шага 2.3 её ограничивает, не отменяет).

## Шаг 5 — выход строго по finding-schema.json

Результат стадии — единственный JSON-документ, валидный по `assets/finding-schema.json` этого
пакета (draft-07, `additionalProperties: false`). Каждый элемент `candidates` заполняет все
required-поля схемы (пустого/частичного вердикта по кандидату схема не допускает). Top-level
`findings` — индексы/ссылки на кандидатов из `candidates` с `decision: "generalize"`. `summary` —
короткое прозаическое резюме прогона стадии (число кандидатов, число findings, есть ли
`pending_human_confirmation: true`).
