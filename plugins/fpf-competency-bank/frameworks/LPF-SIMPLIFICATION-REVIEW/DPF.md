Эта LPF **специализирует** его гейты в процедуру одной стадии конвейера — не переопределяет coupling/connascence/SDP/bounded-context.

> **Структурный отчёт носителя (CC-DPF.8):** файл для роли **reviewer стадии «Упрощение»** конвейера 4.0 библиотеки `esb-tools` (между GREEN-фазой и код-ревью на корректность; роль может совмещаться architect+dev), и для **оркестратора** конвейера, решающего, требует ли находка эскалации мейнтейнеру. ## 3. Forces — тензии (scoped, E.4.DPF:3)

| Force | Тензия | Scope |
|---|---|---|
| Should-meet vs must-meet | «Улучшает health» (T10) — взвешенное суждение; публичный контракт требует бинарного knockout (T14/T15) — два разных режима гейта на разных уровнях Blast Radius, не оттенок одного | design-time, маршрутизация находки (§4 П1) |
| Письменный ответ vs воспроизводимость числа | Отказ от чек-листа/дефект-плотности (T11, решение мейнтейнера) даёт lightweight-эффективность, но теряет числовую аудируемость формальной инспекции — принятая, не бесплатная потеря | формат Finding (§4 П2) |
| Boy Scout vs batch-size | «Чини по ходу» (T12) увеличивает объём диффа → снижает эффективность downstream-ревью на стадии, чувствительной к AI-driven росту batch (T13) — оппортунизм и малый батч в натяжении | scope-bounding одной находки (§4 П3) |
| Пустой список vs rubber-stamp | Высокий FP-baseline автодетекторов (T17) делает «0 находок» ожидаемым исходом; alert fatigue (T16, до ~40% алертов игнорируется) даёт СИММЕТРИЧНЫЙ риск — reviewer закрывает всё не глядя, прикрываясь валидностью пустого списка | терминальный исход стадии (§4 П4) |
| Детализация гейта vs LLM-исполнитель | Формат «письменный ответ на каждый гейт П1→П6» детален по построению; T16 контринтуитивно показывает, что детальный промпт ПОВЫШАЕТ misjudgment LLM-ревьюера — формат, полезный человеку, может вредить автомату | исполнитель стадии — человек vs LLM-агент (§4 П5) |

## 4. Паттерны — E.8 (CC-DPF.6)

> Порядок — от «кто решает» к «как оформлено» к «что делать с сигналом от автомата» (не переоткрывает П1–П6 базового ДПФ: там — критерий обобщения, здесь — процедура ревью одной стадии). Каждый паттерн: Recognition → Принцип (SoTA) → наша инстанциация → контрпример → анти-паттерн → conformance → связи.

### Паттерн 1: Маршрут по поверхности контракта — must-meet (Boundary → мейнтейнер) vs should-meet (Local/Module → оркестратор)

- **Recognition:** П1–П3 базового ДПФ пройдены для кандидата (роль одна, связь классифицирована, граф до/после посчитан) — нужно решить, кто принимает финальное решение по находке.
- **Принцип (SoTA):** must-meet-критерии — бинарные knockout-вопросы, провал которых останавливает решение; should-meet — взвешенные суждения, ранжирующие выживших (T14, Cooper Stage-Gate); маршрутизация решения идёт по типу затронутой поверхности, не по расположению файла (T15, CODEOWNERS-механизм — публичный API «дрейфует не туда, когда владение подразумевается, а не явно»); «улучшает code health, не идеально» (T10) — легитимный стандарт ТОЛЬКО там, где решение взвешенное.
- **Наша инстанциация (worked slice, git-evidence):** коммит `0e6117b` («decode в core и композиция вместо кооперативного ромба middleware») добавил параметр `esb_middlewares` (аннотация `Sequence[Callable[[ESBContext], MiddlewareCM]] = ()`; в faststream-модулях менеджеров — тот же тип через алиас `t.Sequence`) в публичные конструкторы менеджеров и фабрики **обоих** бэкендов: kombu — `bootstrap.py:60` (фабрика `create_esb_service`), `event_in.py`, `request_in.py`, `request_out.py`; faststream — `service.py:254` (фабрика), `event_in.py:48`, `request_in.py:54`, `request_out.py:60`. Воспроизводимо: `grep -rn "esb_middlewares:" esb_tools/backends/` покрывает обе подветки (номера строк — рабочее дерево на 2026-07-13); точный вариант с `t.Sequence` матчит только faststream-менеджеры — kombu импортирует `Sequence` напрямую, история этой невоспроизводимой цитаты — `references/quality-record-2026-07-13.md`. Это сигнатура конструкторов, которые потребитель библиотеки вызывает напрямую при сборке сервиса — Boundary по `existing-code.md` (публичная поверхность пакета). Reviewer стадии «Упрощение» письменно отвечает: «да, это Boundary — новый параметр публичного конструктора на обоих бэкендах» → must-meet → эскалация мейнтейнеру (в данном прогоне owner и мейнтейнер совпадают, но решение зафиксировано явно в теле коммита: «единый контракт пользовательских middleware... (параметр esb_middlewares у менеджеров) + кросс-бэкенд контракт-тест» — не тихая протечка, осознанное решение о публичном контракте, подкреплённое `tests/test_cross_backend_middleware_contract.py`).
- **Контрпример [A.11]:** локальный `extract-method` внутри одного модуля (КП-5, `theses-antitheses.md`) — прогонять бинарный must-meet knockout здесь избыточно; Local/Module-уровень решает should-meet суждением оркестратора без эскалации.
- **Анти-паттерн [E.8]:** авто-одобрение изменения публичного контракта доводом «в целом стало чище» (T10) без прогона must-meet — смешаны should-meet (health) и must-meet (Boundary) режимы (ошибка №3, каталог); симметрично — блокировка Local/Module-находки в ожидании «идеальной абстракции», когда T10 прямо разрешает одобрять, как только «определённо улучшает» (ошибка №4).
- **Conformance:** решение сопровождается явным письменным ответом на вопрос «это Boundary-поверхность (публичный экспортируемый символ, сигнатура конструктора, on-wire формат) или нет?» — до применения should-meet рассуждения.
- **Связи:** `require`/`sequence` — применяется ПОСЛЕ П1–П3 базового ДПФ, не вместо них; питает Паттерн 2 (в каком формате оформляется written-ответ маршрутизации); `scope-dependent` с Паттерном 5 базового ДПФ (bounded-context guard задаёт, что вообще считается «поверхностью» этого проекта).

### Паттерн 2: Письменный ответ на гейт — не чек-лист и не число

- **Recognition:** reviewer должен зафиксировать результат прохождения гейтов по кандидату (принят / отклонён / эскалирован).
- **Принцип (SoTA):** lightweight-ревью тратит <20% времени формального инспекционного протокола и находит столько же дефектов (T11, Cohen/SmartBear, эмпирика Cisco); «smallness» диффа — про концептуальную идею, не про механический счётчик строк (T10 Claim 3, вторичный пересказ — используется только как принцип, не как число, `source-pack.md` открытый provenance-вопрос).
- **Наша инстанциация (worked slice):** формат `Finding` этой LPF (`sota-research.md` §5 Operator/Object inventory) — граф рёбер до/после + форма connascence + FPF-обоснование (ссылка на A.11/A.7/A.1.1 базового ДПФ) + рентабельность-как-гипотеза + путь отката — прозаический ответ, БЕЗ числового поля дефект-плотности или балльного чек-листа. Для коммита `0e6117b` таким письменным ответом было бы: «роль одна (единый контракт middleware на обоих бэкендах, П1 базового ДПФ), связь — Boundary (Паттерн 1 выше), граф сократился (дублирующиеся ad-hoc обёртки middleware на каждом бэкенде заменены одним контрактом `Callable[[ESBContext], CM]`, подтверждено `tests/test_cross_backend_middleware_contract.py`), рентабельность — ставка на то, что оба бэкенда и далее будут нуждаться в едином контракте (гипотеза, не факт), откат — Module-уровень, старый способ конструирования обёрток можно восстановить без разрушения публичного API» — не число.
- **Контрпример [A.11] (КП-2):** механический `rename` одного символа через `backends/faststream` и `backends/kombu` — 600 строк diff, но концептуально одна правка (connascence of name, единая идея); LOC-порог здесь не применяется как veto — раздельный подсчёт строк не заменяет суждение о концептуальном размере.
- **Анти-паттерн [E.8]:** reviewer выдаёт числовую дефект-плотность или балльный чек-лист 10–20 пунктов вместо прозаического ответа — импорт формата формальной инспекции, отвергнутого мейнтейнером (ошибка №1–2, каталог); симметрично — жёсткое правило «>400 строк → reject» применённое к диффу, где объём весь концептуально однороден.
- **Conformance:** каждая находка — законченное предложение с явной ссылкой на FPF-guard (A.11/A.7/A.1.1) и без численного скорингового поля; проверка «можно ли это число посчитать конвейером автоматически» — если да, это не Finding этой LPF, это отдельный CI-гейт.
- **Связи:** `composition` с Паттерном 1 (маршрут — какой ответ куда идёт) и Паттерном 4 (пустой список — тот же формат, применённый к нулевому результату); `conflict` со слепым переносом T11 LOC-чисел (Forces §3).

### Паттерн 3: Scope-bounding находки — in-scope только в файлах текущего диффа, иначе deferred-note

- **Recognition:** reviewer, разбирая дифф фазы, замечает генерализуемый повтор.
- **Принцип (SoTA):** оставляй код лучше, чем нашёл, чини «прямо здесь или в течение нескольких минут» (T12, Fowler Opportunistic Refactoring) — НО (внутренняя тензия той же традиции, community-практика) «resist the urge to while-I'm-here», выноси крупный рефакторинг в отдельный коммит; на стадии, чувствительной к росту batch size при AI-адопции (T13, DORA: throughput −1.5%, stability −7.2%, второй год подряд), оппортунистическое раздувание диффа прямо противоречит цели стадии.

### Паттерн 5: Автомат/LLM-сигнал — кандидат, не вердикт; детальный гейт-промпт не гарантия качества

- **Recognition:** источником кандидата на обобщение выступает автоматический детектор (jscpd/CPD-стиль) или LLM-под-агент, исполняющий часть/всю стадию.
- **Принцип (SoTA):** токен-детекторы структурно не могут отличить одинаковый «shape» от одинаковой «role» (T17 Claim 3, задокументированное архитектурное ограничение CPD, воспроизводимо на публичных примерах) — это прямая иллюстрация П1/П2 базового ДПФ применительно к инструменту, не новый принцип (guardian-концерн 1: не переоткрывать role-first здесь, только иллюстрировать); LLM-ревьюеры систематически ошибочно классифицируют корректный код как дефектный, причём ДЕТАЛЬНЫЙ промпт (с объяснениями/правками — то есть формат этой самой LPF) ПОВЫШАЕТ долю ошибок (T16 Claim 1, Springer ASE 2026, контринтуитивно); мульти-агентный рефактор часто переобучается на тест-кейсы диффа (T16 Claim 2, SWE-Refactor) — GREEN не доказывает корректность рекомендованного обобщения.
- **Наша инстанциация:** для кандидата из КП-6 выше (`event_in.py`/`request_in.py`) автоматический флаг регистрируется как `Candidate`, не как `Finding` — human-in-the-loop (или отдельный человеческий пере-прогон, если стадию исполнял LLM-агент) обязан явно ответить на П1 базового ДПФ («одна роль?») ПЕРЕД тем, как флаг попадёт в findings-список в любом виде (в т.ч. как «закрыто»). Если исполнитель стадии — LLM-агент, П1–П6 этого файла (детальный письменный формат) исполняются им как ПЕРВЫЙ проход, но помечаются `pending human confirmation` для находок уровня Boundary (Паттерн 1) — не как финальный вердикт; для находок Local/Module — оркестратор (человек) утверждает should-meet суждение перед принятием.
- **Контрпример [A.11]:** человек-reviewer, лично читающий дифф и применяющий П1 базового ДПФ напрямую (без автоматического пре-скана) — этот паттерн неприменим, риск hyper-correction относится к автомат/LLM-исполнителю, не к прямому суждению человека.
- **Анти-паттерн [E.8]:** доверие флагу jscpd/CPD «дубликат» как готовой находке без проверки роли (ошибка №9, каталог); наращивание детализации гейт-промпта LLM-ревьюера в надежде улучшить точность — T16 показывает обратный эффект (ошибка №10); признание рекомендованного обобщения валидным, «раз GREEN прошёл» (ошибка №11); перенос числовых порогов AI-false-positive (5–15%, 40%) как норматива вместо иллюстрации проблемы (ошибка №12).

- **Связи:** `require` П1/П2/П3 базового ДПФ (роль/сила/граф — неотрекрываемая база); `conflict` (scoped) с Паттерном 2 при LLM-исполнителе (детальный письменный формат может повышать misjudgment — Forces §3); `scope-dependent` — активируется только когда исполнитель/под-инструмент автоматизирован.

- **Recognition:** дифф фазы вводит новые имена без ведущего подчёркивания (функции, методы, свойства, константы, поля конфиг-типов) либо расширяет сигнатуры существующих публичных функций — независимо от того, было ли это целью фазы.

## 10. Разнородные приёмочные случаи (E.4.DPF §10, D8)

> Мотивирующие примеры уже инстанциированы в §4: коммит `0e6117b` (П1, эскалация Boundary), коммит `c0b62cb` (П3, in-scope scope-bounding), пара `event_in.py`/`request_in.py` (П4/П5, автомат-флаг закрыт по роли). Ниже — 3 непохожих кейса, заставляющих паттерны работать за пределами этих примеров.

**Случай A — сильная connascence of algorithm внутри тест-кода, закрыта границей DAMP>DRY (`tests/test_architecture.py`, коммит `cc8f191`).** Пять функций `test_invariant_a`…`test_invariant_e` имеют идентичную механическую форму (список-фильтр по предикату → `assert not violations` → форматированное сообщение через общий `_format_violations`) — сильный сигнал connascence of algorithm по П2 базового ДПФ, ровно того рода, что обычно оправдывает централизацию (§4 Паттерн 2 базового ДПФ). Reviewer стадии, пройдя П1 базового ДПФ, фиксирует: роль каждой функции РАЗНАЯ (проверяет свой инвариант а/б/в/г/д конвенции импортов), общая только report-and-fail механика; применяет контрпример КП-8 базового ДПФ (тест-код — граница DAMP>DRY) и закрывает кандидата письменным вердиктом, не обобщением. Это — реальная инстанциация Паттерна 4 этой LPF (пустой список с вердиктом), не гипотетическая: находка рассмотрена и закрыта с конкретным основанием, а не пропущена. Показывает: сильный сигнал connascence сам по себе не отменяет применимость контрпримеров/границ базового ДПФ — Паттерн 4 требует письменного прохождения гейтов ДАЖЕ когда механический сигнал силён.

**Случай B — исполнитель стадии как переменная: LLM-агент вместо человека (адаптация T16, не evidence этого репозитория).** Стадия «Упрощение» этого конвейера в других прогонах может исполняться LLM-агентом (как эта самая DPF-сборка исполняется LLM-агентом сейчас — self-application). По Паттерну 5: если гейт-формат П1→П6 базового ДПФ + П1–П6 этой LPF применяется LLM-исполнителем в его максимально детальной письменной форме — по T16 Claim 1 это КОНТРИНТУИТИВНО повышает риск гипер-коррекции (флагования корректного кода как дефектного), а не снижает его. Явно НЕ evidence из истории `esb-tools` — телеметрии LLM-исполненных прогонов этой конкретной LPF ещё не существует (стадия только собрана этим прогоном) — перенесённая SoTA-иллюстрация, помеченная как таковая (A.10, не повышена до факта). Показывает: Паттерн 5 должен различать исполнителя ДО применения детального письменного формата — тот же формат, полезный человеку (П2), становится риском для LLM-агента без дополнительного `pending human confirmation`-шага на Boundary-находках.

**Случай C — большой батч-мердж не подлежит отклонению стадией по объёму (`c1ec9b8`, «feat: new topology and tests and merge master», 51 файл, +2733/−517, merge-коммит).** Если бы этот дифф был подан на стадию «Упрощение» этого конвейера как единица работы, наивное применение T11 LOC-порога («>400 строк → reject») заблокировало бы его целиком. По Паттерну 3 (контрпример КП-4 §4): объём — результат MERGE двух веток (топология + master), т.е. upstream-решение оркестрации, а не решение, которое reviewer стадии одного диффа фазы способен или обязан оспорить по объёму. Показывает: Паттерн 3 работает и на диффах, которые НЕ являются результатом одной фазы конвейера в узком смысле (merge, а не sequential-фаза) — граница «что вообще является единицей ревью этой стадии» шире одного commit-per-phase сценария из §1 First use, и Паттерн 3 обязан её держать без модификации.
