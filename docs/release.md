# Релиз

Эта страница для участника, который выпускает изменения маркетплейса. Перед
выпуском пройдите всю процедуру: незавершённый либо неуспешный обязательный шаг
останавливает выпуск.

## Версия плагина

Версия в `.claude-plugin/plugin.json` считается относительно последнего общего
релизного тега `vX.Y.Z`, а не относительно предыдущей правки. Версию поднимают
один раз при выпуске — на наибольший применимый шаг Semantic Versioning для
всех накопленных с последнего релиза изменений.

- `MAJOR` означает нарушение совместимости: удалены или переименованы команды
  либо агенты, изменён формат.
- `MINOR` означает новую функциональность: добавлены команды, агенты или
  скиллы.
- `PATCH` означает исправления, опечатки и уточнения промптов.

У плагина, созданного после последнего тега, ещё не было выпуска. До его первого
релиза промежуточные изменения не требуют отдельного повышения версии.

## Порядок выпуска

1. Внесите изменения в затронутые плагины и создавайте рабочие коммиты без
   повышения версии после каждой правки.
2. Перед выпуском определите наибольший применимый шаг Semantic Versioning
   относительно версии плагина в последнем теге и поднимите версию один раз.
3. Выполните локальные тесты и строгую проверку каждого затронутого плагина:

   ```bash
   claude plugin validate <путь-к-плагину> --strict
   ```

   Для каждого затронутого плагина, в котором есть `evals/run.py`, обязателен
   полный успешный запуск этого файла на выпускаемом содержимом. Для `planner`:

   ```bash
   python3 plugins/planner/evals/run.py
   ```

   Частичный прогон, достигнутый предел стоимости, пропущенный кейс или
   результат ниже установленного порога не считаются успехом. Порог строгий:
   три успешных повтора каждого кейса из трёх. Понижать порог вместо
   исправления поведения запрещено.
4. Обновите отчёт каждого затронутого плагина в `docs/reports/` фактическими
   данными свежего `aggregate-result.json`. Подробный порядок запуска проверок
   и обновления отчётов описан в [инструкции проверки](testing/running.md).
5. На машине, где выполнен прогон, сверьте отчёт с его последним результатом:

   ```bash
   python3 scripts/check_report_numbers.py <плагин>
   ```

   Выпуск продолжается только при коде выхода `0`. Код `1` означает
   расхождение либо ошибку разбора, код `2` — отсутствие результата для
   сверки; оба исхода блокируют выпуск. В чистой копии CI результаты прогона
   игнорируются Git, поэтому там эта сверка не выполняется.
6. Создайте релизный коммит без тега и отправьте его:

   ```bash
   git push
   ```

7. Дождитесь успешного GitHub Actions workflow на точном SHA релизного
   коммита. Перед созданием тега рабочее дерево должно быть чистым, а локальная
   ветка — совпадать с отправленным коммитом.
8. Создайте и отправьте общий тег:

   ```bash
   git tag vX.Y.Z
   git push --tags
   ```
