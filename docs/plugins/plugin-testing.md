# plugin-testing: проверка поведения плагинов

## Что это

Один скилл, семь справочников и утилита. Скилл срабатывает на просьбы вида
«написать тесты для плагина», «добавить eval-кейс», «прогнать plugin eval»,
«разобрать красный прогон», «проверить, что скилл срабатывает», «настроить
релизный гейт».

| Справочник | О чём |
|---|---|
| `validate` | структурная проверка и её измеренные границы |
| `graders` | шесть видов критериев и их ловушки |
| `wrapper` | обёртка прогона: почему нулевого кода выхода недостаточно |
| `failures` | разбор красного прогона по порядку |
| `deterministic-routing` | когда формулировки не спасают и нужен хук |
| `early-access` | природа гейта раннего доступа |
| `report` | что обязан содержать отчёт о прогоне |

Утилита `check_eval_suite.py` находит пустые проверки — те, что проходят всегда:
кейс без критериев, неизвестный вид критерия, `max: 0` без `min: 0`, запрет
инструмента, который кейсу и не выдавали, дублирующееся имя критерия. Коды
выхода `0`, `1`, `64`.

## Для чего это

Структурная проверка отвечает, загрузится ли плагин. Она никогда не заметит, что
скилл не срабатывает ни на одном живом запросе — а это самый частый дефект
плагина: содержание правильное, но модель до него не доходит.

Второе назначение — не дать зелёному прогону значить меньше, чем кажется. Прямой
вызов `claude plugin eval` легко запустить без нужного инструмента, принять
частичный результат или прочитать старый файл результата как свежий. Поэтому
проверка идёт через обёртку, которая читает агрегат и требует ровно ожидаемые
кейсы, ровно нужное число повторов, отсутствие пропущенных критериев и признак
`partial: false`.

## Как пользоваться

```bash
# Найти проверки, которые проходят всегда
python3 "${CLAUDE_PLUGIN_ROOT}/skills/plugin-testing/scripts/check_eval_suite.py" plugins/<плагин>/evals

# Полный прогон через обёртку плагина (пример: planner)
python3 plugins/planner/evals/run.py
```

Порядок работы, разбор отказов и обновление отчётов — в общем разделе
[Проверка плагинов](../testing/index.md). Наблюдённые прогоны — в
[отчётах](../reports/index.md).

## Когда НЕ пользоваться

- **Проверка структуры.** Для этого есть `claude plugin validate --strict`, он
  бесплатный и детерминированный. Поведенческий прогон здесь избыточен.
- **Проверка смысла промпта поиском слов.** Тест, ищущий фразу в тексте скилла,
  проходит и на бессмысленном тексте с теми же словами. Смысл проверяется
  чтением и поведенческими примерами.
- **Прогон в CI на каждый коммит.** Проверка платная и требует включённого
  раннего доступа. Её место — локальный гейт перед выпуском.
- **Плагин без обещанного поведения.** Справочный плагин достаточно покрыть
  тестами его скриптов; см. [решение 5](../decisions.md).

## Чего у самого плагина нет

Своего eval-набора у `plugin-testing` нет — по критерию из
[решения 5](../decisions.md): он поставляет методику и утилиту, а не обещание
поведения модели. Утилита покрыта девятью автоматическими тестами.
