# sdlc

Помогает провести изменение через полный цикл разработки — от архитектуры до
реализации и ревью.

## Основные возможности

- Разделяет проектирование, реализацию и ревью между отдельными ролями, чтобы
  решения, код и проверка не смешивались в одной работе.
- Передаёт результат каждого этапа следующему в понятном формате, сохраняя
  контекст и причины решений.
- Учитывает стек проекта: Python, React и проектирование API получают свои
  рекомендации и проверки.
- Закладывает безопасность в каждое ревью, а тесты и линтеры — в каждый цикл
  реализации.

## Состав

Три роли разработки — проектирование, реализация, ревью. Каждая поставляется
парой: агент, которого вызывают, и скилл с методом этой роли.

| Роль | Модель | Что ведёт |
|---|---|---|
| `architect` | opus | ограниченные контексты, договоры передачи, поток данных, точки интеграции, открытые вопросы |
| `code-implementer` | sonnet | реализацию по готовому документу через цикл тестов; запускает весь набор тестов и линтеры |
| `code-reviewer` | sonnet | безопасность, принципы ясности, стековые ловушки; замечания со ссылкой `файл:строка` |

Команд, хуков и workflow у плагина нет: порядок вызова задаёт человек или
оркестратор.

## Как пользоваться

### Передача между ролями

```text
требования → architect → code-implementer → code-reviewer
```

- Тесты и линтеры запускает `code-implementer` и отчитывается точными командами
  с наблюдённым итогом.
- `code-reviewer` сам код не запускает: находку, требующую запуска, он помечает
  непроверенной и называет команду для реализующей роли. Отчёт реализации ему
  передаёт `/plan-do`.
- Дефект реализации возвращает работу реализующей роли. Замечание к
  проектированию оркестратор показывает человеку и останавливает выполнение до
  следующей рабочей фазы. Архитектор сам не вызывается; если человек меняет
  архитектуру, гейт свежести требует пересобрать план выполнения.

### Артефакты

```text
<каталог фичи>/ARCH-NN.md                           architect, когда путь не назначен иначе
<каталог фичи>/IMPLEMENTATION-NN.md                 code-implementer, один файл на реализацию или круг правок
<каталог фичи>/review-request-changes/REVIEW-NN.md  code-reviewer, один файл на раунд
```

Путь архитектурного документа архитектор берёт по порядку: сначала названный
оркестратором (в конвейере planner — `ARCHITECTURE.md` из шапки
`PLANNER_EXECUTION.md`), затем соглашение проекта из `planner-context.md`, затем
`ARCH-NN.md`. Существующий документ обновляется на месте.

Имя и нумерацию `IMPLEMENTATION-NN.md` держит `/plan-do`: он резервирует путь и
передаёт его роли, а та пишет по переданному пути.

Полный отчёт уходит в файл, когда вызывающая сторона передала и точный путь, и
форму компактной сводки. Без любого из двух входов роль выводит полный отчёт в
чат, даже если каталог фичи существует.

### Стековые справочники

| Роль | По стеку | Вне стека |
|---|---|---|
| `architect` | Python, React, дизайн API | договоры проектирования |
| `code-implementer` | Python, React | — |
| `code-reviewer` | Python, React | безопасность (OWASP), договоры ревью |

Скиллы читают эти справочники по надобности. Особый случай один: скилл ревьюера
велит загружать `references/security.md` первым и при любом стеке и держать
раздел `## Security` в отчёте даже при нуле находок — «no security issues found
in scope». Держится это текстом скилла.

Признак стека роли определяют двумя способами. Архитектор и реализатор смотрят
на корень проекта: `pyproject.toml`, `requirements.txt` или `*.py` в корне дают
Python, `package.json` с `react`, `next`, `vue` или `svelte` — фронтенд, Python
проверяется первым. Ревьюер смотрит расширения изменённых файлов в дифе: `*.py`
даёт Python, а `*.tsx`, `*.jsx`, `*.ts`, `*.vue`, `*.svelte` — фронтенд.
Поверхность API добавляет справочник по дизайну API у архитектора. Смешанный
стек берёт оба справочника у всех трёх ролей, а «сначала бэкенд» — порядок
реализации, не порядок чтения справочников. На неизвестном стеке остаются
универсальные принципы, отказа нет.

Тексты справочников поставляются вместе со скиллами ролей и лежат в
`plugins/sdlc/skills/<роль>/references/`; страница называет только их назначение.

### Зависимости

Плагин объявляет `tdd-master` и `functional-clarity` полем `dependencies` в
манифесте, и установка подтягивает их сама — см.
[связи между плагинами](relations.md). Тексты скиллов описывают и работу без
них: без `tdd-master` цикл тестов ведётся общими средствами, и ослабление нужно
отметить в отчёте; без `functional-clarity` принципы применяются по памяти.

Соскилл `document-skills:frontend-design`, который называют все три роли, под
этим именем не разрешается: в официальном маркетплейсе `frontend-design` —
отдельный плагин, а `document-skills` даёт `xlsx`, `docx`, `pptx` и `pdf`. Пока
имя не исправлено в скиллах, визуальное качество фронтенда роли разбирают на
универсальных принципах; дизайн-систему архитектор всё равно называет в
документе.

## Границы

Одна граница закрыта списком инструментов агента: `architect` не запускает тесты
и никакие другие команды, `Bash` ему не выдан.

Остальные держатся текстом агента и скилла:

- Цикл сам не запускается: у плагина нет ни команд, ни хуков.
- Ради однострочной правки роли не зовут: три передачи между ролями стоят
  дороже, чем правка. Роли берут, когда у изменения есть контракт, граница или
  поверхность безопасности.
- `architect` работает только по готовым требованиям фичи и сам их не собирает:
  без README или PLAN скилл предписывает остановиться с отказом.
- `architect` не пишет код, тесты и миграции: `Write` разрешён ему только на
  архитектурный документ фичи.
- `code-implementer` не проектирует и не проводит ревью.
- `code-reviewer` не правит код, не пишет тесты и не запускает набор тестов: он
  ставит диагноз, правки делает реализующая роль. Точечной правки у него нет,
  `Edit` не выдан; но `Write` и `Bash` есть, и от записи в исходники и от команд
  `git` его держит текст скилла, а не среда.
