# sdlc: проектирование, реализация, ревью

## Что это

Три агента с разными полномочиями и три скилла за ними. Ни команд, ни хуков
плагин не поставляет: порядок вызова задаёт человек или оркестратор.

### architect — только проектирование

**Делает:** читает требования среза, выделяет ограниченные контексты и их
владельцев, задаёт договоры передачи, поток данных, точки интеграции. Фиксирует
решения, что вне объёма и открытые вопросы. Пишет архитектурный документ.

**Не делает:** не пишет продуктовый код, тесты, миграции и конфигурацию, не
запускает тесты, не выбирает новый стек по вкусу. Вопрос, требующий разведки, не
решает — назначает разведку реализующей роли.

Модель: `opus`. Проектирование — самый дорогой по последствиям шаг.

### code-implementer — только реализация

**Делает:** требует готовый документ с явным объёмом. До продуктового кода
активирует `tdd-master`, проходит цикл красный–зелёный–рефакторинг, применяет
минимальные изменения и fail-fast. После зелёного набора запускает весь набор
тестов и линтеры и отчитывается точными командами с их итогом. Для затронутых
поверхностей собирает подтверждения вне модульных тестов: запуск, независимое
подтверждение записи, проверку фактического формата обмена.

**Не делает:** не придумывает архитектуру, когда документа нет или он
противоречив; не меняет договоры молча; не рефакторит соседний код «заодно»; не
проводит ревью.

Модель: `sonnet`.

### code-reviewer — только ревью

**Делает:** работает по конкретному дифу. Сначала обязательный проход по
безопасности, затем принципы ясности и стековые ловушки. Каждое существенное
замечание подкрепляет ссылкой `файл:строка` и наблюдаемым основанием. Отделяет
дефект реализации от замечания к проектированию.

**Не делает:** не исправляет код, не пишет недостающие тесты, не запускает набор
тестов, не проектирует, не выдаёт вкусовые предпочтения за дефекты. Гипотезы,
требующие запуска, помечает как непроверенные и передаёт реализующей роли.

Модель: `sonnet`.

## Для чего это

Когда одна роль проектирует, пишет и проверяет, она проверяет собственные
решения. Замысел перестаёт быть отделим от реализации, а ревью превращается в
самооправдание — оно подтверждает то, что только что было сделано.

Ценность плагина не в трёх ролях, а в том, что каждая знает границу: что она
делает и чего не делает никогда. Граница видна из промпта роли, поэтому её можно
проверить и на неё можно ссылаться в споре.

## Как пользоваться

Порядок работы:

```text
требования → architect → code-implementer → code-reviewer
                  ↑                              │
                  └── замечание к проектированию ─┘
```

Дефект реализации возвращает работу реализующей роли, затем ревью повторяется.
Замечание к проектированию возвращает работу архитектору — и тогда план
выполнения нужно пересобрать.

Роли вызываются двумя способами. Прямо — обычной репликой («спроектируй»,
«реализуй по документу», «отревью диф»); тогда последовательность держит человек.
Через оркестратор — `/plan-do` из `planner` заполняет свои абстрактные роли
агентами из `.claude/planner-context.md`, и эти три подходят на первые три роли.

### Договор передачи между ролями

Три места, где раньше договоры расходились, и как решено сейчас
([основания](../decisions.md)):

| Вопрос | Решение |
|---|---|
| Кто запускает тесты и линтеры | реализующая роль, с точными командами в отчёте; ревью их не запускает |
| В каком виде выдаются замечания | один отчёт за раунд: `review-request-changes/REVIEW-NN.md` |
| Какой файл правит архитектор | документ, названный в шапке плана выполнения; второй файл рядом не создаётся |

### Стековые справочники

Роли не тащат в контекст всё сразу, а подгружают нужное по признакам стека.

| Роль | Всегда | По стеку |
|---|---|---|
| architect | договоры проектирования | Python, React, дизайн API |
| code-implementer | — | Python, React |
| code-reviewer | безопасность | Python, React |

Правила выбора: маркеры Python → справочник Python; React, Vue или Svelte →
справочник фронтенда; любая поверхность API → справочник API; смешанный стек →
оба стековых справочника; неизвестный стек → универсальные принципы, без отказа.

Смешанный стек реализуется в порядке «сначала бэкенд, потом фронтенд», чтобы
фронтенд строился против фактического договора, а не против ожидаемого.

Проход по безопасности у ревью безусловный: он выполняется всегда и первым, и
раздел о безопасности присутствует в отчёте даже когда находок нет.

### Зависимости

```json
{
  "dependencies": ["tdd-master", "functional-clarity"]
}
```

- `tdd-master` — реализующая роль обязана активировать его до продуктового кода.
  Без плагина допустим цикл общими средствами, но деградацию нужно отметить в
  отчёте явно.
- `functional-clarity` — принципы, на которые опираются все три роли, и
  дисциплина работы с существующим кодом.

При установке `sdlc` обе зависимости ставятся автоматически. Отключить их по
отдельности нельзя, пока `sdlc` включён.

## Когда НЕ пользоваться

- **Правка на несколько строк.** Три передачи между ролями стоят дороже, чем
  сама правка. Роли оправданы там, где есть договор, граница контекста или
  поверхность безопасности.
- **Нет written требований.** Архитектор начинает с готового объёма. Сырой
  замысел сначала идёт в проработку `planner`, иначе роль вернёт вопросы вместо
  документа.
- **Ожидание, что плагин сам проведёт цикл.** У него нет ни команды, ни хука.
  Последовательность держит человек или `/plan-do`.
- **Ожидание, что ревью починит.** Ревью ставит диагноз и не лечит. Правки
  делает реализующая роль — иначе появится второй набор непроверенных изменений.
- **Проект с другим принятым SDLC-контуром.** Два конкурирующих договора хуже
  одного: берите отдельные плагины (тесты, ясность кода), а не весь набор ролей.
