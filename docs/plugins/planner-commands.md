# planner: справочник по командам

Восемь команд. Для каждой — что принимает, что оставляет на диске, какие у неё
состояния и где она останавливается. Общая идея этапов и примеры разговора — на
[странице planner](planner.md).

Четыре продуктовые команды (`/plan-idea`, `/plan-epic`, `/plan-roadmap`,
`/plan-feat`) работают через один общий скилл проработки и различаются видом
документа. У каждой свой справочник режима, свои метаданные и своя проверка
готовности.

## `/plan-idea` — замысел

**Принимает:** свободный текст, путь к существующему `IDEA-NNNN-<slug>.md` или
ничего. Пустой аргумент — разговор начнётся с вопроса об исходной формулировке.

**Оставляет:** `ideas/IDEA-NNNN-<slug>.md`. Один файл, без каталога: у замысла
нет технических приложений. Корень берётся из контекста проекта, по умолчанию
`ideas/`. Номер выдаёт скрипт, на глаз он не выбирается.

**Стадии и исход.** Замысел — единственный вид с явным решением о судьбе:

```text
stage:   exploring | resolved
outcome: open | feature | epic | research | experiment | decision |
         deferred | rejected | duplicate | split
```

| Исход | Когда выбирается | Что дальше |
|---|---|---|
| `open` | тип следующей работы не выбран, критичное неизвестное записано | снова `/plan-idea` по этому файлу |
| `feature` | один результат, один независимо поставляемый срез | `/plan-feat` |
| `epic` | один результат требует нескольких срезов или рубежей | `/plan-epic` |
| `research` | вопрос закрывается имеющимися сведениями, логами, интервью | проверка, затем `/plan-idea` снова |
| `experiment` | нужны новые наблюдения: есть опровергаемое допущение, метрика, порог | проверка, затем `/plan-idea` снова |
| `decision` | выбирается политика или направление, а не поставляемая возможность | команда планировщика не нужна |
| `deferred` | замысел не опровергнут, но сейчас не берём; условие возврата записано | `/plan-idea` при наступлении условия |
| `rejected` | есть достаточное ограниченное основание отказаться | следующего шага нет |
| `duplicate` | канонический объект уже есть, ссылка на него в `target` | работа идёт с объектом по ссылке |
| `split` | вход содержит несколько независимых возможностей | `/plan-idea` на каждый новый замысел |

Связь стадии и исхода проверяет скрипт, и нарушение не записывается:
`exploring` требует `outcome: open` и запрещает `target`; `resolved` запрещает
`open`; для `feature`, `epic` и `duplicate` ссылка `target` обязательна.

**Что важно знать.** Отсутствие подтверждений — не основание для `rejected`.
Если допущения не подтверждены и не опровергнуты, исход — `research`,
`experiment` или `deferred`, а когда решение нельзя принять честно, замысел
остаётся открытым с записанным критичным неизвестным.

**Готовность:** исходная формулировка сохранена дословно с источником; тип
следующей работы выбран или явно оставлен открытым; у каждого утверждения
указаны тип и носитель; оценка подтверждения отражает фактический носитель, а
гипотеза точки зрения не названа отзывом; названы следующий шаг и условие
пересмотра.

## `/plan-epic` — общая гипотеза

**Принимает:** путь к замыслу с исходом `epic`, существующий `EPIC.md` или
сформированный текст.

**Оставляет:** `epics/EPIC-NNNN-<slug>/EPIC.md`. Каталог, а не файл, потому что
рядом будет лежать порядок срезов. Порядок здесь не создаётся.

**Стадии:** `shaping` → `active` → `closed`, плюс `superseded`, когда гипотезу
заменила другая. Новая гипотеза создаётся в `shaping`. Необязательный блок
`origin` хранит ссылку на замысел с его версией и отпечатком — блок появляется
только если гипотеза выросла из замысла.

**Готовность:** один результат, а не набор несвязанных работ; заданы границы и
объём усилий; есть минимум два независимо полезных среза; у открытых вопросов
есть владелец и пометка «блокирует или нет»; гипотеза не выдаётся за
подтверждённую.

Ни стадия, ни ссылка на замысел подтверждением не являются. Формулировки
«подтвердится, если» и «опровергнуто, если» пишутся так, чтобы существовала
проверка, способная их различить.

## `/plan-roadmap` — порядок срезов

**Принимает:** путь к `EPIC.md` или к каталогу гипотезы.

**Оставляет:** `epics/EPIC-NNNN-<slug>/ROADMAP.md` — рядом со своей гипотезой.
Своего номера порядок не получает: имя файла фиксировано. Идентификаторы есть
только у элементов тела, и на них потом ссылается `/plan-feat`.

**Состояния:** `active`, `paused`, `completed`, `cancelled`. Блок `epic`
обязателен: ссылка на гипотезу в том же каталоге с её версией и отпечатком. Один
порядок принадлежит одной гипотезе.

Сырой замысел в порядок работ не попадает: он строится из уже сформированных
срезов.

## `/plan-feat` — требования среза

**Принимает:** описание среза, путь к замыслу с исходом `feature`, путь к
`ROADMAP.md` с идентификатором элемента, путь к существующему срезу или ничего.

**Оставляет:**

```text
features/FEAT-NNNN-<slug>/
  README.md                 # требования среза
  review-request-changes/   # пустой; отчёты ревью появятся здесь позже
```

Каталог среза и пустой каталог для замечаний создаёт скрипт.

**Метаданные:** `readiness` — `draft` (проработка продолжается) или `ready`
(проверка готовности пройдена, срез можно передавать в архитектуру);
необязательный `parent` — ссылка на гипотезу или замысел, из которых срез
вырос. Второго родителя не бывает: цепочку «замысел → гипотеза» восстанавливает
сама гипотеза.

**Что дальше при `readiness: ready`:**

```text
/plan features/FEAT-NNNN-<slug>/README.md          → ARCHITECTURE.md
/plan features/FEAT-NNNN-<slug>/ARCHITECTURE.md    → PLANNER_EXECUTION.md
/plan-do features/FEAT-NNNN-<slug>/                → реализация
```

## `/plan-jira` — описание задачи для Jira

**Принимает:** описание среза. **Оставляет:** текст в чате — файлов не пишет,
инструмента записи у команды нет.

Единственная команда, которая не использует общий скилл проработки: у неё свой
разговор про путь пользователя, крайние случаи, критерии готовности и своя
проверка готовности к работе. Итог — бриф в разметке Jira.

Берите её, когда результат нужен в трекере, а не в репозитории. Если срез должен
дальше пойти в архитектуру, нужен `/plan-feat`: только он оставляет файл, на
который сможет опереться `/plan`.

## `/plan` — архитектура и план выполнения

Одна команда с двумя режимами; режим определяется по входу.

| Вход | Режим | Результат |
|---|---|---|
| `README.md` среза или каталог с ним | архитектура | `ARCHITECTURE.md` рядом с README |
| существующий архитектурный документ | план выполнения | `PLANNER_EXECUTION.md` рядом с ним |
| свободный текст без читаемого пути | архитектура | `.claude/plans/<slug>/ARCHITECTURE.md` |

Путь, который выглядит как путь, но не читается, — ошибка, а не свободный текст.

**Версии и отпечатки.** Новый документ начинается с версии 1. Смысловое
изменение тела повышает версию; переформулировка без смены указаний сохраняет
версию и обновляет отпечаток. План выполнения хранит путь, версию и отпечаток
архитектуры.

**Что происходит с планом при правке архитектуры.** Сразу после записи новой
архитектуры план выполнения помечается устаревшим — тело плана при этом
сохраняется, а не удаляется. Перестроить его нужно той же командой по
архитектуре.

**Границы записи:** контекст проекта при первичном сканировании, архитектура и
план выполнения в каталоге среза, один временный файл `<цель>.prepared` рядом с
целью. Планировщик не исполняет план и не запускает рабочих агентов.

## `/plan-do` — исполнение плана

**Принимает:** каталог среза, README, архитектуру или план выполнения.
Обязателен читаемый `PLANNER_EXECUTION.md`, чья шапка указывает на читаемую
архитектуру.

**Гейт свежести перед каждым вызовом агента:**

```text
0  план актуален — продолжаем
2  план устарел — остановка до перестройки
3  план неверен или нечитаем — остановка
64 неверный вызов помощника — исправить вызов и повторить
```

Проверка повторяется перед каждым следующим вызовом агента: долгая сессия не
должна продолжаться после того, как архитектуру изменили под ней.

**Как распределяется работа.** Команда не знает про конкретные плагины. Она
читает роли из `.claude/planner-context.md` — реализующую, ревьюера, архитектора,
хранителя документации — и вызывает записанных там агентов. Имена агентов не
придумываются.

**Порядок внутри этапа:**

1. реализующая роль получает входы и выходы этапа;
2. в каждый вызов передаётся запрет на идентификатор задачи в коде — он живёт
   только в именах файлов внутри каталога среза;
3. реализующая роль запускает тесты и линтеры и отчитывается точными командами;
   «тесты проходят» без команды и её вывода итогом не считается;
4. ревью получает диф и этот отчёт, набор тестов само не запускает и пишет один
   отчёт за раунд в `review-request-changes/REVIEW-NN.md`;
5. дефект реализации возвращает работу реализующей роли, затем ревью повторяется;
6. замечание к проектированию отправляет работу архитектору — он правит документ,
   названный в шапке плана, после чего `/plan-do` останавливается: план нужно
   перестроить;
7. этап закрывается только при чистом ревью.

Параллельно этапы идут только там, где план помечает их независимыми.

После чистых этапов вызывается хранитель документации — он правит только те пути,
которые перечислены в контексте проекта.

## `/plan-reflect` — уроки в контекст проекта

**Принимает:** каталог среза или ничего (тогда берётся текущая сессия).

**Читает:** план выполнения, коммиты, отчёты ревью, запуски агентов и поправки
человека. **Дописывает:** устойчивые уроки в `.claude/planner-context.md`.

Смысл этапа — чтобы поправка, сделанная руками в этот раз, в следующий раз
попала в план сама. Ручные правки в контексте сохраняются: команда дописывает, а
не перезаписывает.

## Где остановка, а где отказ

| Что случилось | Что делает планировщик |
|---|---|
| нет обязательного поля в черновике поставщика | отклоняет ответ, недостающую часть закрывает ограниченный режим с пометкой |
| поставщик сообщает, что записал файл | отклоняет ответ: писать файлы вправе только скрипт |
| поставщик заявляет исследование пользователей или подтверждение гипотезы | отклоняет ответ как нарушение договора |
| раздел способностей не разбирается | повторяет сканирование контекста проекта, затем повторяет выбор |
| обязательная способность не покрыта | останавливается, подмены закреплённого поставщика нет |
| ошибка записи документа | сообщает путь и ошибку, выводит подготовленное тело в чат как запасной результат |

Ни один из этих случаев не «дозаполняется молча»: остановка называется вместе с
причиной и командой, которой её снимают.
