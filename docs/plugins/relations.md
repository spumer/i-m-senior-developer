# Связи между плагинами

Плагины ставятся независимо, но часть из них рассчитана на совместную работу.
Здесь описано, какие связи реальны, чем они обеспечены и что произойдёт без
второго плагина.

## Три вида связи

Различать их важно: только первый вид механизм соблюдает сам.

| Вид | Чем обеспечен | Что будет без второго плагина |
|---|---|---|
| Объявленная зависимость | поле `dependencies` в манифесте | плагин не включится |
| Операционная ссылка | скилл вызывает чужой скилл по имени | работа деградирует, деградацию нужно отметить |
| Роль по договорённости | абстрактная роль в контексте проекта | роль просто не заполнена |

## Объявленные зависимости

```text
sdlc ──────► tdd-master
     └─────► functional-clarity

fpf-competency-bank ──────► fpf-integration
```

**`sdlc` → `tdd-master`, `functional-clarity`.** Реализующая роль обязана
активировать цикл тестов до продуктового кода, а все три роли опираются на
принципы ясности. Без них договор роли неполон.

**`fpf-competency-bank` → `fpf-integration`.** Банк содержит только данные —
своды компетенций. Исполнять их умеет резолвер из `fpf-integration`. Банк без
резолвера бесполезен, поэтому зависимость объявлена в этом направлении.

Обратной зависимости нет намеренно: резолвер работает с любым банком — проектным,
пользовательским или плагиновым, — и не требует именно эталонного.

Установка `sdlc` подтягивает обе зависимости автоматически. Включение плагина
включает и его зависимости; отключить зависимость по отдельности нельзя, пока
зависящий плагин включён.

## Операционные ссылки

**`sdlc` → `planner`.** Документация `sdlc` называет `planner` оркестратором, а
роли читают его таблицу стека. Обратной статической привязки нет.

**`functional-clarity` → `sdlc`.** Проверку внутренних идентификаторов и словарь
границ Functional Clarity передаёт ролям `sdlc`, чтобы не дублировать их.

**`clarity-language` → `functional-clarity`.** Первый отвечает за ясность текстов,
второй — за ясность кода. Вызова друг из друга нет, только разделение предмета.

**`plugin-testing` → `planner`.** Связь происхождения: методика собрана из разбора
красных прогонов `planner`. Во время работы `plugin-testing` его не вызывает.

## Роли по договорённости

`/plan-do` из `planner` не называет `sdlc` по имени. Он отображает абстрактные
роли — реализующую, ревьюера, архитектора, хранителя документации — на агентов,
записанных в `.claude/planner-context.md`.

Следствия:

- любой плагин, поставляющий подходящего агента, может занять роль;
- `sdlc` занимает три роли, `llms-keeper` — хранителя документации;
- незаполненная роль не ломает конвейер: `/plan-do` либо останавливается, либо
  выполняет ограниченную часть сам и отмечает это.

Именно поэтому в манифесте `planner` зависимостей нет: жёсткая привязка к
конкретному плагину отняла бы у проекта право выбрать своих исполнителей.

## Внешние проекты

Связи наружу устроены так же, как внутренние: без объявления в манифесте, но с
понятным договором.

**[senior-developer-tools](https://gitlab.com/mlopotkov/senior-developer-tools)**
расширяет инструментарий разработки: по плагину на язык или связку (rust, python,
typescript, web-svelte), плюс System Design для веб-сервисов, GitLab MR-flow,
Bruno, SQLite-паттерны. Методологию не дублирует: цикл тестов, принципы ясности и
роли разработки его плагины берут отсюда. Следствие для установки — подключать
нужно оба маркетплейса, иначе его агенты не найдут нужные скиллы.

**[core-team](https://github.com/noxxer/core-team)** организует командную работу
над проектом: фасилитатор распределяет работу между ролями, память живёт между
сессиями, качество держат гейты. Ставится не через маркетплейс — каталог
`.claude/` копируется в проект. Для `planner` это внешний поставщик продуктовой
проработки: в таблице способностей он проходит как установленный пакет, и
маршрутизация предпочитает его встроенному ограниченному поставщику, когда его
роли фактически доступны.

**[ailev/FPF](https://github.com/ailev/FPF)** — база для части плагинов, а не
плагин. `fpf-integration` читает эту спецификацию через MCP или локальную копию;
без источника скилл останавливается. `fpf-competency-bank` хранит своды,
собранные по её правилам.

Установленный пакет сам по себе поставщиком не считается: нужна доступная роль, а
её заявленная способность подтверждается фактическим результатом запуска. Это
различение описано в справочнике маршрутизации `planner`.

## Типовые наборы

**Полный цикл разработки:**

```text
/plugin install planner@i-m-senior-developer
/plugin install sdlc@i-m-senior-developer
```

Второй установкой подтянутся `tdd-master` и `functional-clarity`.

**Только качество текстов:**

```text
/plugin install clarity-language@i-m-senior-developer
```

**Работа со сводами компетенций:**

```text
/plugin install fpf-competency-bank@i-m-senior-developer
```

Подтянется `fpf-integration`. Банк дополнительно нужно подключить через
`~/.claude/frameworks.paths` — это делается вручную и осознанно.

## Решение: версии зависимостей не закрепляются

Зависимости объявлены без ограничений версии, то есть отслеживают то, что даёт
маркетплейс. Ограничения вида `~1.1.0` резолвятся по тегам отдельного плагина
`{плагин}--v{версия}`, а в этом репозитории теги общие — `vX.Y.Z`. Объявление,
которое не резолвится, выглядит как гарантия совместимости, не будучи ею.
Основание — [решение 6](../decisions.md).

Условие пересмотра названо явно: релиз каждого плагина нужно тегировать
отдельно.

```bash
claude plugin tag --push
```

Команда сама выводит имя тега из манифеста и записи маркетплейса, проверяет их
согласованность и требует чистое рабочее дерево. До перехода на такие теги
ограничения версий добавлять не нужно: они не смогут разрешиться.

## Проверка состояния зависимостей

```bash
claude plugin list
```

Проблемы зависимостей показываются здесь и в интерфейсе `/plugin` понятным
текстом. Машинно читаемый вид — `claude plugin list --json`: у плагинов с
проблемами появляется поле с ошибками, у исправных его нет.

Осиротевшие автоматически установленные зависимости убираются командой
`claude plugin prune`.
