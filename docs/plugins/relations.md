# Связи между плагинами

| Вид связи | Чем обеспечена | Без второго плагина |
|---|---|---|
| объявленная зависимость | поле `dependencies` в манифесте | плагин не включится: команда включения называет недостающую зависимость |
| вызов по имени | скилл активирует чужой скилл как `плагин:скилл` | работа деградирует, деградацию нужно отметить |
| ссылка по смыслу | текст называет другой плагин, но во время работы к нему не обращается | ничего не ломается: текст указывает на плагин, которого нет |
| роль по договорённости | абстрактная роль в контексте проекта | роль не заполнена |

## Объявленные зависимости

```text
sdlc ──────► tdd-master
     └─────► functional-clarity

fpf-competency-bank ──────► fpf-integration
```

- `sdlc` → `tdd-master`: реализующая роль обязана активировать цикл тестов до
  продуктового кода.
- `sdlc` → `functional-clarity`: принципы, на которые опираются все три роли.
- `fpf-competency-bank` → `fpf-integration`: банк хранит пакеты и объявляет
  публикатор пути; резолвер пакетов поставляет `fpf-integration`.

Обратной зависимости от банка нет: резолвер работает с любым банком —
проектным, пользовательским, плагиновым.

Установка подтягивает зависимости. Отключить зависимость по отдельности нельзя,
пока зависящий плагин включён.

## Ссылки между плагинами

| Откуда | Куда | Вид | Чем связаны |
|---|---|---|---|
| `sdlc:code-implementer` | `tdd-master:tdd-master` | вызов по имени | активируется до продуктового кода; без него скилл велит перейти на общие правила цикла и записать ослабление в отчёт |
| три роли `sdlc` | `functional-clarity:functional-clarity` | вызов по имени | активируется в работе роли; без него принципы применяются по памяти |
| `sdlc` | `planner` | по смыслу | тексты ролей называют `planner` оркестратором и указывают на его таблицу стека путём от корня репозитория |
| `functional-clarity` | `sdlc` | по смыслу | справочники называют роли `sdlc` местом, где исполняются проверка идентификатора, словарь границ и гигиена комментариев |
| `functional-clarity` | `tdd-master` | по смыслу | скиллы объявлены взаимодополняющими; при недоступном `tdd-master` скилл советует его установить |
| `plugin-testing` | `planner` | по смыслу | методика собрана из разбора его красных прогонов; во время работы не вызывает |

## Роли по договорённости

`/plan-do` не называет `sdlc` по имени. Он берёт роли — реализующую, ревьюера,
архитектора, хранителя документации — из `.claude/planner-context.md`.

- роль занимает тот плагин, которого назвал проект в каталоге агентов:
  подходящих агентов дают `sdlc` (реализация, ревью, архитектура) и
  `llms-keeper` (хранитель документации);
- незаполненная роль не ломает конвейер: `/plan-do` останавливается или
  выполняет ограниченную часть сам и отмечает это.

Поэтому в манифесте `planner` зависимостей нет.

## Внешние проекты

**[senior-developer-tools](https://gitlab.com/mlopotkov/senior-developer-tools)**
расширяет инструментарий разработки: по плагину на язык или связку (rust, python,
typescript, web-svelte), System Design для веб-сервисов, GitLab MR-flow, Bruno,
SQLite-паттерны, повседневные команды, спецификации модулей. Методологию не
дублирует: его агенты вызывают здешние скиллы по имени и без этого маркетплейса
их не найдут, поэтому подключать нужно оба.

**[core-team](https://github.com/noxxer/core-team)** организует командную работу
над проектом: фасилитатор, роли, память между сессиями, гейты качества. Ставится
копированием каталога `.claude/` в проект. Для `planner` — внешний поставщик
продуктовой проработки: в таблице способностей проходит как установленный пакет.
Свои копии этих методов он везёт внутри себя, поэтому рядом с плагинами того же
назначения указания начинают спорить.

**[ailev/FPF](https://github.com/ailev/FPF)** — база для `fpf-integration` и
`fpf-competency-bank`.

Установленный пакет поставщиком не считается: нужна доступная роль, и полное
покрытие даёт только описание, подтверждающее договор способности. Фактический
ответ проверяется по договору ответа уже после выбора.

## Версии зависимостей не закрепляются

Ограничения вида `~1.1.0` резолвятся по тегам отдельного плагина
`{плагин}--v{версия}`, а здесь теги общие — `vX.Y.Z`. Условие пересмотра —
переход на отдельные теги:

```bash
claude plugin tag --push
```

Основание — [решение 6](../decisions.md).

## Проверка состояния

```bash
claude plugin list            # версия, область, включённость каждого плагина
claude plugin list --json     # то же машиночитаемо
claude plugin prune           # убрать осиротевшие зависимости
```

Недостающую зависимость называет команда включения, а не список.
