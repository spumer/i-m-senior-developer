# Отчёт: planner

Проверяется продуктовый слой: попадает ли сырой замысел в проработку и
соблюдает ли встроенный поставщик свои ограничения.

## Последний прогон

| Параметр | Значение |
|---|---|
| Дата | 31.08.2026 |
| Claude Code | `2.1.250` |
| Версия плагина | `2.0.0` |
| Модель | `opus`, судья `haiku` |
| Порог | `1.0` (строгий) |
| Стоимость | `$1.95` |
| Длительность | 12 минут |
| `partial` | `false` |

Итог: **проверка проходит** — три случая, каждый по три повтора из трёх.

| Кейс | Оценка | Успешных повторов |
|---|---|---|
| `baseline-provider-limits` | `1.00` | 3 из 3 |
| `idea-routing` | `1.00` | 3 из 3 |
| `multi-step-input` | `1.00` | 3 из 3 |

## Что изменилось с прошлого прогона

Прогон выполнен на выпускаемом содержимом, где продуктовый помощник получил
реестр оснований в теле документа и обязательное имя поставщика в метаданных.
Поведение продуктового слоя от этих правок не пострадало.

Из набора сняты два случая про передачу выбора человеку. Причина в среде, а не в
поведении: `AskUserQuestion` в песочнице прогона модели не выдаётся, поэтому
критерий на число вызовов этого инструмента ничего не наблюдал — подробнее в
разделе известных ограничений.

`baseline-provider-limits` потребовал поднять `timeout_seconds` со 180 до 300,
как у двух других случаев. На первом прогоне этого дня два повтора из трёх
оборвались по таймауту с частичной оценкой `0.67` — это обрыв на середине, а не
отказ критерия: продуктовый помощник теперь читает ещё и реестр оснований, и
запуск стал длиннее. После правки времени случай даёт три повтора из трёх без
единой ошибки.

Отдельное наблюдение о доверии к прогонам: код возврата прогона зелёным набором
не является. Один из прогонов этого дня завершился нулевым кодом, тогда как
записанный результат проверку не проходил — `casesPassed` равнялся двум из трёх.
Итог снимается с `aggregate-result.json` и его проверкой в `evals/run.py`.

## Что покрыто

- `idea-routing` — сырой замысел попадает в продуктовую проработку, а не сразу
  в требования фичи.
- `multi-step-input` — вход из нескольких самостоятельных исходов не
  сворачивается в одну фичу.
- `baseline-provider-limits` — встроенный поставщик называет свои ограничения,
  не заявляет исследование пользователей и не пишет файлы, хотя запись ему
  разрешена кейсом.

## История: как проверка стала зелёной

Первый полный прогон был красным, и это оказалось находкой, а не сбоем.

1. **Маршрутизация не срабатывала вовсе.** Скилл `product-discovery` не
   вызывался ни в одном из шести повторов. Инструмент `Skill` и сам скилл при
   этом были доступны в трассе, то есть механизм доставки работал.
2. **Модель оказалась значимым условием.** На `sonnet` вызова не было ни разу;
   на `opus` те же кейсы начали вызывать скилл. Закрепление `sonnet` измеряло не
   ту среду, поэтому проверка переведена на `opus`.
3. **Формулировки описания дали неустойчивый результат.** После правок описания
   `idea-routing` стал проходить, а `multi-step-input` срабатывал 1 раз из 3.
   Устойчивости 3 из 3 переписывание описания не давало.
4. **Устойчивость дал структурный механизм.** В плагин добавлен хук
   `UserPromptSubmit`, который опознаёт продуктовый вход по явным признакам и
   требует вызвать скилл до ответа. После этого прогон стал зелёным.
5. **Один повтор ранее падал по таймауту 180 с.** Работающий скилл занимает
   больше времени, поэтому `timeout_seconds` у маршрутизационных кейсов поднят
   до 300. Позже по той же причине пришлось поднять его и у
   `baseline-provider-limits`: на прогоне 31.08.2026 два повтора из трёх упали
   по таймауту 180 с, причём частичная оценка обоих была `0.67` — обрыв на
   середине, а не отказ критерия. Продуктовый помощник с тех пор читает ещё и
   реестр оснований, поэтому запуск стал длиннее.
6. **Зелень оказалась неустойчивой, и причина была в порядке работы скилла.**
   `idea-routing` получил `0.83` при пороге `1.0`: проверяемое поведение не
   наступало вовсе. Проработка замысла требовала контекст проекта до первого
   вопроса человеку, а в пустом рабочем пространстве такого файла нет — все
   три повтора уходили в сканирование файловой системы по процедуре
   бутстрапа. Ходы кончались раньше разговора, запуск обрывался ошибкой на
   инструменте записи, и судья выносил решение по обрезанной трассе; два
   повтора он засчитал, один отклонил. Диалогу контекст проекта не нужен — он
   нужен выбору поставщика и созданию документа, поэтому при отсутствующем
   файле разговор идёт первым, а сборка контекста откладывается до момента,
   когда без неё нельзя продолжить. Правка подтверждена сравнением трасс на
   одном кейсе с тремя повторами: до неё все три обращались к процедуре
   бутстрапа и заканчивались ошибкой, после — ни одного обращения, ни одной
   ошибки, все три сразу разбирают проблему с человеком.

## Известные ограничения

- Проверка подтверждает поведение на `opus`. На `sonnet` маршрутизация в
  проработку не наблюдалась — это ограничение плагина, а не проверки.
- Сообщение `error: exit 1: (no stderr)` в этом прогоне не наблюдалось. Раньше
  его объясняли недоступностью `AskUserQuestion` в headless-режиме; разбор трасс
  показал другую причину — обрыв на отказе инструмента записи во время сборки
  контекста. Договор повтора в любом случае задают критерии и оценка, а не этот
  код.
- Живой сократический диалог, интерактивный выбор человека и проверка готовности
  документа в конце диалога одношаговыми кейсами не покрываются. Причина глубже
  отсутствия ответов человека и наблюдаема прямо: в песочнице прогона
  `AskUserQuestion` модели не выдаётся вовсе — списка инструментов в сохранённой
  трассе он не содержит, хотя кейс называет его в `allowed_tools`. Поэтому
  критерий на число вызовов этого инструмента измеряет состав песочницы, а не
  поведение плагина. Два таких случая из набора сняты; вернуть их можно только
  вместе со средой, которая инструмент выдаёт.
