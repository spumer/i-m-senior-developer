# Витрина плагинов Claude Code

Девять плагинов для Claude Code, собранных из практики одной команды. Каждый
плагин — одна компетенция: планирование, проектирование, тесты, ревью, ясность
текстов, проверка самих плагинов. Ставятся по отдельности; работают вместе, если
их поставить вместе.

Здесь — системное представление и описание каждого компонента. Философия, из
которой всё это выросло, живёт в
[корневом README](https://github.com/spumer/i-m-senior-developer/blob/master/README.md)
и здесь не пересказывается: документация показывает, как эта философия
превращается в конкретные плагины, файлы и договоры.

## Как читать эту документацию

Каждая страница компонента отвечает на четыре вопроса в одном и том же порядке:

1. **Что это** — из чего плагин состоит и как срабатывает.
2. **Для чего это** — какую работу он забирает у человека.
3. **Как пользоваться** — минимальный рабочий сценарий.
4. **Когда НЕ пользоваться** — где он бесполезен или вреден.

Четвёртый вопрос обязателен. Инструмент без границ применения приходится держать
в голове целиком, а это ровно та когнитивная нагрузка, от которой плагины и
должны избавлять.

Ни один плагин не запускает другой напрямую. Связь идёт либо через объявленные
зависимости, либо через роли, которые проект заполняет сам —
[Связи между плагинами](plugins/relations.md).

## Три решения, определяющие всю систему

**Результат шага — файл, а не сообщение в чате.** Замысел, требования среза,
архитектура и план выполнения лежат в репозитории под версионированием. Поэтому
изменение видно в диффе, а история принадлежит git, а не переписке. Отсюда же
гейт свежести: план выполнения связан с версией архитектуры, и по устаревшему
плану реализация не запускается.

**Полномочия ролей разделены.** Ревью не правит код, реализация не придумывает
архитектуру, планировщик не запускает исполнение. Роль, которая проверяет свою
же работу, проверяет собственные решения — и ревью превращается в
самооправдание.

**Зависимость объявляется только там, где без второго плагина договор неполон.**
Остальное — роли по договорённости, которые проект заполняет своими агентами.
Иначе витрина превращается в комбайн, где нельзя взять одну деталь.

## Когда всё это не нужно

- **Разовая правка в чужом проекте.** Конвейер планирования оправдан, когда за
  задачей будет следующая; для одной опечатки он лишний.
- **Работа без репозитория.** Половина ценности — версионируемые файлы; без git
  остаются только промпты.
- **Готовое чужое соглашение.** Если в проекте уже принят другой SDLC-контур,
  ставьте отдельные плагины (тесты, ясность кода), а не весь конвейер.

## Локальная сборка сайта

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install zensical
zensical build
```

Готовый сайт появится в `site/`. Каталог `site/` не коммитится: его собирает CI.
