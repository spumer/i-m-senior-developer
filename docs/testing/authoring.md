# Формат кейсов и критериев

## Из чего состоит кейс

Кейс — каталог под `evals/` плагина. Минимальный состав:

```text
evals/<case>/
├── prompt.md
└── graders/
    └── <criterion>.md
```

`prompt.md` — frontmatter с параметрами запуска, тело файла становится запросом
пользователя. Каждый файл в `graders/` — один критерий с полем `type` во
frontmatter.

Дополнительные возможности требуют `case.yaml`: подготовка файлов перед запуском,
воспроизведение записанного диалога и дополнительные каталоги.

Значения по умолчанию: три повтора, десять ходов, 300 секунд на повтор.

## Шесть типов критериев

| Тип | Что проверяет | Стоимость |
|---|---|---|
| `regex` | текст ответа, трассу или содержимое файла | бесплатно |
| `tool_used` | сколько раз вызван инструмент | бесплатно |
| `tool_order` | порядок двух вызовов | бесплатно |
| `file_exists` | создан ли файл во время прогона | бесплатно |
| `llm` | смысловое соответствие по рубрике | платно |
| `baseline` | сравнение с сохранённой трассой | платно |

Детерминированные критерии предпочтительнее: они дешевле и дают одинаковый
результат. Модель-судья нужна там, где проверяется смысл ответа.

## Ловушки, проверенные на практике

**`max: 0` без `min: 0` не работает.** По умолчанию `min` равен `1`, поэтому
запрет вызова инструмента задаётся обеими границами сразу.

**Запрет невозможного ничего не доказывает.** Проверка «файлов не пишет» имеет
смысл только когда инструмент записи выдан на двух уровнях: кейс запрашивает его
в `allowed_tools`, а оператор разрешает флагом `--allow-tools Write`. Иначе
критерий запрещает то, что и так недоступно.

**`files` — это список путей, а не содержимое.** Для проверки содержимого нужен
явный источник-файл.

**`file_exists` видит только созданные файлы.** Изменённый или подготовленный
заранее файл он не заметит.

**Критерий `tool_used` на инструменте `Skill` в режиме сравнения с базой
автоматически становится индикатором наличия плагина** и выпадает из подсчёта
очков. Для продуктовых кейсов сравнение с базой отключают.

## Что проверять не eval

Детерминированный код проверяется обычными тестами рядом с исходником: они
точнее, дешевле и не зависят от решения модели. Не нужно создавать кейс, который
ищет строку в ответе там, где тест может вызвать функцию и сверить результат.

Eval нужен для того, что существует только в поведении модели: срабатывает ли
скилл на естественной формулировке, не уходит ли работа в реализацию раньше
времени, соблюдает ли роль свои ограничения.

## Чего проверить нельзя

Дочерний агент запускается в headless-режиме, механизма ответа на живой вопрос
человеку в формате кейса нет. Поэтому одношаговыми кейсами нельзя покрыть:

- интерактивный выбор человека;
- полный сократический диалог как последовательность вопросов и ответов;
- поведение после человеческого решения;
- проверку готовности документа, которая наступает в конце диалога.

Для поведения после нескольких ходов нужен записанный диалог: провести настоящий
обмен, сохранить транскрипт в каталоге кейса и оценивать следующий ход. Написанный
от руки диалог свидетельством не является — кейс начнёт проверять придуманное
поведение.

## Что загружается в песочницу

Каждый повтор получает новый временный каталог. В дочернюю сессию не попадают
проектные и пользовательские настройки, `CLAUDE.md`, память, пользовательские
хуки и другие установленные плагины. Загружается только проверяемый плагин —
включая его собственные хуки.

Песочница не блокирует сеть и не является границей безопасности. Подготовительные
скрипты выполняются от имени текущего пользователя, поэтому по умолчанию
выключены.
