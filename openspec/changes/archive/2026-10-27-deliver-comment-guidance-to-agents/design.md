# Design

## Context

Изменение уже реализовано в `functional-clarity` и ссылках из `sdlc`. Этот документ записывает выбранное устройство и границы проверок для PR; он не означает, что требования были подготовлены до реализации. Причина изменения описана в `proposal.md`.

Хуки передают текст в контекст модели. Ни описание навыка, ни памятка не являются машинной проверкой качества комментариев.

## Goals / Non-Goals

**Goals:**

- Связать требования доставки правила с существующими хуками и проверяемым выводом.
- Сохранить один полный источник правила и один общий текст памятки.
- Указать случаи пропуска доставки и проверки исправлений, найденных при ревью.

**Non-Goals:**

- Перехватывать каждый вызов `Write` или `Edit` исполняемым кодом.
- Обещать активацию навыка или соблюдение инструкции моделью на основании теста хука.
- Исправлять код хуков, менять содержание правила, зависимости или версии плагинов в документационном коммите.

## Decisions

### Полное правило поставляется отдельным навыком

`skills/comment-style/SKILL.md` содержит правило и описание запросов, к которым оно относится. Остальные инструкции направляют к этому навыку. Прежний справочник не оставлен второй копией: две версии правила могли бы разойтись.

### Обе точки запуска используют общую памятку

`hooks/comment-gate.txt` хранит краткое правило, а каждый хук подставляет корень установки. Альтернатива — отдельный текст внутри каждого хука — потребовала бы синхронизировать одинаковые ограничения вручную. Полный путь позволяет открыть навык без поиска относительно рабочего каталога проекта.

`SessionStart` проверяет файл через `iconv` с UTF-8 на входе и выходе. Вывод добавляется только при успехе всей проверки: корректный префикс повреждённого файла тоже отбрасывается. При отсутствии утилиты остаётся выжимка принципов без памятки. В отличие от чтения через Python этот вариант не добавляет зависимости начала сессии от Python.

### Субагент получает правило независимо от своей роли

В `hooks/hooks.json` событие `SubagentStart` не ограничено типом агента. Python-обработчик формирует JSON по договору хоста; команда оболочки пропускает обработчик, если `python3` отсутствует. Ошибки чтения и декодирования необязательной памятки приводят к отсутствию дополнительного контекста, а не к отказу запуска субагента.

При сериализации JSON Unicode-символы экранируются стандартным способом. После разбора потребитель получает исходный текст, а запись JSON не требует поддержки этих символов кодировкой stdout.

### Проверка доставки отделена от проверки смысла

Существующие тесты проверяют подстановку пути, JSON и случаи пропуска. Для ASCII-кодировки stdout и повреждённого UTF-8 в начале сессии добавлены регрессионные тесты: оба упали до исправления и прошли после него. Положительный сценарий начала сессии сохраняет Unicode и абсолютный путь при пробелах в корне установки.

Запуск реальных команд хуков проверяет их подключение через манифест. Согласование исключения для `XXX` и границы обещаний памятки проверены чтением, без автоматического поиска слов в промпте. Платная оценка поведения модели не запускалась.

## Risks / Trade-offs

- Модель может не выполнить полученную инструкцию. Спецификация обещает доставку памятки и описывает предписание перед правкой, но не выдаёт его за автоматический запрет записи.
- При недоступном тексте субагент запускается без памятки. Это выбранный договор необязательной подсказки; такое отсутствие не считается доказанной доставкой.
- Отсутствие `iconv` в среде означает пропуск памятки в `SessionStart`. Выжимка принципов и успешный код завершения сохраняются; это ограничение указано в README плагина.
- Успех структурной проверки и unit-тестов не означает, что модель соблюдает правило. Для этого требуется отдельная поведенческая оценка.

## Migration Plan

Изменения спецификации добавляются к существующей возможности `functional-code-clarity`; прежние требования и сценарии сохраняются. Ссылка на удалённый справочник исправляется в исходном функциональном коммите. Документы OpenSpec и новые требования записываются отдельным коммитом.

После завершения проверок изменение можно архивировать с уже синхронизированной основной спецификацией. Выпуск и повышение версий в эту правку не входят.
