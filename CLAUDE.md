## Версионирование плагинов

Версия плагина в `.claude-plugin/plugin.json` считается **относительно последнего релиза (тега `vX.Y.Z`), а не относительно предыдущего изменения**. Бамп делается **один раз — при выпуске**, отражая суммарный характер изменений плагина с последнего релиза (наибольший применимый шаг semver). Внутри невыпущенного окна версию на каждый коммит не поднимают: Claude Code кеширует по версии только у **выпущенных** плагинов, поэтому промежуточные бампы ничего не дают и лишь копятся.

Плагин, созданный после последнего тега, ещё не выпускался — правки в него до релиза версию не бампают (он весь — один будущий первый выпуск).

Как считать шаг (**Semantic Versioning**, semver.org) — относительно версии плагина в последнем теге:
- **MAJOR** (1.0.0 → 2.0.0) — breaking changes: удалены/переименованы команды, агенты, изменён формат
- **MINOR** (0.1.0 → 0.2.0) — новая функциональность: добавлены команды, агенты, скиллы
- **PATCH** (0.1.0 → 0.1.1) — исправления: баги, опечатки, уточнения в промптах

## Релизный workflow

1. Внести изменения в плагин(ы) — коммитами по мере работы, **без бампа версии в каждом**.
2. При выпуске — бампнуть `version` каждого затронутого плагина **относительно его версии в последнем теге** (один шаг semver на весь набор изменений с релиза).
3. До релизного коммита прогнать локальные тесты и `claude plugin validate --strict`. Для каждого затронутого плагина со своим `evals/run.py` обязателен полный успешный прогон этого файла на выпускаемом содержимом. Для planner:
   ```bash
   python3 plugins/planner/evals/run.py
   ```
   Частичный прогон, достигнутый лимит стоимости, пропущенный кейс или результат ниже порога блокируют релиз. Порог строгий: три повтора из трёх. Понижать порог вместо исправления поведения запрещено.
4. Обновить отчёт по затронутому плагину в `docs/reports/` фактическими числами из свежего `aggregate-result.json`. Порядок — в `docs/testing/running.md`.
5. Создать релизный коммит и отправить его без тега: `git push`.
6. Дождаться успешного GitHub Actions workflow на точном SHA релизного коммита. Перед тегом рабочее дерево должно быть чистым, а локальная ветка — совпадать с отправленным коммитом.
7. Создать и отправить тег: `git tag vX.Y.Z && git push --tags`.

## Сообщения коммитов

Заголовок не начинается с инфинитива: «добавить», «согласовать», «проверять» —
это калька с английского императива, по-русски так не пишут. Заголовок — законченное
утверждение о результате: «Договоры передачи между ролями согласованы», «Добавлен
хук продуктового входа».

Префикс по типу изменения и область сохраняются: `fix(planner,sdlc): …`,
`docs: …`. Тело объясняет причину — почему так, а не перечисление файлов, которые
и так видны в диффе.

## Документация

Сайт документации собирается Zensical из `docs/` и публикуется в GitHub Pages
workflow `docs.yml` при пуше в `master`. Разделение содержания обязательно:

- `docs/plugins/` — что даёт каждый плагин и как плагины связаны между собой;
- `docs/testing/` — общие правила проверки плагинов, одинаковые для всех;
- `docs/reports/` — отчёты по конкретным плагинам, по одному файлу на плагин.

Отчёт описывает наблюдённый прогон, а не замысел проверки. Пилотный запуск с
одним повтором успехом не записывается.

Локальная сборка: `zensical build`. Каталог `site/` не коммитится.

## Зависимости плагинов

Межплагинные зависимости объявляются полем `dependencies` в манифесте плагина и
только когда без второго плагина договор первого неполон. Объявленные сейчас:
`sdlc` → `tdd-master`, `functional-clarity`; `fpf-competency-bank` →
`fpf-integration`.

Ограничения версий не добавлять, пока релизы плагинов не тегируются отдельно как
`{плагин}--v{версия}` через `claude plugin tag`: общий тег `vX.Y.Z` для них не
резолвится. Разбор видов связи — в `docs/plugins/relations.md`.
